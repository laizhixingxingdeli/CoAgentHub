# 三层沟通优化实施方案（2026-10-04，用户已确认平台实施）

## 目标与原则
以减少完成时间和无效往返为目标，维持 L3 定需求、L2 定方案及验收、L1 按工单实现的职责。用户执行中修改要求是正常行为，最终按最后确认的要求验收；修订号用于说明信息来源、识别遗漏，不作为一变化就停机或全量重做的门禁。本文件是方案，不代表已实现或已验证运行效果。

已有适配器简报透传和提示词修正已整合到 coagent-pi 的 ef61ada；本方案不重复实施。当前平台已有工单冻结、修订记录、L2 逐条验收及提交来源校验，但缺少在途变更可靠通知、变更影响与旧证据的明确关联，以及完整的阶段耗时归因。

## 推荐顺序与切票
| 顺序 | 票 | 具体改动 | 主要责任层 | 性质 |
| --- | --- | --- | --- | --- |
| 1 | COM1 简报与唤醒指令一致 | 消除协调者每次唤醒都必须 get_mission 与简报优先之间的冲突；阻塞和打回统一表达 | application（pi 提示词已完成） | 现有流程修正 |
| 2 | COM2 工单快照保护 | 修复 contextRefs 元素仍可被内部引用修改；保留合法整单修订 | kernel | 现有不变量修复 |
| 3 | COM3 运行中需求变更闭环 | 保存明确差异，L2 判断影响，可靠交给受影响运行并确认应用 | application + runtime 端口 + pi | 已确认，调查并细化后冻结 |
| 4 | COM4 验收与成果复用 | 建立受影响验收项和证据关联，仅重验变化涉及的部分 | application | 已确认，调查并细化后冻结 |
| 5 | COM5 耗时归因 | 在已有时间线上区分排队、运行、验证和等待决策，显示可测数据 | application 观测 + web | 已确认，核实观测接缝后冻结 |

先落地 COM1、COM2；COM3 与 COM4 形成一个完整的需求变更闭环，再接 COM5。每票保留独立验收边界，互不依赖的改动可同批验证、同一次空档重启。COM3 的具体运行时接口须调查确认后冻结，不能靠提示词模拟可靠送达。

## COM1：减少现有流程中的无效往返
问题：启动简报已包含工作项索引、上一跳变化和返工要求，但协调者唤醒正文仍要求先查询 Mission，产生重复读取；提示词之间的冲突也使执行路径不稳定。

改动：在 src/application/orchestrator.ts 的协调者唤醒正文对齐已经完成的 coagent-pi/src/roles.ts，统一为“先使用本次简报；缺少必要详情、遇到并发变化或平台拒绝时再查询”。简报不能替代派发、提交和验收时的权威状态校验。审查本轮已提交项后继续派发可执行工作，不为每次验收额外开一轮协调者；保留依赖、预算和升级门禁。

AC4 收尾实际暴露了额外交接缺口：工单引用上层契约五项验收，却没有给执行者可见的原文，测试完成后额外查找约 8 分半。协调者派发时应携带相关验收原文或完整对应关系，不要求执行者寻找它无权限取得的契约；这比只减少一次重复查询更直接影响完成时间，不新增协议字段或硬性语义门禁。`send_back` 的 accepted 工作项处置还须核实平台实际允许顺序，不放宽修订状态。

阻塞使用现有 reason/whatWasTried/needsFromUpstream，一次写清已核实事实、尚缺决定及建议；同一阻塞相关问题合并，互不相关且后续调查才出现的问题允许补报。打回使用现有 requiredChanges，明确验收项、实际表现、预期表现和复验方法。执行者提交前在现有证据中覆盖工单验收和验证命令，L2 仍作独立验收；不额外建立一套重复的执行者验收协议。

验收：完整简报场景不再强制重复 get_mission；缺失详情场景仍能查询；一轮能审查多个结果并派发无依赖工作；blocked/reject 的原有门禁和角色权限不变。参照 test/platform.test.ts、现有协调者唤醒测试及 pi 的 roles.test.ts、extension.test.ts。预期收益是减少每次正常唤醒的一次重复查询，实际省时通过事件计数验证，不承诺百分比。

## COM2：让工单冻结符合已有承诺
问题：freezePayload 只保护对象和直接数组，contextRefs 数组元素可通过内部引用被改动，可能绕过修订记录。已核实的是内存对象保护缺口，并非已证明的外部 API 攻击路径。

改动：在 src/kernel/work-item.ts 的 freezeWorkOrder 工单构造边界明确复制并冻结嵌套数据，采用与实际数据形状相符的小函数，避免给所有载荷引入复杂通用框架。合法改工单仍走既有 reviseOrder，状态许可、修订号和事件保持原语义；不绑定一个永远不能变化的需求版本。

验收：修改调用方原始 contextRefs 不影响已创建工单；对工单内部元素赋值无法改变快照；合法修订仍产生新工单及修订记录；旧输入兼容。参照 test/work-item.test.ts 与 test/platform.test.ts，测试边界和引用隔离，不逐字段复制实现测试。

## COM3：运行中修改要求，可靠通知且有结果
用户确认新要求后，L3 保存目标差异；L2 判断哪些工单受影响、哪些可以继续、哪些要返工。L1 只接收 L2 已明确的工单调整，不自行解释或改变项目目标。

建议的变更记录包含：唯一 changeId、来源修订、改变/保留/作废的要求、受影响验收项、L2 处理结论、目标工作项或 Attempt、送达与应用记录。区分“平台保存”“运行时送达”“执行者已按更新继续”，三者不能互相冒充；重复投递必须幂等。连续变更可合并待送内容，但保存来源记录，不能让迟到的旧要求覆盖新要求。

现有 pi agent-entry.ts 读取 stdin 到 EOF 后启动，无法直接用原输入管道追加通知。实施前先核实当前 SDK、src/runtime/spawn.ts 和现有带运行令牌的接口，选择一种独立控制通路；建议由运行时在工具/回合安全边界获取更新并反馈接收记录。没有可验证的通路时，不宣称实时生效，转入明确的协调者续跑边界处理。这个接口选择是冻结票前必须完成的调查项。

应用规则：兼容变化继续执行；验收变化更新目标并安排相关复验；范围扩展先由 L2 调整工单；互斥或无法安全继续的变化才暂停/取消受影响运行。正在执行的工具默认等安全边界，不能假定模型收到消息就能撤销文件写入。旧适配器没有通知能力时显示待应用，不伪造 ACK，不按修订号自动重启全部工作。

改动落点：application 管持久变更记录、投递及影响决策；runtime 端口表达控制能力；pi 负责向当前会话应用更新及回执；kernel 保持状态约束。与 L3 Delivery 分离，不借用交卷 ACK 作为执行者变更确认。需要记录 ADR，说明单写者、持久性、兼容和恢复边界。

验收：运行中改要求可在安全边界应用；重复及乱序不重复应用或回退；重连后待应用记录可恢复；不支持通路的适配器明确降级；只停受影响且不能继续的运行；最终交卷满足最新已确认要求。使用临时仓库和 scripted runtime 验证，不派发真实平台任务作单测。

## COM4：只复验受影响部分，避免实现漂移
问题：平台已保留 accepted 成果，也会复用同 submittedAttemptId 的验证报告，但没有完整的“需求变化—受影响验收—证据”关系；同一个提交来源不足以证明后来工作区和要求仍兼容。

改动：L2 对每次变更列出受影响验收项、涉及工单及所需复验；未受影响项可以保留已有验收，并写明复用依据。证据保留真实提交/代码来源、覆盖的验收项和验证上下文；报告复用还要核实相关代码与测试条件，没有可靠依据时标为待复验。先做明确关联和失效判断，不做自动语义推断系统或跨环境测试缓存。

最终交卷按最新要求逐项核对：受影响项必须有更新后的证据，未受影响项允许有来源清楚的旧证据。不能因为合同修订号不同把所有项判失败，也不能因为以前 accepted 就自动证明新要求满足。运行时间线展示变更、L2 影响结论、应用及复验，帮助用户知道当前实现依据。

验收：只改描述且行为不变可保留结果；修改行为要求只失效相关项；改变相关代码或验证环境不能盲用旧报告；退回再提交不误挂旧 Attempt 证据；最终遗漏一项新增要求不能交卷。参照 test/platform.test.ts、test/orchestrator-standard-validation.test.ts，保留既有提交及验证来源门禁。

## COM5：把耗时变成可定位的原因
先利用现有 attempt.started/ended、工具开始/结束、验证时间和等待状态。可直接显示运行、工具、验证、等待决策的可测区间；排队时间需要补保留入队/认领时点，不能把不断覆盖的 updatedAt 当完整历史。

展示沿用用户已确认的单条 Mission 时间线，最新在顶上；增加阶段耗时及已有 token 数据，不新增重复时间线。工具并发按区间并集计算占用，验证若与运行重叠要标明，避免叠加成总耗时。模型生成、网络传输和不可观测空档显示“未分类”，不能把无工具时间全部标成思考，也不能用 token 推算精确耗时。

验收：串行和并行工具耗时计算正确；等待决策与执行区分；缺失事件标未知；重连不重复计时；历史 Mission 数据缺项时可读。参照 test/runtime-events.test.ts、test/budget-command-facts.test.ts 及现有前端时间线测试，不改变调度策略。

## 交付、验证和生效
每票实施前核实接口形状、现有测试和数据兼容；源码在独立分支，主工作区保持干净。新协议同时验证平台和适配器，支持旧记录和旧适配器的明确降级。先跑相关测试，再按仓库要求运行全量；只有既有 HAOFF1 的 7 个 skip 可按当前基线解释，其他失败或新增 skip 要处理。

服务仅在没有运行中 agent 的批次空档重启；不直接改状态文件，不恢复 AC4 充当测试。合入 master 另等用户明确授权。上线后用实际 Mission 观察协调者唤醒次数、重复查询、blocked/reject 往返、变更送达/应用延迟、首次验收通过率和完成时间，token 作为辅助原因；测试通过不能代替实际省时效果。

## 已确认范围与实施边界
用户要求先补齐插件、完成 AC4 收尾，再实施 COM1、COM2、COM3、COM4、COM5。COM1、COM2 是现有能力修正；COM3、COM4、COM5 已随本方案获用户授权通过平台实施；COM3 的运行时接线仍须协调者调查后冻结具体工单。方案不包括自动改需求、自动扩范围、强制任务等级/搜索次数/时间门禁、新预算策略、鉴权 D1d、预算 B7，也不重新引入检视待办或第二条运行时间线。
