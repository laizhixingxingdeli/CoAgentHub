# ADR-0009:判据必须指名它所裁定的事实

**状态**:已接受(2026-08-31)

## 背景

2026-08-30/31 一轮排障中查出的八个缺陷里,**六个是同一个形状**。
它们分布在互不相干的模块 —— 额度分级、产出判定、任务分流、冷却合并 ——
但错法完全一致:

> **判据读的是一个近似量,而它被当作了另一个事实来用。**

| 缺陷 | 判据实际读的(近似量) | 它被当作的事实 | 沉默的前提 |
|---|---|---|---|
| 额度分级 | 命中行的**措辞**(英文关键词) | 距恢复还有多久 | 供应方说英文 |
| 干净退出的产出判定 | `checkpointRef..HEAD` **提交计数** | 本次运行有没有产出 | 工作树被本次运行独占 |
| 发现项票的分流 | **消息类型**(是不是 findings) | 这次工作动没动冻结的 spec | 发现项都是修复 |
| 冷却合并 | **写入到达顺序** | 哪个恢复时刻更可信 | 后写的信息更多 |

四个近似量**在它们各自成立的环境里都是对的**。失效的从来不是判据本身,
而是那条**从没被写下来的环境前提**。前提一旦不成立,判据不会报错 ——
它会给出一个语法正确、语义错误的答案,并且沿着调用链一路传下去。

三例已在生产兑现:

- 群内三个执行器都说中文,它们真正的瞬时限流全部误判为额度耗尽,吃 300 分钟冷却
  —— 修这个病的那张票,在它最可能发生的形态上原封不动。
- 检视者提交一份 spec,就使一个撞了真 429 且未提交的执行器被判为「有产出」,
  任务落 `done`、不进冷却,下一张票继续派给它。
- 一次撞额度产生两条终态写入,解析不出恢复时刻的那条因排在后面而覆盖了准确值,
  执行器被多停 3 小时 14 分。

### 为什么三层检视没有拦住

L2 是**对着 spec 的验收标准**查的,而这类缺陷常常**就写在 spec 自己的判据表里**。
额度分级那例中,spec、实现、L2 三方各自都没错:spec 的判据表用英文措辞写死,
执行器逐字实现,L2 逐条对照全绿。**盲区是 spec 的,验收标准继承了同一个盲区。**

## 决策

**一、判据必须指名它所裁定的事实,并写下它成立的前提。**

任何用于分流、放行、拦截的判据,在代码注释或 spec 中必须回答两句:

1. **这个判据在拿什么代替什么?**
2. **那个代替在什么条件下不成立?**

第 2 句写不出来,通常意味着还没想清楚,而不是没有前提。
前提一旦写下,它就成为可被测试、可被检视、可在环境变化时被重新审视的对象。

**二、同一个事实只能有一个判定出处。**

同一事实出现两个判定点时,必须收敛为单点,调用方只读结果、不自行判定。
两套判据一定会在某个输入上分叉,而分叉的那一刻没有任何人在看。
(额度分级与冷却时长曾对同一行给出不同答案:一个读得出中文时刻,另一个读不出。)

**三、当多个来源写同一个事实时,合并规则必须按置信度,不得按到达顺序。**

低置信的兜底猜测不得覆盖高置信的解析结果。**保守是「无信息时的默认」,
不是「压过有信息的结论」。** 因此冷却一类的值必须携带来源标记
(`parsed` / `fallback`),而不能只是一个裸数字。

**四、把「换一个真实输入」变成检视动作,而不是靠想。**

判据的推广性**必须用真实输入实跑验证**,不得靠阅读代码推断。
上述中文盲区是拿群内执行器的真实回显跑了一遍才暴露的;
在此之前,三方的静态审阅都判它通过。

## 落地

- **L1(执行器自检)**:新增坏味道项 —— 本次改动引入的判据,是否写明了它裁定的
  事实与成立前提;是否与既有判定重复。
- **L2(协调者验收)**:验收标准中出现判据表 / 关键词表 / 模式匹配时,
  额外核对该表是否覆盖**本群实际执行器**的真实输出形态,而不只是 spec 举的例子。
- **L3(检视者)**:检视项新增 —— 用**验收标准之外**的真实输入实跑本次判据,
  确认它推得开;并核对是否引入了同一事实的第二个判定出处。
- **写 spec 时**:判据表必须标注其**主轴**(它裁定的那个可计算的事实)与
  **兜底**(无信息时的默认),两者不得混为一档。

## 后果

- 写判据变慢一点:多写一句前提。
- 换来的是:前提成为显式对象。环境变化时(多一种语言、多一个并发写入者、
  工作树不再独占),失效的判据能被找出来,而不是继续给出语法正确的错答案。
- 本 ADR 不追溯修改既有判据;四个已知实例各自有冻结的 spec 在队列中。
