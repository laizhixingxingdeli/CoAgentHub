# ADR-0008:执行器适配——机制归代码,字段归配置

**状态**:已接受(2026-08-29)

## 背景

接入第五个执行器(pi)时,清点了「接入一个新执行器要改哪些地方」,发现适配点分散在
三处互不相干的机制里,且都以执行器 key 为分支条件:

| 适配点 | 位置 | 形态 |
|---|---|---|
| 实时输出解析 | `output-parser.ts` `createExecutorOutputParser` | `switch` |
| token 账目 | `token-usage.ts` `collectTokenUsage` | `if-else` 链 |
| 最终汇报正文提取 | `queue.ts` | 三元链,**无 default 兜底** |
| 注册配置 / 展示名 / 并发上限 | `executors.ts` `DEFAULT_EXECUTORS` | 硬编码数组 |

两个后果已经实际发生:

1. **静默漂移**。`token-usage.ts` 里有 `collectClaude()`,但 `DEFAULT_EXECUTORS`
   里根本没有 `claude` 这个 key —— 这段收集器是死代码;反过来 `reasonix` /
   `hermes` / `win-hermes` 有 key、无任何适配。没有任何一处能回答「哪家缺哪一项」。
2. **内置执行器用户改不动**。`PATCH /executor/:key` 对内置 key 返回 403、
   `DELETE` 返回 409。想给 AtomCode 换个参数只能改代码。而开机
   `ensureExecutorParticipants` 会无条件注册全部内置 participant —— 哪怕这台机器
   一个都没装,协调者照样看得见、派得过去、spawn ENOENT。

同时观察到:四家 CLI 的输出差异**几乎全是字段名的差异,不是逻辑的差异**。
pi 的 `tool_execution_start.toolName` 与 codebuddy 的 `content[].type == "tool_use"`
在语义上是同一件事,只是路径不同。

## 决策

**一、机制归代码,字段归配置。**

- **字段**(哪个路径是工具名、哪个是正文、usage 在哪、怎么聚合、哪些行是信封噪音)
  → 声明式配置,存 DB,网页可编辑。只有**路径与枚举**,没有条件、没有循环 ——
  是字段映射表,不是 DSL。
- **机制**(运行方式 `kind`、行式解析引擎本身、排队/冷却/重派/权限判定)→ 代码。

判据:**「字段名不一样」归配置,「机制不一样」归代码。**据此,以下仍必须写代码:
新的 `kind`(gRPC / WebSocket / 多轮交互协议)、非行式输出(TUI 转义流、二进制)、
超出「env + bin」的鉴权流程。

**二、取消内置执行器。**

`DEFAULT_EXECUTORS` 删除,`executor_config` 表成为唯一真相源;一次迁移把现有七条
写成 DB 行。`isBuiltinExecutorKey` 及其 403/编辑禁令、409/删除禁令一并删除。
`EXECUTOR_BIN_<KEY>` 环境变量覆盖保留 —— 那是「同一份配置在不同机器上路径不同」,
属于部署,不属于接入。

推论:执行器列表里有的,就是这台机器上真的配了的。这比「无条件注册全部内置」更准。

**三、下发权归群内角色,不归执行器配置。**

现状是两道串联的门:

```
canCarryDispatcher = 群内角色 ∈ DISPATCH_ALLOWED_ROLES  &&  !senderIsPureExecutor
                     └─ 已经是群作用域 ─┘                  └─ canDispatch,全局 ─┘
```

第一道已经是群作用域(`group_members.roles`)。第二道 `canDispatch` 是挂在执行器
配置上的**全局否决**,只能做减法。既然下发权本就是群内语义,**删除第二道门**,
由群内角色单独裁定。

推论:`DISPATCH_CAPABLE_KEYS` 与 `ExecutorConfig.canDispatch` 一并删除;内置的
`reviewer` 那条**假执行器**(注释写明「永远不会被 spawn」,存在的唯一理由就是给
`DISPATCH_CAPABLE_KEYS` 挂一个 key)随之消失,不迁移成 DB 行。

**四、下发权不进接入表单。**

授予下发权是权限动作,不是接入偏好。它通过「在某个群里给这个 participant 配
coordinator / reviewer 角色」表达 —— 已有的成员管理路径,不新增开关。

## 后果

**正面**

- 接入新执行器的常规路径变成:网页填表 → 接入向导跑一次最小任务、自动推断输出画像
  → 预览确认。不改代码、不发版。
- 三个适配消费点读同一份画像,「哪家缺哪一项」在一张表里可见,漂移不再静默。
- 用户能改任何执行器的参数与模型,不再有改不动的七条。

**代价(已知,不隐藏)**

- **18 个测试文件**直接引用内置 key,须改为 fixture 注入。这是本次改造最大的一块
  隐性成本。
- 全新安装的执行器列表为空,首次使用必须先接入一个 —— 由接入向导承接。
- 配置填错的失败模式从「编译不过」变成「运行时行为退化」。缓解:所有画像字段
  可缺省,认不出的行**逐字保留**(既有 R3 规则不变),最坏退化到通用解析器水平;
  且向导以真实输出预览为准,而不是让用户凭空手写路径。

**放弃的方案**

- *给每家写一个 adapter 模块 + 注册表*:收敛了分散,但接入仍需改代码发版,
  达不到「用户自助接入」。
- *纯通用启发式,不要画像*:通用规则能覆盖大部分形态,但对「每消息 usage 不累计」
  (pi)这类结构性差异会系统性报错,且无处修正。画像是那个可修正的旋钮。

## 相关

- ADR-0003(单调度器执行器):调度机制仍归代码,本 ADR 不触碰。
- ADR-0005(角色解绑与群内提示词):本 ADR 的第三条是它的直接延伸 ——
  角色是群内职务,下发权自然也是。

## 后续决策

`specs/executor-adapter-registry.md`(Frozen, 2026-09-02)将落地路径调整为
**先做适配器注册表(代码),声明式输出画像暂缓**。实证理由:四家里三家的 token
账目读的是家目录会话文件(扫目录 / 时间窗 / 唯一性断言),画像解释器若要表达它
就不再是「字段映射表」;只接 4~5 家时注册表总量也更小。

- ADR-0008 要防的「三处分散」由收敛到一个 `ExecutorAdapter` 接口 + 查表解决,
  不依赖画像;`output_profile` 列保留不动、仍不读。
- **画像不是被否决,是被推后。** 注册表是容器,画像是往容器里塞东西的一种方式;
  `declarativeAdapter(profile)` 将来可作为注册表的一员共存。
- 因此,上文「放弃的方案」里「给每家写一个 adapter 模块 + 注册表」一条已被本后续
  决策部分取代(注册表先落地;用户自助、零发版接入仍以画像为远期目标)。
