# 三层分工与交接：检视者管需求与架构，协调者管方案与验收，执行者只执行

用户 2026-09-30 定。原始记录在仓库外 `coagent-experiments/roles/role-redesign-2026-09-30.md`；本 ADR 只留长期有效的取舍。

## 取舍

每一层吃透一样东西，守住一条不碰的线：

| | 检视者（L3） | 协调者（L2） | 执行者（L1） |
|---|---|---|---|
| 吃透 | 需求和架构 | 代码和方案 | 手上这一张工单 |
| 不碰 | 不写代码、不在代码层面验收 | 不改需求（契约） | 工单以外的不看、不想、不改 |
| 交给下一层 | 票：why、范围（到目录级）、验收、约束、非目标、依赖 | 工单：目标、要读的文件和段落、能改的文件、验证命令 | 代码改动 + 证据 |
| 验收 | 看结论：每条验收标准是否达成 | 看代码：是否达标、是否守住架构 | 不验收，只如实报告 |
| 拿不准 | 问用户 | 升级给检视者 | 报 blocked 退回协调者 |

- 检视者是用户开着的会话（暂定），可以直接读源码；协调者、执行者跑在 pi 上，模型由用户按角色指定。
- 拆分两级：检视者按架构边界切票，协调者在 Mission 内拆工作项。新需求开跑前，票单给用户确认。
- 检视者不看 diff、不卡代码合并：协调者验收、集成验证绿就合；检视者只收结构化结论并及时处理。验收标准没有全部达成的，不自动合，交检视者决定。
- 必须问用户的只有四类：改变用户要的东西（或原话有歧义）、超预算、不可逆 / 对外操作、合 master。
- `.coagent/` 由检视者维护；协调者只能以差异提议，检视者批准才写；提交时机交平台（有 Mission 在跑就排队），否则会让在跑的 Mission 合不进去。
- 交接按角色精简：执行者只拿工单、执行者红线、环境提示；协调者拿契约（非目标只列相关的票）、规划、工作项索引、上一跳以来的新情况、project.md；细节按需取。放进上下文的每一段，这一跳后面每次模型调用都要再读一遍。

不采用：检视者逐个读 diff 放行（贵，而且检视者不在时整夜停）；协调者接整份需求自己切票（切票本身是架构决策）；执行者自己探索代码补分析（贵，而且越过了工单）。

## 补充（2026-09-30 深夜 – 10-01，第 33 波的教训）

- **每一层都核对上一层交下来的东西。** 执行者对工单已经如此（报 blocked）；协调者对检视者的票也要如此：开工先核对范围、输入、假设、矛盾，有问题先升级、不派工（CV1 平台强制）。检视者下发的不一定对，协调者提出票有问题时，检视者修票而不是坚持。
- **Mission 是基本单位，方案只是队列。** 升级、预算、连续失败、重跑、挂起都按 Mission 算；不做方案级的升级单、上限与记录（PL1 去掉方案层）。
- **执行者只用便宜的模型。** 不靠换强模型提速，由上两层把工单写到照着做就能完成（project.md「工单标准」）。
- **测试尽量少，只加在关键地方。**
- **省钱看协调者的跳数和每跳读的量。** 实测钱几乎都花在协调者反复醒来重读上下文上（PLAT4、PLAT2 协调者占 93–96%，写出的内容不到 1%）；先做 HO1–HO3、VR1a / VR1b、CV1 把它降下来，再做「分工 vs 协调者自己改」的对照。

## 实现

分六波做，见原始记录的统一计划；实现之前的过渡期，由值守的检视者人工执行：开跑前票单给用户确认；单票花费到 $10、或开到 15 个工作项时停下；每个 Mission 合进去后读结论，没达成的验收开补票。

## 为什么

1. **贵的模型只做贵的判断。** 实测每跳协调者约 83 万、执行者约 68 万 token，绝大部分是上下文被反复重读；把分析集中在协调者、执行者只读必要的东西，是最直接的省法。
2. **每层的输出要让下一层不用猜。** 票不用猜用户意图，工单不用再读别的代码，结论不用读代码就能判断。做不到就是上一层的活没做完，要退回上一层，而不是下一层自己补。
3. **用户只在真正需要人的地方出现。** 其余交给检视者，检视者不在时按规则挂起或过期，不让一个问题停住整个方案。

## 什么时候该推翻它

- 检视者改由平台托管（例如 pi 检视者）并能被平台唤醒时，值守与通信那部分要重写；
- 执行者模型能力足以自己探索而且更省时，可以放宽执行者的读取限制；
- 实测按角色精简后反而返工变多（执行者频繁报工单不够），先补协调者写工单的能力，再考虑放宽。

2026-10-04 PL1 后端落地：项目 execution-config 与已确认 Mission 清单投影由 Activity 持久承载，服务按顺序和依赖推进；不新增队列运行实体、总预算或升级单。启动配置固定到 Mission，终审使用项目集成验证；生产 run-plan 退役。历史 PlanRun 仅读取与恢复兼容，真实数据不迁移或伪造完成。UI1 分类角色复用候选池，QueryRun 保持独立只读用例；前端继续暂缓。

## 补充（2026-10-07，COM9 恢复路径与授权边界）

用户 2026-10-07：「已作废的项为什么还要完成。其他的做。c先不做」。依据 COM9 调查（`docs/com9-recovery-paths-design-20261007.md`，五类「状态机走不通」逐类核实了源码与历史记录）：

- **作废（retired）只表示这件事不用做了或已被取代**，作废的项本身从不需要完成，也不得用作废来重启一个卡住的工作项。历史上 COM3-B2b 的 W-472、W-474 被作废再另建替代单，是因为被杀的执行者让工作项残留 dispatched、平台既不能修订它也没有收尾入口，作废成了唯一出路——那是缺平台能力，不是规则。
- **已验收的项要补做**：协调者直接新建引用原工作项 id 的补修单（原单的验收记录不动、不修订、不作废），目标、验收、范围不变就**不升级给检视者**。
- **平台放弃重跑（执行者被墙钟掐掉，或同一工作项无结构化结果到上限）且能证明没有活执行者时，由平台把停在 dispatched 的工作项转 blocked**（kernel 已有 dispatched→blocked 边，不新增状态边），协调者修订同一张单再重派，不作废重建（COM12）。
- **被杀执行者留下的未提交半成品**仍由检视者逐案批准保存恢复快照；平台侧恢复快照（COM9 草案 C）暂不做，再出现时重新评估。
- **仍然升级给检视者**：目标、验收、范围变化；来源不明；预算或不可逆；平台证明不了执行者已停。
- **不变**：未经检视者不得 completed，master 一律用户放行，冻结工单的修订门禁（只有 created / rejected / blocked 可修订）不放宽，不新增 kernel 状态边。

跨跳交接（COM10，`docs/com10-handoff-notes-design-20261007.md`）评估后暂缓 `plan.codeMap` 与 `reviewPackage`：协调者换成 Sol 6.1 并加了 COM1「简报优先」之后，今晚 26 个协调者跳平均每跳读代码调用 5.9 次、$0.10（规划派发 12.6 次、评审 1.2 次、交卷 1.4 次），而 10-04 到 10-07 的基线是规划派发 41 次、评审 40.5 次（$0.69、$0.77，含大量 Grok 4.7 跳）。重复读代码的问题已基本消掉，评审跳无可省，剩下的收益抵不过改内核类型、规划结构、pi 工具参数与每跳固定前缀多出最多约 4K 估 token 的代价；协调者若换回大模型或每跳读代码次数再升高，再回头看。
