# Spec: 链条失败后遗留的 queued 任务长时间静默滞留(实测 5 小时)

> **状态**: Frozen — 2026-09-04(v1.1:标题与 §1 更正 —— 原写「永不被拾起」,实为延迟)
> **相关**: [detached-close-deadlock-guard-vs-no-poll.md](detached-close-deadlock-guard-vs-no-poll.md)(同一次事故的另一处)

## 1. 现象(2026-09-03 实证)

> ⚠️ v1.0 的标题与结论是「**永不**被拾起」。**那是错的** —— 我只观察了 14 分钟。
> 该任务于 **20:57:20** 被拾起并正常跑完(15:55:29 入队,历时约 **5 小时**)。
> 缺陷仍然成立,但性质是「长时间静默滞留」,不是「永不执行」。

协调链条失败后,子任务 `01a067fb-7c10` 停在 `queued`。检视者在 15:57~16:09
观察的 14 分钟内无人拾起,当时:

- 群内无任何执行器进程(`ps` 查不到 codex / atomcode / codebuddy / pi)
- 其执行方 codex `available=true`,不在冷却
- `maxConcurrentPerWorkspace: 1`,但当时没有任何 running 任务占用工作树
- 群内其余任务全部终态

也就是说:**当时没有任何理由不跑它。** 它最终在约 5 小时后才被拾起 ——
中间这段既没有进展,也没有任何说明。

## 2. 危害

`queued` 在界面上与「排队中,马上会跑」无法区分。一个永不被拾起的任务
看起来完全正常,只有人去数进程才会发现不对。本次是检视者手工
`ps` + 12 分钟观察才确认。

链条一断就留一个静默孤儿,而**队列门槛按群算** —— 这个孤儿还会继续占位。

## 3. 要做的

**R1 queued 任务必须有**及时**拾起保证。** 队列泵在有空闲槽位、执行方可用时,
必须能在有界时间内拾起**任何** `queued` 任务,不依赖它是否由当前进程入过内存队列。
⚠️ v1.1:判据是**时延有界**,不是「最终会跑」——最终会跑这件事已经实测成立。
今天 `queue.ts:1025` 的注释写着「queued 是本 server 自己入过队的,同样跳过」——
这个假设在协调链条中途失败、或进程重启之后不成立。

**R2 无法拾起必须可见。** 若某 `queued` 任务因任何原因不被拾起(槽位、冷却、
执行方缺失),须在其 `diffSummary` 记录原因与时刻,并在任务 API 透出,
使界面能与「正常排队」区分。**静默排队是本票要消灭的状态。**

**R3 兜底回收。** `queued` 超过阈值(建议取 `stallAlertMinutes`)仍未 spawn →
按 stall 处置(告警,并交回协调者),不得无限期躺着。

## 4. 硬验收

真实端到端:

1. 构造一个协调链条中途失败、遗留 queued 子任务的场景 →
   断言该任务**在阈值内**(建议 `stallAlertMinutes`)被拾起并执行。
   ⚠️ 断言必须带时限;「最终跑了」不算通过(本次实测 5 小时后确实跑了)。
2. 人为让其执行方不可用 → 断言 `diffSummary` 出现不可拾起的原因,
   且任务 API 能透出该原因。
3. 超过阈值 → 断言按 stall 告警,不静默。

⚠️ 不接受用「新建一个 queued 任务」来验收 R1 —— 那条路径今天本来就是通的。
必须复现**链条失败后遗留**的那种 queued,否则验收会绕开真正的分支。

## 5. 不涉及

- 不改 `maxConcurrentPerWorkspace` 与工作树互斥语义。
- 不改冷却、限流处置。
