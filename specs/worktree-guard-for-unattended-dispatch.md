# Spec: 无人值守派发期间守住「在途工作仍在途」的看门狗

> **状态**: Landed(2026-09-09,检视者亲自实施并逐条实测)
> **版本**: 1.1
>
> **v1.1(2026-09-09,落地当天实战暴露)**:加 `--protect <路径>`。
>
> **为什么**:v1.0 只有「快照启动那一刻在途的一切」这一种模式,
> 它把**操作者自己有意提交自己的工作**也判成告警 ——
> 检视者当天提交 3 个测试文件就触发了一次误报。
>
> ⚠️ **这不是小瑕疵**:一个对正常操作狂叫的看门狗会被养成无视的习惯,
> 而那正是真告警被漏掉的方式。**它比没有看门狗更危险。**
>
> **规则**:有 `--protect` 就只守它们;没有才回落到快照全部。
> 知道该守谁的时候就点名 —— 回落模式只用于完全无人值守。
>
> 实测:点名 `mine.sh` 后,守护期内提交**未守护**的 `other.txt` **不告警**,
> 提交 `mine.sh` **告警且退出码 1** —— 误报消除,检出能力未削弱。
>
> **实施记录 —— §4 五条验收全部真跑(临时仓库,未碰用户在途工作)**:
>
> | 条 | 结果 |
> |---|---|
> | 1 通用夹带检测 | ✅ 守护期内 `git add` + commit 掉一个 `??` 文件 → 告警并给出还原命令;脚本内 `grep` 不到任何具体业务文件名 |
> | 2 新增不告警 | ✅ 期内新建文件 + 再改已跟踪文件 → **不告警**,退出码 0 |
> | 3 HEAD 判据 | ✅ 造 `coagenthub checkpoint …` 的 HEAD → 告警,还原命令指向 `HEAD^` |
> | 4 不自动修复 | ✅ 告警前后 `git status --porcelain` **完全相同** |
> | 5 退出码 | ✅ 无告警 `0`;有告警 `1` |
>
> **实现要点**:基线路径集合在 `while read` 子 shell 里比对,
> 子 shell 无法回写变量 —— 用标记文件把告警状态传回主 shell。
> **日期**: 2026-09-09
> **来源**: 2026-09-08 检视者在连续派发 21 张票期间自建的临时脚本
> (`.scratch/dispatch-2026-09-07/worktree-guard.sh`)。
> `.scratch/` 是 gitignored —— **换台机器或清一次就没了**。本票把它固化。

## 1. 背景与目标

### 1.1 它是为什么造出来的

2026-09-08 当晚,用户**未提交**的 567 行报告与**未跟踪**的 `start.ps1`
被平台**连续吞掉三次**:

```
582c4e28  coagenthub checkpoint 01a0804b-5f7b-…
40b1a576  coagenthub checkpoint 01a0804b-5f7b-…
30653661  coagenthub checkpoint 01a0804b-5f7b-…
```

成因是两个缺陷连环(均已 Landed):

- [dispatch-must-not-spawn-the-reviewer.md](dispatch-must-not-spawn-the-reviewer.md)
  `68ad401b` —— 派发门把定向到检视者的消息当成派发;
- [rollback-puts-checkpoint-commit-on-head.md](rollback-puts-checkpoint-commit-on-head.md)
  `99113e88` —— 重试回滚把 checkpoint 提交推上 HEAD。

**两个缺陷都修好了。那为什么还要这个看门狗?**

因为**它守的不是这两个缺陷,是这一类风险**:

1. 无人值守连续派发时,执行器可能 `git add -A` / `git commit -a` 夹带
   用户未提交的工作 —— 这与上述两个缺陷无关,靠票面纪律约束,
   而**纪律没有强制力**;
2. 任何将来引入的、会改写工作树或历史的机制,都可能重演同一后果;
3. 检视者当晚敢把 21 张票连着派出去,靠的就是它 ——
   **它是「可以放手」的前提,不是事后补救**。

### 1.2 现状脚本的问题

`.scratch/` 版本把当晚的具体文件名**写死了**:

```sh
REPORT="docs/implementation-optimization-review-2026-09-07.md"
… case "$st" in *"?? start.ps1"*) …
```

它守的是「那两个文件」,不是「在途工作」这个概念。
**换个需求就失效,而且失效是静默的** —— 它照样报「本轮无异常」。

### 1.3 目标

**把不变量从「这两个文件」提升为:
启动那一刻处于「未提交 / 未跟踪」状态的每一条路径,
在整个守护期内必须保持该状态。**

## 3. 详细改动

### R1. 不变量:开机快照 → 逐轮比对

启动时用 `git status --porcelain` 取一次基线,记下每条
` M`(已跟踪已修改)与 `??`(未跟踪)的路径。

此后每轮重取,**任何一条基线路径从这两个状态里消失即告警**。

⚠️ **只看「消失」,不看「新增」**:守护期内执行器**本来就会**产生新的改动
与新文件,那是正常工作。**新增不是异常,消失才是。**

### R2. HEAD 判据保留

HEAD 的提交信息以 `coagenthub checkpoint ` 开头 → 告警。

该模式**永远不该出现在 HEAD 上**(它是 `commit-tree` 的机器产物),
所以命中即损坏,无歧义。

### R3. ⚠️ 只告警,不自动修复

`.scratch/` 版本早期做过自动 `git reset --mixed`,**后来去掉了,本票沿用「去掉」**。

理由:守护期内执行器的提交**可能是有效工作**,盲目 reset 会毁掉它。
看门狗的职责是**让人在几十秒内知道**,不是替人决定。

告警里要给出**可直接执行的还原命令**,但**不执行**。

### R4. 退出码要能被脚本消费

- 无告警 → `0`;
- 有告警 → **非 0**(具体值自定,写进注释)。

⚠️ 现状脚本无论如何都返回 0,调用方无法自动判断 ——
2026-09-08 检视者每轮都得人工读输出。

### R5. 参数与默认值

轮数与间隔可传参,并给出合理默认。
**默认值要让一轮的总时长适合挂在一次派发旁边**(当晚用的是 20s × 90 轮 = 30 分钟)。

## 4. 验收标准

1. **通用性(核心)**:在一个**与当晚无关**的工作树状态下
   (随便造一个已修改文件 + 一个未跟踪文件)启动看门狗,
   然后**模拟夹带**(把那个未跟踪文件 `git add` 并提交)
   → **必须告警**。
   ⚠️ 脚本里**不得**出现任何具体业务文件名。
2. **新增不告警**(R1):守护期内新建一个文件 / 修改另一个文件
   → **不告警**(那是正常工作)。
3. **HEAD 判据**(R2):构造一个提交信息以 `coagenthub checkpoint ` 开头的
   HEAD → 告警。用完即还原。
4. **不自动修复**(R3):上述任一告警场景中,
   仓库状态**未被脚本改变** —— 断言告警前后 `git status --porcelain` 相同。
5. **退出码**(R4):无告警 `echo $?` 为 `0`;有告警为非 `0`。**贴出实际值。**
6. **零平台代码改动**:`git show --stat` 不得出现 `packages/**`。**硬约束。**

⚠️ **验收 1–4 必须真跑**,不接受「逻辑上应该」。
构造场景请用**临时仓库**或**临时文件**,
**不要拿用户真实的在途工作做实验**。

## 5. 不涉及的改动

- 不做自动修复(R3);
- 不接入 CI、不做常驻服务 —— 它是**手动挂在派发旁边**的工具;
- 不改平台代码、不改派发流程与 skill;
- 不试图替代 `dispatch-must-not-spawn-the-reviewer` /
  `rollback-puts-checkpoint-commit-on-head` 两个已 Landed 的修复 ——
  **它是兜底,不是修复**。

## 6. 兼容性

- 纯新增脚本,无行为变更;
- POSIX sh,Windows 上经 Git Bash 运行(当晚的实际环境)。
