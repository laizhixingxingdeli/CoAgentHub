# Spec: 一票一提交,从建议变成硬约束

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-23
> **范围**: 仅 `skills/coordinator/SKILL.md`,不改代码

## 背景:一次真实的事故

提交 `6cfc84e`「Implement task lineage and coordination contracts」**同时包含三票**:

- `task-parent-link`(`13fe14e`)—— 含 SQL 迁移 `0020`
- `verify-agent-claims`(`3d7245d`)—— `claim-verification.ts`
- `coordination-payload-contract`(`f33b909`)—— `coordination-payload.ts`

我在派发时明确写过:

> ⚠️ task-parent-link 与 coordination-payload-contract 都会碰任务的 PATCH/创建路径,
> **建议不要并行下发给同一执行器同时跑。**

结果不但并行了,还合成了一个提交。**直接后果**:三票的改动捆在一起,其中的迁移没被
应用,后端重启后 `/api/groups/:id/tasks` 全线 500,三个群的任务列表全废。

**分开落地的话,坏的只会是一票。**

## 现有规则为什么没拦住

`skills/coordinator/SKILL.md` §2.1 Dispatch 纪律写的是:

> 单张任务书只对应 spec 里的**一个内聚关注点**

这条管的是**下发粒度**,没说**落地粒度**。协调者可以合规地下发三张票,
然后执行器把三票的产物合成一个提交——**字面上没违反任何规则**。

---

## 要求

### R1. §2.1 增补:一票一提交

在 Dispatch 纪律里增加一条,大意:

> **一张任务书 = 一个提交。** 不同任务书的改动不得合并进同一个提交,
> 即使它们由同一个执行器连续完成、即使改动相关。

理由要写进去(不要只写规则):

- **回滚粒度**:合并提交后,想撤销其中一票必须连带撤销另外两票
- **L2 对照**:验收是逐票对照 specHash 的验收标准,合并提交让「这一票做到了什么」
  无法单独判断
- **事故隔离**:实证——`6cfc84e` 把迁移与两个无关改动捆在一起,一处遗漏导致整个
  任务接口崩溃

### R2. L2 检视清单增加对应检查项

§4.1 的 L2 检视步骤里增加:确认**本票的改动独立成一个提交**,
未与其他任务书的产物混合。

- 发现混合时的处置写清楚:是要求执行器拆分重提交,还是记录后放行、
  由检视者裁决——**选一个并写明**,不要留模糊

### R3. 明确一个例外

同一票内的多个提交是**允许**的(实现 + 修复自检发现的问题,分两次提交很正常)。
禁止的是**反向**:多票合成一个提交。

这条要写清楚,否则容易被理解成「一票必须恰好一个提交」。
