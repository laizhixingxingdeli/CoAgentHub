# Spec: 「派完就退」落地了,行为没稳定 —— 同一条任务空转 26 分钟

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-26

## 现象

`coordinator-exits-after-dispatch`(冻结 `0a38e59e`,已 Landed `3645c741`)
要求协调者派发成功后结束本轮,不得轮询等待。落地当时实测两次均符合。

**但在其之后的任务 `01a03d87` 上失效了**:

```
01a03d88  执行子任务  done    24 分钟前已完成
01a03d87  协调任务    pid 54731 仍存活 —— 派完未退出,累计空转 26 分钟
```

另一检视者会话在同一条任务的输出里查得更细:
`sleep` 出现 **19 次、累计 590 秒 ≈ 9.8 分钟**,`coagenthub_get_task` 轮询 **20 次**。

## 检视者的判断失误

我(检视者)给 `coordinator-exits-after-dispatch` 判通过时,依据是**两次**实测
(`01a03bfa` pid 4328、`01a03c3d` pid 17278,均派完即退)。

⚠️ **两次不等于总是。** 那条裁决把「观察到两次」当成了「行为已稳定」,
下早了。规范文本落地是事实,行为稳定不是 —— 两者当时被我混为一谈。

## 根因待查(不要凭猜实现)

⚠️ **动手前必须先查清它为什么还在等**,不要直接加限制。已知的两种可能:

1. **技能没被读到** —— `SKILL.md` 的 `2.3 派发成功后退出本轮` 是否进入了
   该次运行的上下文?协调者每轮重新加载技能,可能因上下文裁剪未读到该节。
2. **等的不是子任务** —— 它可能在等别的东西(例如轮询自身任务状态、
   等待某个回写确认),而 `2.3` 只规定了「不要等子任务终态」,没覆盖这种。

请从该次运行的实际输出取证(`sleep` 前后各在做什么、`coagenthub_get_task`
查的是哪条任务的什么字段),判定属于哪一种再动手。

## 决策

### R1. 先定位,再修

任务汇报中**必须写明**空转的实际原因(上述两种之一,或第三种),
并附取证片段。⚠️ **没有定位就改代码的实现,一律打回。**

### R2. 按定位结果修,不扩大范围

- 若是**没读到技能** → 修上下文注入,使该节稳定进入每轮上下文;
  ⚠️ 不要改 `2.3` 的文本(它已被验证有效:上一票协调者仅凭任务书就照做了)
- 若是**等别的东西** → 补充 `2.3`,写明「等待自身任务状态回写」等场景同样不应轮询,
  并说明正确做法

### R3. 不加平台侧强制

⚠️ **不得**在平台侧强杀空转进程或强制退出 ——
`coordinator-exits-after-dispatch` R5 已论证:无法可靠区分「在阻塞」与「在做 L2」,
误杀正在检视的协调者比空转更糟。该结论**仍然成立**,本票不推翻它。

### R4. 验收必须多次

⚠️ **本票的验收不接受单次或两次观测。**
需连续 **3 张**真实需求票均满足:派发成功后协调者 pid 在 60 秒内消失,
且平台创建续跑任务接手 L2。

这条是针对我上次判断失误的直接补正 —— 上次正是两次就下了结论。

## 验收标准

- [ ] 汇报中写明空转的**实际原因**并附取证片段(R1,必须)
- [ ] 连续 **3 张**真实需求票:派发成功后协调者 pid 60 秒内消失(R4,必须)
- [ ] 同上 3 张:平台均创建续跑任务且 `resumeOf` 指向父任务
- [ ] 该 3 张中**无一**出现 `sleep` 轮询等待子任务终态(查输出确认)
- [ ] 平台侧**未新增**强杀或强制退出逻辑(R3,读代码确认)
- [ ] `2.3` 若被修改,改动限于 R2 所定范围,原有措辞不被推翻
- [ ] 后端/技能相关测试全绿,贴出用例数

## 不涉及

- 平台侧强制退出(R3)
- 实时输出的内容与体积(另票 `live-output-shows-narration-not-actions`)
- 协调者是否应自己实现(另票 `dispatching-should-be-the-default`)
