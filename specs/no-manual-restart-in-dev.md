# Spec: 手动重启后端这件事本身就不该存在

> **状态**: Landed — L3 通过(2026-08-25),实现 `a5bd7a64`
> **版本**: 1.0
> **日期**: 2026-08-25
> **相关**: `executor-task-liveness`(`b6ee605b`)让这个循环**可见**;本票**消除**它

## 背景:四次同款失败,根子是我给自己造的负担

本轮有 **4 张协调任务**因同一模式落 `failed`:

```
01a034e8  dispatch-to-role          {"error":"server-restart"}
01a033a7  stale-runtime-detection   {"error":"server-restart"}
01a03384  stale-runtime-detection   {"error":"server-restart"}
01a03307  serial-dispatch-guard     {"error":"server-restart"}
```

模式一致:**执行器停掉后端做验证 → 进程死在那个窗口里 → 无人 PATCH → 任务凭空
挂 `running`,直到有人重启后端由启动恢复判 `failed`。** 四次实现本身都是好的,
只有终态记录不对。

`executor-task-liveness` 已把这个循环**点名**为「监工被自己看管的对象杀掉」,
但它只做了可观测,没有消除。

### 查证推翻了我此前的两个判断

**① 「必须重启后端」不在任务书模板里。** grep `queue.ts` 无命中 ——
**是检视者每次手写进任务书正文的**。不是平台强迫执行器重启,是我在要求它
重启一个正在看管它的进程。

**② `tsx watch` 模式一直存在。**

```json
"dev":   "tsx watch src/index.ts",     ← 改源码自动重载,无需任何人重启
"start": "node dist/server.mjs"        ← 生产模式,改完必须手动重启
```

而检视者全程用的是 `node dist/server.mjs`。**手动重启这个负担完全是自己造的**,
然后写进任务书转嫁给了执行器。

## 决策:开发期用 watch 模式,任务书不再要求任何人重启后端

### R1. 提供一个明确的开发期启动方式

`package.json` 增加或明确一个开发期启动脚本,使后端以**自动重载**方式运行
(基于既有的 `tsx watch src/index.ts`)。

- **不要**改 `start`(生产语义保持 `node dist/server.mjs`)
- 若 `dev` 已可直接用,则本条只需在文档中写明何时该用哪个,并确认它能正常起服务

### R2. 任务书正文不再要求执行器重启后端

这是**检视者的行为**,但需要落成可执行的约束,否则换个检视者一样会写。

在**协调者任务书模板**(`buildReportSection` / `buildExecutionModeSection` 所在处)
的协调者分支中,加入一行明确说明:

> 后端以自动重载方式运行时,**改完源码无需重启**;若确需重启,由**发起方**
> 在验收阶段自行处理,**不要在执行窗口内停掉后端**。

⚠️ **不是**要求执行器「必须重启」,恰恰相反 —— 是明确告诉它**不要停后端**。

### R3. 文档写明两种模式的适用场景

`docs/architecture.md` 或 `CONTEXT.md` 写清:

| 模式 | 命令 | 何时用 | 改完源码 |
|---|---|---|---|
| 开发期 | `tsx watch src/index.ts` | 日常协作、执行票 | **自动重载** |
| 生产/验收 | `node dist/server.mjs` | 需要验证打包产物时 | 手动重启 |

并写明:**用生产模式跑开发流程,是本轮 4 次任务失败的根因。**

### R4. 不做自动重启机制

**不要**做「平台检测到源码变化就自己重启自己」之类的机制。理由:

- `tsx watch` 已经提供了这个能力,再造一个是重复;
- 让服务自己重启自己会与 `stale-runtime-detection` 的语义冲突
  (那张票的立论正是「运行的和构建的可能不是一回事」,自动重启会掩盖它)。

### R5. 不改这些

- **不改** `start` 脚本的生产语义(R1)
- **不改** `stale-runtime-detection` 的检测逻辑 —— 它在生产模式下仍然必要
- **不改** `executor-task-liveness` —— 那是兜底,即使本票落地也应保留

## 验收标准

- [ ] 开发期启动方式可用:以 watch 模式起服务,修改 `src/**` 下任一文件后
      **服务自动重载**,`GET /api/health` 的 `startedAt` 随之更新(实测)
- [ ] `start` 脚本**未被改动**(回归)
- [ ] 协调者任务书模板含 R2 的说明,且措辞是「**不要在执行窗口内停后端**」,
      不是「必须重启」
- [ ] 执行器任务书**不含**该说明(它不负责重启,加了是噪音)
- [ ] `docs/architecture.md` 或 `CONTEXT.md` 含两种模式的对照表与适用场景
- [ ] 文档写明「用生产模式跑开发流程」是本轮 4 次失败的根因
- [ ] **未新增**任何自动重启机制(R4)
- [ ] **未改动** `stale-runtime-detection` 与 `executor-task-liveness` 的逻辑
- [ ] 后端测试全绿,贴出用例数

## 不涉及

- 自动重启(R4 明确否决)
- 生产部署方式
- 已失败那 4 张任务的补救(历史数据,不回填)
