# Spec: 并发下发撞车没有任何防护 —— 共享工作树,却允许同时开工

> **状态**: Landed — L3 通过(2026-08-24),实现 `b94bd8ee + 9083284b`
> **版本**: 1.0
> **日期**: 2026-08-24
> **严重度**: 高 —— 本轮真实发生过一次,后果是 kill 全部进程 + 丢弃工作树

## 背景:一次真实事故

检视者一次性下发 13 张票。它们**没有排队**,而是立刻 spawn 出 13 个独立的 OS
进程,全部指向**同一个 git 工作树**(`/Users/apple/Projects/CoAgentHub`)。

其中 4 张票要改同一个文件(`RequirementTimeline.tsx`)。几分钟内工作树里混进了
多张票的半成品,互相交叉、无法按票拆分归属。最终只能:kill 掉 11 个进程 →
`git checkout -- . && git clean -fd` 丢弃全部未提交改动 → 把 12 条卡在 `running`
的任务行手工标 `failed` → 逐张重来。

**平台全程没有任何提示或阻拦。**

### 现有配置挡不住

`dispatch-policy.json` 里有两个看似相关的旋钮:

| 配置 | 实际语义 |
|---|---|
| `maxParallelGroups: 2` | 按**群**限并发 —— 同一个群里的多张票不受限 |
| `maxConcurrency`(执行器级) | 按**执行器**限 —— 换个执行器就绕过 |

事故里 13 张票**同群、同项目、不同执行器**,两条限制一条都没命中。

真正的约束是**物理的**:一个 git 工作树同时只能有一方在写。而平台的并发模型
是按「群」和「执行器」切的,**没有按「工作树」切的那一维**。

## 决策:按项目工作树串行,超出则排队而非拒绝

### R1. 新增按工作树的并发闸

同一 `projectPath`(群绑定的项目路径)下,同时处于 `running` 的任务数上限
**默认为 1**。超出的任务**进入 `queued` 排队**,不拒绝、不失败。

- 配置项:`dispatch-policy.json` 新增 `maxConcurrentPerWorkspace`,**缺省 1**
- **复用现有排队机制**(`groupQueues` / 泵),不要另写一套调度
- 前一个任务落终态 → 自动泵出下一个

**排队而非拒绝**的理由:下发方(检视者/协调者)不该被迫承担调度职责。本轮我是
靠自己记住「必须串行」才没再撞车 —— 那是记忆,不是机制,换个 agent 就失效。

### R2. 判定依据是工作树路径,不是群

同一 `projectPath` 的**不同群**也要计入同一个闸。

理由:三个项目群(CoAgentHub / Codex 插件 / DSH 插件)中,若两个群绑到同一个
仓库路径,它们的任务依然共用一棵工作树。按群限并发挡不住这种情况 ——
`maxParallelGroups` 已经证明了这一点。

`projectPath` 为空的群(未绑定项目)→ **各自独立,不参与本闸**
(它们不在共享工作树上作业)。

### R3. 排队要可见

任务因本闸排队时,`queued` 状态需能看出原因。**复用现有的排队提示机制**
(本轮日志里见过「前面还有 N 个」这类提示),不要新造一套字段。

不可见的排队与挂死无法区分 —— 这是本轮反复吃过亏的地方。

### R4. 不改这些

- **不改** `maxParallelGroups` 与执行器级 `maxConcurrency` 的语义
  (三个闸各管一维,叠加生效)
- **不做** git worktree 隔离 —— 那是更大的架构改动,本票只做闸
- **不改**重试/冷却/超时逻辑

### R5. 明确不做的替代方案

**不要**改成「下发时检测到冲突就报错让调用方重试」。理由与 R1 同:把调度责任
推给下发方,等于要求每个 agent 都记得串行 —— 而本轮已经证明,靠记忆约束
下发行为是不可靠的。

## 验收标准

- [ ] 同一 `projectPath` 下已有 1 个 `running` 任务时,新任务落 **`queued`** 而非
      `running`,且**不失败**
- [ ] 前一个任务落终态后,排队任务**自动开始**,无需人工干预
- [ ] `maxConcurrentPerWorkspace` 可配置,缺省 **1**;设为 2 时允许两个并行
- [ ] **不同群但同 `projectPath`** → 计入同一个闸(R2 核心)
- [ ] `projectPath` 为空的群 → **不参与**本闸,行为与改动前一致
- [ ] 排队原因可见(复用现有提示机制)
- [ ] `maxParallelGroups` 与执行器 `maxConcurrency` 行为**未改变**(回归,必测)
- [ ] 未新增独立的调度器,复用现有排队与泵机制
- [ ] 后端测试全绿,贴出用例数;上述每条验收都要有对应用例

## 不涉及

- git worktree 级别的真隔离(R4)
- 下发时拒绝的方案(R5 明确否决)
- 前端展示排队原因
