# Spec: 协调者派出子任务之前,界面把它显示成执行者

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-26

## 现象:界面说「还没有协调任务」,而协调任务正在跑

下发一张需求票后,协调者已接单并运行,界面却显示:

```
L2 协调    未开始    「该需求还没有协调任务」
L1 执行    进行中    1 次执行  →  Codex(协调者)
```

数据层完全正常 —— 检视者发给 `role/coordinator`,Codex 接单,`parentTaskId` 为
null,进程在跑。**错的只是显示**,而这个错误显示会让人得出「协调者被跳过了」
的结论,并据此去排查一个并不存在的故障。

## 根因:靠「有没有人认它当父」反推身份

`group-tasks-by-spec.ts:109`:

```ts
const coordinationIds = new Set(tasks.map((t) => t.parentTaskId));
l1Tasks = tasks.filter((t) => !coordinationIds.has(t.id) && !isReviewRequestTask(t));
```

协调任务的身份是**反推**出来的:只有当已经存在指向它的子任务时,它才被认作
协调任务。**在派出第一个子任务之前,没有任何人指向它**,于是落进 L1。

这不是边界情况 —— 它必然发生在每一张票的开头,而且恰好覆盖协调者思考、
读规范、决定怎么拆的那几分钟,也就是最需要看清「协调者在干活」的时候。

同一文件 `:226` 的标题提取用的是同一套反推判据(同样的 `coordinationIds`),
有同样的问题。

## 决策

### R1. 按执行者角色判定,不再反推

任务的执行者在本群的角色含 `coordinator` → 该任务是**协调任务**(L2),
与它有没有子任务无关。

⚠️ **复用现成判据,不要另写**:`RequirementTimeline.tsx:405-408` 已经在按
`executorParticipantId` 查 `members` 读 `roles`,那是 `timeline-layer-by-actor`
立下的规矩。本票把同一套判据用到分层上,**不要引入第二种角色查法**。

### R2. 保留反推作为回退,顺序明确

成员查不到时(历史数据、成员已退群),**回退到现有的 parentTaskId 反推**,
行为与现在逐字一致。顺序是:先查角色,查不到再反推。

⚠️ **不要**反过来,也**不要**两者取并集 —— 角色是权威,反推是兜底。

### R3. 标题提取同步修正

`:226` 的协调任务集合改用同一份判定结果,不要在两处各写一份。

### R4. 不动后端

后端已经返回 `executorParticipantId`,群成员角色前端也已有。
**不新增字段、不加接口、不改任何后端代码。**

### R5. 不改分组与父子归拢规则

有 `parentTaskId` 的任务仍沿父链归到父之下(现有注释 `:10-15` 描述的规则不变);
悬空父仍按无父处理,**不猜测父子关系**。本票只改「哪个任务算 L2」。

## 验收标准

- [ ] 协调者的任务**零子任务**时:归入 L2,L2 状态跟随该任务(进行中/完成/失败),
      **不再**出现在 L1(核心场景,必测)
- [ ] 此时 L1 显示「暂无执行记录」而非「1 次执行」
- [ ] 协调任务派出子任务后:分层结果与改动前**一致**(回归,必测)
- [ ] 执行者角色的任务(executor)始终归 L1,与有无父任务无关(回归,必测)
- [ ] 成员查不到时回退反推,结果与改动前**逐字一致**(回归,必测)
- [ ] 检视请求任务(`isReviewRequestTask`)仍被排除在 L1 之外(回归,必测)
- [ ] 标题提取:协调任务仍不参与提取,零子任务时也不参与(回归,必测)
- [ ] 前端测试全绿,贴出用例数

## 不涉及

- 后端字段与接口(R4)
- 父子归拢与悬空父规则(R5)
- 协调者该不该自己实现 —— 那是行为问题,本票只管**显示**
