# Spec: 需求列表与时间线的可读性

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-23
> **协作模式**: 三层
> **取代**: `specs/group-detail-readability.md`(该 spec 的问题一、问题二并入本票;
> 问题三已作废,改由 `specs/remove-context-panel-and-settings-page.md` 处理)

## 背景

平台的核心价值是**让用户看懂 agent 之间在干什么**。当前群详情页做不到:
左栏看不出任务是什么,中间信息过载。以下均为实测截图确认
(群 `01a02a4b-42a2-741f-95d9-2e17386a9655`)。

## 问题一:左栏任务名是 spec 文件名,用户看不懂

左栏只显示 `mcp-contract-defects`——那是 **specRef 的文件名**
(`group-tasks-by-spec.ts` 的 `label` 取自 `specRef` 去扩展名)。

数据里有现成的人写标题:`task.brief` 的**第一行**就是任务名。

```
# 任务:修 MCP 契约两缺陷      ← 第一行
                              ← 空行
## 关联规范                    ← 后续是结构化正文
```

### 要求

- 左栏标题优先取 `brief` 首行(去掉 markdown 标题标记与空白)
- `brief` 为空、或首行不像标题时,回落现有的 specRef 文件名
- 过长截断,但**保证前半句可读**(不要在第 3 个字就截断)

---

## 问题二:阶梯标签是「步骤 N」,等于没说

`RequirementStepper.tsx:17-18` 的注释自己写明了原因:

> 本组件只消费占位数据,不做「检视/协调/执行」层级语义判定 ——
> 因此标签用通用文案「步骤 N」(props 只有 steps,拿不到执行者信息)。

### 要求

- 把执行者与任务名喂进去,标签从 `步骤 2` 变成 `atomcode · 改前端渲染`
- 执行者名优先用成员真实身份:`executorParticipantId` 命中即读成员名,
  关联不上才回落 `executorKey`(`RequirementTimeline.tsx:207-213` 已有这套
  回落逻辑,**复用它,不要写第二份**)
- 四种状态的图标 / 配色 / 呼吸动画**全部保持现状**,本票只改标签
- 标签过长时截断,阶梯不得被撑变形

---

## 问题三:中间详情信息过载,任务名被包在气泡里

### 现状(截图确认)

- 顶部 `mcp-contract-defects` 出现**两次**(列表标题 + 详情标题),
  中间还夹着 `executor`、`步骤 1` 这类内部标识
- **任务名被塞进消息气泡**:
  `🚀 [atomcode] 开始执行:# 任务:修 MCP 契约两缺陷 ## 关联规范 - specRef: spe`
  ——任务名、markdown 标记、specRef 糊成一条并被截断
- 执行器汇报是一整段未分段的文字墙

### 要求

- **任务名不得包在气泡里**:它是这条需求的标题,应作为标题呈现,
  与「谁在什么时候说了什么」的消息卡片分开
- 同一个名字不重复显示两遍;`executor`、`步骤 1` 这类内部标识**不要直接暴露**
- 执行器汇报是结构化的(`diffSummary` 有 `summary`/`tests`/`hash`/`todo`/`tokenUsage`),
  **按字段分区呈现**,不要整段倒出原始文本
- **长汇报默认截断、点击展开**;展开部分的文字**用与正文不同的颜色**
  ——让人一眼分得清「摘要」与「展开的细节」,而不是一片同色文字墙

### 判断原则

用户想知道:**谁、在做什么、结果如何**。
不想知道:内部 key、步骤编号、markdown 源码、specHash 全文。

## 问题四:`task_status` 不单独成条,挂在触发它的真实消息上

平台自动生成的 `contentType: "task_status"` 消息(「🚀 开始执行…」「✅ 任务完成…」)
把任务书原样复述一遍,而任务名已在标题、状态已在标题旁——纯重复。

> ⚠️ **本节要求已更正**(2026-08-23,检视者):
> 原文写「不为 `task_status` 单独渲染消息卡片」——**按 contentType 一刀切会把
> 执行器汇报一起藏掉**,那是时间线里最有价值的一条。
>
> 证据链:`report.ts:132` 的 `renderTaskCard` 以 `✅ 任务完成` 开头 →
> 命中 `notify.ts:20` 的 `STATUS_EMOJI_RE` → `notify.ts:101` 判定
> `contentType: "task_status"`。**汇报本身就是一条 task_status。**
>
> 真正的分界不是 contentType,而是**这条状态消息带不带内容**。

### 要求

- **区分两类 `task_status`,不要按 contentType 一刀切**:
  - **纯状态、无内容**(🚀 开始执行 / ↻ 重试提示 —— 它们把任务书原样复述一遍,
    而任务名已在标题、状态已在标题旁,纯重复)→ **不单独成条**
  - **携带汇报内容**(✅ 任务完成的 `renderTaskCard`、❌ 失败原因)→
    **必须保留**,按问题三的要求分区呈现
  - 判别方式自行设计(按 emoji 前缀、按是否有对应 `diffSummary`、
    或让后端补一个更细的标记都行),**在汇报里说明选了哪种及理由**
- 被隐藏的纯状态改为**标注在触发该任务的那条真实消息上**。锚点是现成的:
  `task.messageId` 指向触发消息(schema 里 `notNull().unique()`,一一对应),
  反查即可挂回去
- 呈现方式自行设计(角标、状态点、行内标签皆可),但**必须能看出
  「这条消息触发的任务,现在是什么状态」**

## 验收标准

- [ ] 左栏显示人可读的任务名(取自 `brief` 首行),无 `brief` 时回落 specRef
- [ ] 阶梯标签为「执行者 · 任务名」,不再是「步骤 N」
- [ ] 阶梯的图标 / 配色 / 动画未改动
- [ ] 执行者名优先用成员真实身份,复用既有回落逻辑
- [ ] 中间的任务名作为标题呈现,**不在消息气泡内**
- [ ] 同一名称不重复显示;`executor` / `步骤 N` 等内部标识不直接暴露
- [ ] 执行器汇报按 `diffSummary` 字段分区呈现,不是整段文字墙
- [ ] 长汇报默认截断、可点击展开,**展开部分文字颜色与正文不同**
- [ ] 纯状态类 `task_status`(🚀 / ↻)不单独成条,标注在 `task.messageId` 对应的真实消息上
- [ ] **携带汇报内容的 `task_status`(✅ / ❌)仍然可见**,未被一并隐藏
- [ ] 判别方式已在汇报中说明
- [ ] skill 安装引导不出现在需求时间线中
- [ ] `pnpm --filter @laizhixingxingdeli/web test` 全绿(先跑一次确认基线,不得减少)
- [ ] `pnpm --filter @laizhixingxingdeli/web build` 通过

## 不涉及

- **不改**后端、不加接口(`brief` / `diffSummary` / `messageId` 都是现成数据)
- **不做**删右栏与设置页(另一票 `remove-context-panel-and-settings-page`)

- 不引入新依赖
