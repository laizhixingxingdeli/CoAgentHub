# Spec: 兜底冷却猜测覆盖已解析的准确恢复时刻

> **状态**: Landed — L3 pass(2026-09-02,三轮)。实现 `f0182410` + `8bab7811` + `43f518b9`
> **版本**: 1.1
> **日期**: 2026-08-31

## 1. 现象(已在生产兑现)

2026-08-31 02:02,Codex(协调者)撞额度。同一次事故产生**两条**终态写入,
各自独立计算冷却,写入相隔 10 秒:

```
02:02:31  01a053d4(L2 续跑)  输出含 "try again at 3:48 AM"
                              → parseRateLimitRecoveryMs 解析成功 → 冷却至 03:48:00  ✅ 准确
02:02:41  01a053cb(父协调票)  自身输出无可解析恢复时刻
                              → 回退固定冷却 → 冷却至 07:02:41           ← 02:02:41 + 300min
```

`GET /api/executors` 在 03:49 的读数:

```
codex  available=False  cooldownEndMs=07:02:41  reason=额度冷却至 2026/8/31 07:02:41
```

供应方自己声明的恢复时刻(03:48)已经过去 1 分钟,平台仍判 Codex 不可用。
**净代价:执行器被多停 3 小时 14 分**,期间群内无可用协调者,队列完全停摆。

## 2. 根因:兜底猜测与解析结果同权,且后写者无条件获胜

```ts
// queue.ts
export function enterCooldown(ex, endMs, persisted?): number {
  const end = endMs;
  executorCooldowns.set(ex.key, end);   // ← 无条件覆盖
  ...
}
```

`enterCooldown` 只接受一个数字,**不知道这个数字是「供应方说的」还是「我们猜的」**。
于是:

| | 依据 | 置信度 | 结局 |
|---|---|---|---|
| 03:48:00 | 供应方原话 `try again at 3:48 AM` | 高 | 先写,被覆盖 |
| 07:02:41 | 解析失败 → 固定 300 分钟兜底 | 低(纯猜测) | 后写,生效 |

⚠️ 固定兜底本身是**对的**(`quota-exhaustion-triggers-infinite-retry` R2/R7:
解析不出来时宁可保守长冷却)。错的是**它被允许推翻一个已知更准的值** ——
保守是「无信息时的默认」,不是「压过有信息的结论」。

⚠️ 这是本轮反复出现的形状的又一实例:**权威源不唯一**。同一个事实
(这个执行器什么时候恢复)有两个写入者,而系统没有裁定谁更权威的依据 ——
它只按到达顺序。与 `quota-failure-on-clean-exit` R9、
`transient-ratelimit-escalated-to-long-cooldown` R7、
`findings-ticket-hardcoded-to-fix-bypasses-l3` 同源。

### 2.1 为什么会有两条终态写入

一次事故里,父协调任务与其续跑任务都由同一个 CLI 进程承载;进程撞额度退出后,
孤儿收敛器在**相邻两轮**(10 秒间隔)分别把它们判为额度失败,各自独立走一遍
「解析恢复时刻 → normalizeCooldownEnd → enterCooldown」。
⚠️ **本 spec 不改这个结构** —— 两条任务各自落终态是对的,要改的是冷却的合并规则。

## 3. 改动范围

- `packages/backend/server/src/lib/executor-task/queue.ts`(`enterCooldown` 签名与合并规则)
- 其三处调用点(队列进程退出 / 队列执行超时 / 孤儿收敛器)传入来源标记

## 4. 详细改动

### R1 — 冷却值必须带来源标记

`enterCooldown` 增加一个参数标明该值的来源,至少区分两档:

| 来源 | 含义 |
|---|---|
| `parsed` | 从执行器输出中**解析出**的供应方声明恢复时刻 |
| `fallback` | 解析失败,采用固定兜底时长 |

⚠️ 标记由**调用点**给出 —— 调用点知道 `parseRateLimitRecoveryMs` 返没返回值,
`enterCooldown` 不得自行推断(推断即是第二处判定)。

### R2 — 合并规则:`fallback` 不得覆盖仍在生效的 `parsed`

- 当前冷却来源为 `parsed` 且**尚未到期**时,新的 `fallback` 值**丢弃**,
  保留现有值;在日志与 `diffSummary` 留一条可读记录说明被丢弃的值与原因。
- 其余组合按**取较晚者**合并(`parsed` 覆盖 `fallback`;同源取 max)。
  ⚠️ 取 max 而非无条件覆盖 —— 冷却只应延长或到期自然解除,不应被缩短。

### R3 — 留痕必须能事后区分两档

冷却相关的 `diffSummary` 留痕中记录该次冷却的来源(`parsed` / `fallback`)
与被丢弃的竞争值(若有)。⚠️ 今晚这条缺陷之所以要人肉比对两条任务的
`executorCooldownEndMs` 才看得出来,正是因为留痕里没有来源。

### R5 — 恢复时刻解析必须与分级判据同口径(v1.1 新增)

R1–R3 处理的是「两个冷却值谁赢」。本条处理更前一步:**为什么会产出一个纯猜测的值**。

#### 实证(2026-08-31 10:06,任务 `01a05591-1f50`)

CodeBuddy 的命中行**白纸黑字带着恢复时刻**:

```
429 您的使用量已超出频率限制,将在 2026-08-31 18:03:10 UTC+8 重置,您也可以切换其他模型继续使用。
```

平台写入的冷却:**15:06:13** —— 即 `10:06:13 + 300 分钟`固定兜底。
真实恢复是 **18:03**。于是 15:06 该执行器会被放出重新派活,
**其后近 3 小时内每一次派发都必然失败**。

⚠️ 与 §1 的方向**相反**:§1 是兜底**过长**(多停 3h14m),本条是兜底**过短**
(空转 3 小时)。两个方向都源自同一件事 —— 那个数字是猜的。

#### 根因:两个函数读同一行,给出不同答案

`transient-ratelimit-escalated-to-long-cooldown` **R7** 已让分级判据学会中文:
`recoveryDistanceMs` 内的 `CN_ABSOLUTE_DATETIME_RE` 能解析
`将在 2026-08-31 18:03:10 重置`,并据此正确判为 `exhausted`。

但**算冷却时长**走的是另一个函数 `parseRateLimitRecoveryMs`(`executors.ts`),
它只认三种英文形态(`resets around HH:MM` / `try again at HH:MM` /
`try again in N seconds`),对同一行返回 `null` → 回退固定兜底。

```
同一行  ──→ recoveryDistanceMs      读出 18:03:10  → 判 exhausted  ✅
        └─→ parseRateLimitRecoveryMs 读不出 → null  → 冷却 300min  ❌
```

⚠️ R7 的 spec 明写「不改 `parseRateLimitRecoveryMs` 的解析规则」——
那对 R7 的范围是对的(它只管分级),但**代价现在兑现了**:
分级与时长成了两套判据,对同一事实给出不同结论。
这正是本轮反复出现的「权威源不唯一」。

#### 要求

- **R5-a(必须):恢复时刻的解析必须单点。** 冷却时长与分级**共用同一个**
  恢复时刻提取器。⚠️ **不得**在 `parseRateLimitRecoveryMs` 里再抄一份中文正则 ——
  那是把两套判据变成两套半。收敛方向由实现选择(把
  `recoveryDistanceMs` 提为共用、或让 `parseRateLimitRecoveryMs` 复用它),
  但**结果必须是:同一行只有一个恢复时刻的答案**。
- **R5-b(必须):`parsed` 的判定随之统一。** R1 的来源标记以「共用提取器
  是否给出恢复时刻」为准 —— 提取到即 `parsed`,提取不到才 `fallback`。
- ⚠️ **不改** `normalizeCooldownEnd` 的 R7 语义:提取到的时刻若
  ≤ 最小有效冷却,仍回退固定兜底,且该结果来源记为 `fallback`(§R4 已述)。
- ⚠️ **不放宽**既有英文形态的解析结果 —— 三种英文形态的返回值逐字不变。

### R4 — 不涉及

- 不改 `parseRateLimitRecoveryMs` 的解析规则。
- 不改 `getRateLimitCooldownMs()` 取值(300 分钟)。
- 不改 `normalizeCooldownEnd` 的 R7 语义(解析值 ≤ 最小有效冷却 → 回退固定兜底)。
  ⚠️ 注意 R7 回退产出的值,来源是 **`fallback`** 而不是 `parsed` ——
  它虽然「解析成功过」,但最终用的是兜底时长。
- 不改孤儿收敛器把两条任务分别判终态的行为(见 §2.1)。
- 不做冷却的跨进程持久化重建。

## 5. 验收标准

1. 先以 `parsed`(未来 1 小时)进冷却,再以 `fallback`(未来 5 小时)进冷却
   → 生效值仍为**1 小时**,且留痕含被丢弃的 5 小时值。
   ⚠️ 这是本票存在的直接理由,必测。
2. 先 `fallback`(5 小时)再 `parsed`(1 小时)→ 生效值为 **1 小时**(parsed 覆盖 fallback)。必测。
3. 同源两次(`parsed` 1 小时,随后 `parsed` 3 小时)→ 取 **3 小时**(max,只延长)。必测。
4. 同源两次(`parsed` 3 小时,随后 `parsed` 1 小时)→ 仍为 **3 小时**(不缩短)。必测。
5. 现有 `parsed` 冷却**已到期**后再来 `fallback` → 正常按 `fallback` 进冷却(不被 R2 误挡)。必测。
6. 单次冷却(无竞争)的行为与冷却时长**逐字不变**(回归,必测)。
7. R3 留痕:每条冷却记录可读出来源;竞争被丢弃时可读出被丢弃的值。
8. **(v1.1 R5)** 命中行为 `429 …将在 2026-08-31 18:03:10 UTC+8 重置…`
   → 冷却至 **18:03:10**(而非 now+300min),来源记为 `parsed`。
   ⚠️ 本条的直接理由,必测。
9. **(v1.1 R5)** 既有三种英文形态(`resets around HH:MM` / `try again at HH:MM`
   / `try again in N seconds`)的解析结果与冷却时刻**逐字不变**(回归,必测)。
10. **(v1.1 R5)** 命中行确无任何恢复时刻 → 仍回退固定兜底,来源 `fallback`(回归)。必测。
11. **(v1.1 R5-a)** 分级(`classifyQuotaFailure` 的 kind)与冷却时刻对**同一行**
    取自同一个提取器 —— 断言二者不会出现「一个读得出、另一个读不出」的分歧。必测。

## 6. 不涉及的改动

- 不做下发前配额预检。
- 不清洗历史记录。
- 不新增清冷却的 API(本票不解决「人工解冻只能改库 + 重启」——另立)。

## 7. 兼容性

- 无竞争的单次冷却路径行为完全不变。
- 本票只在**存在竞争写入**时改变结局,而当前的结局在该情形下是错的。
