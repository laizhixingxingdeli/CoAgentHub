## 1. 背景与目标

本机(Windows)的后端测试是**红基线**:全量 129 failed / 924 passed
(2026-09-07 实测)。因此每张票的验收口径只能是「失败数不增加」,
而写票的人必须先知道**这一票要跑的那几个文件的真实基线**。

现在这个数字靠检视者手动跑一遍 vitest、手动抄进任务书。三次写偏都出在这里:

- 写「保持绿」而该文件本就是红的;
- 写一条在本机根本构造不出来的断言;
- 不知道某个文件有多慢,把太多文件塞进一张票。

**目标:一条命令拿到可直接粘进任务书的基线行,不再手抄。**

## 2. 改动范围

| 文件 | 改什么 |
|---|---|
| `scripts/test-baseline.mjs`(新增) | 工具本体 |

**不改**任何现有文件。不加依赖(只用 Node 内置模块)。

## 3. 详细改动

### R1. 一个脚本,一件事

```
node scripts/test-baseline.mjs <包目录> <测试文件...>
```

例:

```
node scripts/test-baseline.mjs packages/backend/server test/file.test.ts test/group-file.test.ts
```

行为:

1. 在 `<包目录>` 下跑 `npx vitest run <测试文件...>`;
2. 从输出里解析 `Test Files` 与 `Tests` 两行的计数;
3. 打印**一行可直接粘进任务书的基线**,含:失败数、通过数、总数、
   耗时(秒)、当前 `git rev-parse --short HEAD`、平台、Node 版本、取数时刻;
4. 退出码 0(**无论测试红绿**——本工具是取数,不是判定);
   只有工具自身出错(参数缺失、vitest 无法启动、解析不到计数)才非 0。

输出示例(格式自定,但必须含上述全部字段):

```
基线 @ 1c644222 (win32, node v24.13.0, 2026-09-07T23:30:00+08:00, 312s)
  test/file.test.ts test/group-file.test.ts
  → 0 failed | 12 passed (12);文件 0 failed | 2 passed (2)
```

加 `--json` 时改为输出同样字段的单个 JSON 对象,便于脚本消费。

**不做**的事(明确排除,防止范围膨胀):不比较两次基线、不写文件、
不改测试、不并行、不缓存、不猜哪些文件该跑。

## 4. 验收标准

1. **真实取数**:对 `packages/backend/server` 跑
   `test/file.test.ts test/group-file.test.ts` → 输出 `0 failed | 12 passed (12)`
   (检视者 2026-09-07 21:47 实测值,应能复现);贴出实际输出。
2. **红基线不影响退出码**:对同一包跑一个已知有红的文件
   (例:`test/retry-rollback-guard.test.ts`)→ 正常打印基线行、
   **退出码为 0**;`echo $?` 贴进汇报。
3. **`--json` 可解析**:加 `--json` 后输出能被 `JSON.parse` 成功解析,
   且含 failed / passed / total / durationSeconds / commit / platform /
   nodeVersion / timestamp 这些字段(字段名自定,汇报里列出来)。

不需要为本票新增单元测试 —— 它是一次性取数工具,上面三条实跑即验收。

## 5. 不涉及的改动

- 不改任何现有文件、不加依赖、不动 CI。
- 不做基线对比 / 历史存档(需要时另起一票)。
- 不试图修 Windows 红基线本身(那是另一张票)。

## 6. 兼容性

新增脚本,无运行时影响。
