# Spec: 阶梯与层卡片互相矛盾 —— L1 未开始却 L3 通过

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-24
> **严重度**: 高 —— 界面自相矛盾,读者无从判断哪个是真的

## 现象

打开需求「新项目接入:/init + AGENTS.md 标记段」的详情,同屏出现:

```
顶部阶梯:  L1 灰圈(未开始)· 重试 1 次  →  L2 灰圈  →  L3 绿勾
层卡片:    L3 检视 · 通过
           L2 协调 · 该需求还没有派发任务(L2 未开始)
           L1 执行与沟通记录 · L1 未开始
```

**L1 没开始、L2 没开始,L3 却通过了。** 在三层模型里这不可能 —— L3 检的是
L2 交回的成果,前两层没发生就不该有 L3 结论。

## 根因:豁免情形没有被表达

这条协调任务合法使用了 `coordination-close-integrity` R4 的**逃生舱**,
`diffSummary.noExecutionReason` 写明:

> 上一轮执行任务已完成完整实现并留下暂存成果;本票仅对既有实现按冻结 spec 做
> L2 核对、补提交和验证,因此未新增执行子任务。

于是:

- 零子任务 → `l1` 聚合恒为 `pending`
- 但协调者确实做了 L2、也确实交回了 L3,两者都有真实产物

**平台侧一切正常,是界面缺少「本票豁免 L1」这一档。** 它把「豁免」画成了
「未开始」,再与真实的 L3 通过并排,就成了矛盾。

## 要求

### R1. L1 增加「不适用 · 已声明理由」一档

当协调任务的 `diffSummary.noExecutionReason` 为**非空字符串**时,L1 状态取
**`na-declared`**,而非 `pending`。

- 阶梯该步用**中性**样式(与 L3 的 `na-fix` 同款),**不用**未开始的灰圈 ——
  未开始与不适用是两件事
- 层卡片标题显示「L1 不适用 · 已声明理由」
- **理由原文要能看到**:折叠展示 `noExecutionReason` 的内容,不要只给一个状态词

⚠️ 判据是 `noExecutionReason` **非空**,不是「零子任务」。零子任务但**没有**声明
理由的情况现在已被平台拒绝(R1 强制),若历史数据里存在,仍按 `pending` 处理。

### R2. L2 状态不得因零子任务而误判「未开始」

现有 L2 判定把「该需求还没有派发任务」当作 L2 未开始。但**协调任务本身落了
`done` 且带 `review_request`**,说明 L2 已完成。

**L2 的判据应当是协调任务自身的状态与 `review_request`,不是有没有子任务。**
子任务是 L1 的证据,不是 L2 的。

### R3. 阶梯与层卡片必须同源

阶梯每一步的状态与对应层卡片的状态**由同一处计算得出**,不得各算各的。

现状是两处分别推导(`RequirementStepper` 消费 `steps` 数组、层卡片消费
`deriveL1/L2/L3`),所以才可能出现不一致。**统一到一份派生结果**,阶梯只做渲染。

### R4. 不改后端

`noExecutionReason` 已由 `coordination-close-integrity` 落库并透出,
**本票纯前端**。

## 验收标准

- [ ] 带非空 `noExecutionReason` 的需求:L1 显示「不适用 · 已声明理由」,
      **不显示**「未开始」
- [ ] 该理由的**原文可见**(折叠或直接展示)
- [ ] 阶梯对应步用中性样式,与「未开始」的灰圈**视觉可区分**
- [ ] 协调任务 `done` 且带 `review_request` 时,L2 显示为**已完成**,
      不再显示「还没有派发任务」
- [ ] 阶梯状态与层卡片状态**在任何情况下一致**(同源计算,测试覆盖三层各状态组合)
- [ ] 零子任务但**无** `noExecutionReason` 的历史数据 → 仍按 `pending`
- [ ] 正常三层需求(有子任务、L1 完成)行为**不变**(回归,必测)
- [ ] 前端测试全绿,贴出用例数
- [ ] **未改动**后端
