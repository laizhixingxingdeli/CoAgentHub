# Spec: 协调任务落终态的完整性校验 —— 跳过的层不能拿到绿勾

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-24
> **前置**: `specs/ticket-template-role-blind.md`(已落地 `94721245`)—— 先让协调者
>   **收到正确的指令**,再谈强制;顺序反了就是拿平台去罚一个被误导的 agent

## 背景:说明与结构都补齐了,还缺强制

保证一个 agent 按流程走,有三层手段:

| 层 | 手段 | 状态 |
|---|---|---|
| **说明** | 任务书正文 + skill 文本 | ✅ 有,但**靠自觉,失败时静默** |
| **结构** | 平台按群内角色生成对应任务书 | ✅ `ticket-template-role-blind` 刚补上 |
| **强制** | 平台**拒绝**不合规的终态 | ❌ **完全没有** —— 本票 |

缺第三层的实际后果已经发生过:29 条任务 `parent_task_id` 全部为 null,L1 层
从未运行,协调者在 L2 检视自己刚写的代码,而**每一条都拿到了 `done`**。
检视者连续 16 次判 pass 没有察觉 —— 因为 commit 和测试数字都是真的。

### 为什么不能只靠说明

同一轮里有直接对照:检视者把 §4.2 手写进任务书正文的那一张,协调者回传了
`review_request`;后续改写成「按 spec 全文实现」的 11 张,**一张都没回传** ——
skill 里白纸黑字写着,它就是不执行。

**写在 skill 里但没被强制的规则,对一个无记忆的 agent 等于不存在。**

### 为什么这两条是「完整性」而非「风格」

- 协调任务落 `done` 却**零子任务** → L1 从未发生,「三层」实际只有两层,
  而且 L2 退化成自审(§3.14.6 明确要消灭的东西)。
- 协调任务落 `done` 却**无 `review_request`** → L3 拿不到交接载荷,检视者要么
  收不到、要么只能靠人工翻群消息补。§3.14.7 已确认广播群消息唤不醒协调者,
  任务通道是唯一可靠链路,载荷缺失就是链路断口。

两条都不是"最好有",是"缺了这一层就没发生过"。

### 现状的半个洞

`routes/group/tasks.ts:405` 已经会校验 `review_request` 的**形状**(不合形状 → 400),
**但不检查它存不存在** —— 完全不带就静默放行。这与
`specs/dispatch-fields-silent-loss.md` 修掉的那个洞完全同构:契约字段缺失却返回成功。

---

## 决策:在 PATCH 终态处拒绝,而不是记录下来等人看

本票是**单一内聚关注点**(协调任务落终态时的完整性),两条规则共用同一个校验点、
同一个代码位置、同一份测试,不拆成两票。

### R1. 规则一:`done` 的协调任务必须有执行子任务

PATCH 一条**协调任务**至 `done` 时,若不存在任何 `parentTaskId` 指向它的任务
→ **400 拒绝**,错误信息说明「L1 层未发生:本协调任务没有任何执行子任务」。

**「协调任务」的判定复用现成的**:`lib/detached-task-liveness.ts` 的
`isDetachedTask()` 已经封装了同一判据(显式 ReplyMode 标记或目标含 coordinator
角色)。**直接复用,不要另写一套判定** —— 两份同样的判据会各自演化。

### R2. 规则二:该走 L3 时,`review_request` 不得缺失

PATCH 协调任务至 `done` 时,若按 §4.1 的布尔式**本票应当走 L3**,而
`diffSummary` 不含 `review_request` → **400 拒绝**。

判定照抄 §3.14.6 的单布尔式,**不要另立口径**:

```
应走 L3  ⟺  群内 reviewer 与 coordinator 同时在场
            AND  本票 dispatchKind != 'fix'
```

- `dispatchKind` 为 `null`(历史任务/未走新字段)→ **按 requirement 处理**,
  即要求 `review_request`。与 `dispatch-kind-field` R2 同一保守立场:
  宁可多要一次交接,不可让一层静默消失。
- 现有的形状校验**保持不变**,本票只补「存在性」。

### R3. 只管 `done`,不管 `failed`

两条规则**都只在目标状态为 `done` 时生效**。

`failed` 是诚实的失败上报,此时没有执行成果可交接、也可能确实没来得及下发 —— 
对失败追加门槛只会逼 agent 谎报成 `done`。**这条是设计意图,不是遗漏。**

### R4. 逃生舱:显式声明,而不是静默跳过

确实存在无需下发执行器的协调任务(例如判定该需求无需改动)。允许在 `diffSummary`
里显式声明豁免:

```json
{ "noExecutionReason": "<为什么这条协调任务没有执行子任务>" }
```

带该字段时 R1 放行(R2 不受影响)。**非空字符串才算数**,空串/空白不放行。

理由与 `specs/terminal-status-needs-reason.md` 同构:把静默降级变成一句必须写下来
的话。逃生舱存在的意义是**让例外可见**,不是让规则可绕。

### R5. 不改这些

- **不改** skill 文件 —— 本票是平台侧强制,skill 已经写对了
- **不改**前端 —— 前端三层判定是对的
- **不改** `failed` 路径、`detachedTimeoutMinutes` 兜底、checkpoint/回滚
- **不改**现有 `review_request` 形状校验

## 验收标准

- [ ] 协调任务零子任务 PATCH `done` → **400**,错误信息点明「L1 层未发生」
- [ ] 同上但带非空 `noExecutionReason` → **放行**
- [ ] `noExecutionReason` 为空串/纯空白 → 仍 **400**
- [ ] 三方在场 + `dispatchKind` 非 `fix` + 无 `review_request` → **400**
- [ ] 三方在场 + `dispatchKind='fix'` + 无 `review_request` → **放行**(修复票不走 L3)
- [ ] 两方在场(群内无 reviewer)+ 无 `review_request` → **放行**
- [ ] `dispatchKind` 为 `null` + 三方在场 + 无 `review_request` → **400**(保守)
- [ ] PATCH 至 **`failed`** 时两条规则**均不生效**(回归,必测)
- [ ] **非协调任务**(普通执行任务)PATCH `done` 行为**完全不变**(回归,必测)
- [ ] 协调任务判定**复用 `isDetachedTask()`**,未另写一套
- [ ] 现有 `review_request` 形状校验行为未变
- [ ] 后端测试全绿,贴出用例数;上述每条验收都要有对应用例
- [ ] **未改动** `skills/`、前端

## 不涉及

- 提交策略(执行器提交 vs 协调者提交 vs 任务分支 squash)—— 用户已明确暂缓
- L2 打回路径本身的实现
- 执行器侧的任何校验(`verify-agent-claims` 现状保留:只标记不裁决)
