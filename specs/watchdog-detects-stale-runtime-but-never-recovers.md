# Spec: 看门狗检测到运行时陈旧却不自愈,平台可无限期跑旧代码

> **状态**: Frozen — 2026-09-05
> **文件**: `scripts/coagenthub-watchdog.sh`(LaunchAgent `com.coagenthub.watchdog`,`StartInterval` 300s)
> **优先级**: 最高。这不是功能缺陷,是**其它票能否收工的前提**。

## 1. 事故(2026-09-03 ~ 09-05 实证)

运行时在 **09-04 00:10 的构建**上停留约 **22 小时**,期间源码里的修复全部未生效。
后果:结案守卫用的是没有修复的旧版本,**连续四轮协调链条撞同一个已修好的死结**,
一轮协调烧掉 898,330 tokens,净产出为零。

平台一直在报告这件事 —— 结案拒绝文案里逐字写着
「当前运行时为陈旧构建(staleReason: …),本次拒绝可能来自旧版守卫」——
但没有任何自动机制去处理它。

## 2. 两个洞

### 洞 1:`staleReason=process` 分支只记日志,不重启

`coagenthub-watchdog.sh:263-267`:

```bash
# R1:process 陈旧不触发重建(entry 比进程启动新,重启即可)
if [ -z "$failed" ] && [ "$reason" = "process" ]; then
  echo "… INFO staleReason=process,不触发重建(重启即可解决)" >> "$WATCHDOG_LOG"
  return 0
fi
```

注释自己写着「**重启即可解决**」,然后 `return 0` —— **不重启**。
只有健康检查失败才会走 `prod restart`;而陈旧进程是健康的,永远走不到那条路径。

实测日志(09-04 21:02 → 22:12,每 2.5 分钟一条,共 28 条):

```
INFO staleReason=process,不触发重建(重启即可解决)
INFO staleReason=process,不触发重建(重启即可解决)
…
```

70 分钟里它准确地检测到问题、准确地说出解法、**一次都没有执行**。
最后是人工 build + restart 才解除。

### 洞 2:退避打满后永久停用自动重建,且只能人工删文件恢复

`:232-238`,连续失败达 `STALE_MAX_FAILURES`(默认 3)后:

```
SKIP 构建已连续失败 3 次(≥3),停止自动重建,等待人工介入
```

计数持久化在 `/tmp/coagenthub-watchdog-stale-failures`,**没有任何自动归零路径**
(`stale_fail_reset` 只在重建成功时调用 —— 而停用后不再重建,所以永不成功)。

实测三次失败横跨 **三天**:09-03 00:10、09-03 22:05、09-04 21:00,
每次都是同一签名 `复核仍陈旧(stale状态=process) (restart --build 退出码=1)`。
三次之后自动重建对整台机器永久关闭,直到 2026-09-05 检视者手工把文件写回 0。

**退避的本意是防抖,但「跨三天的三次」不是抖动。** 计数没有时间窗,
一次孤立失败会永久累积。

## 3. 危害

- 平台可以无限期运行旧代码,**而所有表面指标都正常**:健康检查通过、任务在派、
  L2 在判、日志在刷。唯一的信号是拒绝文案里一句话和 `/api/health` 的 `stale` 字段。
- 修复被提交、被测试、被合并,却不生效。检视者与协调者都会据此得出错误结论
  (「这个 bug 没修好」),从而反复重派同一张票。

## 4. 要做的

**R1 `staleReason=process` 必须触发重启。** 该状态的定义就是「构建是新的、进程是旧的」,
解法确定且唯一。检测到即执行 `prod restart`(不带 `--build`),
按现有的「无在途任务才动手」守卫(`check_in_flight`)择机进行。
⚠️ 不得放松 `check_in_flight` —— 宁可等,不可误杀在途任务。

**R2 陈旧状态不得静默持续。** 若因在途任务而连续 N 轮(建议 ≥ `stallAlertMinutes` 对应轮数)
无法处理陈旧,必须升级为 `WARN` 并在 `/api/system/health` 或群消息中可见,
不能只在日志里刷同一行 `INFO`。**「每 2.5 分钟记录一次同样的无所作为」是本票要消灭的形态。**

**R3 退避计数要有时间窗与自动恢复。** 失败计数仅统计滚动窗口内(建议 24h)的失败;
窗口外的旧失败自动淘汰。达阈值停用后,须在窗口过期后自动重新尝试一次,
不得要求人删文件。

**R4 停用状态必须显性可见。** 自动重建被停用时,`/api/system/health` 须透出该事实
(如 `autoRebuildDisabled: true` 与停用时刻),使人和协调者能立刻知道
「平台已放弃自愈」。今天这件事只有读 `/tmp` 日志才能发现。

## 5. 硬验收

真实端到端,不接受只有单测:

1. 构造 `staleReason=process`(重新构建但不重启)→ 断言看门狗在下一轮
   **实际执行了重启**,且 `/api/health` 随后 `stale=false`。
2. 同上但制造在途任务 → 断言本轮**不重启**(不误杀),且连续跳过达阈值后
   出现 `WARN` 级可见信号,不是重复 `INFO`。
3. 把失败计数写成 3、并把最后一次失败时间设为 25 小时前 → 断言自动重建
   **自行恢复尝试**,无需人工删文件。
4. 停用期间 `/api/system/health` 能读出停用事实。

⚠️ 验收 1 必须证明「真的重启了」——比对进程启动时间与 `entryMtime`,
或直接断言 `/api/health` 的 `stale` 由 true 变 false。**只看日志里印了什么不算。**

## 6. 不涉及

- 不改健康检查失败时的既有重启路径。
- 不改 `check_in_flight` 的 fail-closed 语义。
- 不改 `restart --build` 自身的实现(它退出码非零的原因是另一件事:
  端口监听进程与 PID 文件不符,见 §7)。

## 7. 附:三次重建失败的真实原因(不在本票范围,但需记录)

`coagenthub-prod.sh restart` 要求进程确实被自己替换,否则非零退出:

```
FAIL restart :端口监听者 pid $now 与本脚本记录 pid $mine 不符,进程未被替换
```

检视者此前多次用 `nohup node dist/server.mjs` 手工起服务,PID 文件对不上,
于是每次 `restart --build` 都退出 1。**这是人为操作打废了自愈,不是脚本缺陷。**
纪律已记录:重启一律走 `scripts/coagenthub-prod.sh restart`。
本票的 R3/R4 要保证的是:**即使再发生这种事,系统也能自己走出来、并且看得见。**
