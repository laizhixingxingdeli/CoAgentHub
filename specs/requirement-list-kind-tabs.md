# Spec: 需求列表按 dispatchKind 分「需求 / 修复」

> **状态**: Landed — L3 通过(2026-08-24),实现 `97dbe91e`
> **版本**: 1.0
> **日期**: 2026-08-24
> **依赖**: `specs/dispatch-kind-field.md`(已 L3 通过,`dispatchKind` 已可读)、
>   `specs/dispatch-fields-silent-loss.md`(在途——该字段能否可靠落库取决于它)

## 背景

用户提出想在需求列表里区分「哪些走的是三层、哪些走的是两层」。经讨论,
「三层/两层」是**编制**(群成员构成,群级),不是逐项状态——同一个群里所有
工作的编制都一样,按编制切列表会切出一个空标签页。

真正逐项变化的是**工作类型**:检视者对每票分流出的 `requirement` /
`fix`(spec v4.0 §3.14.6)。这才是能切出两个都有内容的列表的维度。

## 要求

### R1. 需求列表增加「需求 / 修复」切换

在 `RequirementList` 之上(或列表头部)加一个二态切换,按当前选中态过滤
`group-tasks-by-spec.ts` 产出的 `Requirement[]`:

- **需求**:`dispatchKind === "requirement"`
- **修复**:`dispatchKind === "fix"`

### R2. `null` 的归类:按 `requirement` 处理

历史任务与尚未走通新字段的任务,`dispatchKind` 为 `null`。按
`dispatch-kind-field` spec R2 的既定原则(宁可多检不可漏检的同一立场):
**归入「需求」标签**,不单独开第三个标签,也不归入「修复」。

### R3. 计数与空态

每个标签显示计数(如「需求 (12)」「修复 (3)」)。某个标签下没有内容时,
显示空态提示,**不要**隐藏该标签本身(隐藏会让用户以为功能不存在)。

### R4. 修复类需求的父子归并规则不变

修复票通常复用既有 `specRef`,会被 `group-tasks-by-spec.ts` 的现有分组规则
并入同一 `specRef` 的需求组(见该文件顶部注释)。**本票不改分组算法**——
一条需求组的 `dispatchKind` 取组内**最新任务**的值(与现有 `status`/
`updatedAt` 取值方式一致),因此一个先是 `requirement` 后被追加 `fix` 修正票
的组,会跟着最新一票的类型切换标签。**这是预期行为**,不是 bug:它反映的是
「这条需求线现在正在发生的是什么」。

若执行者认为这个继承规则有更好的处理方式,可在汇报中提出,但**不要不声不响
改成别的规则**。

### R5. 选中态跨标签切换的处理

用户在「需求」标签选中了一条,切到「修复」标签——原选中不在当前列表里。
按 `requirement-live-refresh` spec R3 同样的原则:**回落到未选中**,
不自动挑一条。

## 验收标准

- [ ] 需求列表可在「需求 / 修复」间切换
- [ ] 每个标签显示计数
- [ ] `dispatchKind` 为 null 的任务归入「需求」标签
- [ ] 某标签下为空时显示空态,标签本身仍可见可点
- [ ] 切换标签后原选中(若不在新列表中)回落为未选中,不自动跳选
- [ ] 分组算法(`group-tasks-by-spec.ts`)未被改动
- [ ] 前端测试全绿,贴出用例数
- [ ] **未改动**后端

## 不涉及

- `group-tasks-by-spec.ts` 的分组/归并算法
- 阶梯语义(`requirement-stepper-semantics`)
- 侧栏编制徽章(`sidebar-three-layer-badge`)—— 那是群级,这是票级,两者不是
  同一件事,不要合并成同一套 UI

## 执行环境提示

- 前端 `http://localhost:5173`
- **下发本票前确认** `dispatch-fields-silent-loss` 是否已落地:若未落地,
  `dispatchKind` 可能因竞争条件停留在 null,导致本票验收时「需求」标签
  异常庞大。若遇到这种情况,在汇报中说明,不要误判为本票自己的 bug
