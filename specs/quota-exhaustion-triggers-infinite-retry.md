# Spec: 额度耗尽被当成普通进程消失,10 秒一轮无限重派

> **状态**: Landed — v1.0,L3 通过 2026-08-28,实现 `df8bf8b1`
> **v1.1 新增 R7 / R8,Ready for Implementation**
> **版本**: 1.1
> **日期**: 2026-08-30

## 现象

2026-08-28 实测:Codex 额度耗尽后,平台在约 12 分钟内**重派了 72 个子任务**,
全部立刻 failed,直到检视者停掉后端才止住。

服务端日志:

```
{"type":"error","message":"You've hit your usage limit. Upgrade to Pro ...
 try again at 3:32 PM."}
{"type":"turn.failed","error":{"message":"You've hit your usage limit ..."}}
[executor] server 侧 spawn: codex exec --approve-for-me --ephemeral --json ...
```

任务侧记录的失败原因是 `executor pid <n> no longer exists` ——
即**孤儿收敛器把它当成了普通的进程消失**。

## 根因

进程确实立刻退出了,所以 `process.kill(pid, 0)` 抛 ESRCH 成立;
但退出原因是**额度耗尽**,重试在额度恢复前必然再次失败。
平台没有区分这两种「进程没了」:

```
进程崩溃 / 被杀     → 重试有意义
额度耗尽 / 限流     → 重试必然失败,应退避到恢复窗口
```

⚠️ 执行器的 stdout **明确带着原因与恢复时刻**(`try again at 3:32 PM`),
信息是有的,只是没有被读取和利用。

## 要做的

### R1 — 识别额度耗尽类失败

从执行器输出中识别配额/限流类终止,至少覆盖:

```
"usage limit"     "rate limit"    "quota"
429               "try again at <time>"
```

⚠️ 按**语义特征**匹配,不要为每个 CLI 写一套正则 ——
与 `generic-executor-output-parsing` / `generic-token-usage-collection`
的既有结论一致(定位层不得按 CLI 写死)。

### R2 — 识别为额度耗尽时进入冷却,不得立即重派

复用 `executors.ts` 既有的**冷却机制**(`cooldownEndMs` / `isInCooldown`,
`executor-availability.ts` 已在使用)。
⚠️ **不要新建一套退避实现。**

- 能从输出解析出恢复时刻(如 `try again at 3:32 PM`)→ 冷却至该时刻
- 解析不出 → 采用保守的固定冷却(建议 ≥ 5 分钟),并在日志中写明依据
- **解析出的时刻不在未来 → 视同解析失败,走固定冷却(v1.1 R7)**

### R3 — ⚠️ 冷却期内不得重派给同一执行器

冷却中的执行器视为**不可用**。若群内有其他可用执行器,可改派;
都不可用 → 任务如实标记为等待恢复,**不得空转重派**。

### R4 — ⚠️ 必须有重派次数上限,与原因无关

即使原因识别失败,同一父任务的连续失败子任务数达到阈值(建议 5)后
**必须停止重派**并如实记录,等待人工介入。

⚠️ 这是**兜底防线** —— 本次事故的教训是:只要有一条路径能无限重派,
迟早会踩到。不得只依赖 R1 的原因识别。

### R5 — 留痕

进入冷却与触发上限时,在任务 `diffSummary` 与群内各留一条可读记录,
说明原因与预计恢复时刻,便于人判断是等待还是介入。

### R6 — ⚠️ 范围限制

不改结案守卫,不改孤儿收敛器的 ESRCH 判据本身
(它没判错 —— 进程确实没了,错的是「没了之后立刻重派」)。

### R7 — 解析出的恢复时刻不在未来时,必须回退到固定冷却(v1.1 新增)

R2 原本只有两个分支(解析出 / 解析不出),漏了第三种:**解析出来了,但那个
时刻已经过去或近在眼前**。当前实现把它钳到 `now + 1ms`:

```ts
// queue.ts
export function normalizeCooldownEnd(endMs: number, nowMs = Date.now()): number {
  return Math.max(nowMs + 1, endMs);
}
```

这个守卫的本意是「冷却时刻不得为过去」,实际效果却是**产出一个形同虚设的冷却**
—— 记录上写着「已进入冷却」,执行器下一毫秒就重新可派发,直接违反 R2 的
「不得立即重派」与 R3 的「冷却中视为不可用」。

**实证(2026-08-29):** 任务 `01a04d65-45d0`,20:49:00 判为额度失败,
写入的恢复时刻是 **20:49:15** —— 一个 **15 秒**的冷却。

⚠️ 这条**没有观察到实际级联事故**:那次之后队列恰好 90 分钟没有该执行器的活,
下一次派发(22:23)正常成功。所以它是**机制确凿、危害未兑现**的潜在缺陷 ——
按缺陷修,不要在票面上把它写成已发生的事故。

**要求:**

- 解析所得时刻 `<= now + 最小有效冷却` 时,**丢弃它**,改用 R2 的固定冷却兜底。
- 「最小有效冷却」取一个明确常量(建议 60 秒),不要用魔数 `1`。
- 留痕中写明「解析所得时刻不可用,已回退固定冷却」及被丢弃的原值(R5)。
- `normalizeCooldownEnd` 的**名字与签名可保留**,但语义不得再是无条件
  `Math.max(now+1, x)`。

### R8 — 额度判定必须覆盖所有终态写入路径(v1.1 新增)

R1 只规定了「要识别」,没规定「在哪些入口识别」。当前四条终态写入路径里,
**只有三条**做了额度判定:

| 终态写入路径 | 额度判定 | 说明 |
|---|---|---|
| queue 进程退出(非 detached) | ✅ | `exit N(执行器额度限制,…)` |
| queue 执行超时 | ✅ | queue.ts:1861 |
| 孤儿收敛器(进程消失、任务仍 running) | ✅ | 2026-08-30 实测 25 秒内判出 |
| **执行器/协调者自行 `PATCH` 回写终态** | ❌ | `routes/group/tasks.ts` 内无任何额度判定 |

于是存在一条完整的绕过路径:执行器撞额度 → 其 runtime 自己 `PATCH` 任务为
`failed`、错误正文里写着额度原因 → 进程干净退出 → 收敛器因任务已终态而不看它
→ **全程无人下冷却** → 平台转头把下一张票发给这个已耗尽的执行器。

**要求:**

- `PATCH` 终态路由在写入 `failed` 时,对调用方提供的错误正文复用**同一个**
  分类器(`classifyQuotaFailure`),命中则与其他三条路径**同口径**处理:
  写 `executorCooldownEndMs`、`enterCooldown`、留痕。
- ⚠️ **复用,不得新写一套判定** —— 与 R1「不要为每个 CLI 写一套正则」同源。
- ⚠️ 只在 `failed` 终态上判定;`done` 不判(执行器成功结案时正文里提到额度
  是叙述,不是失败原因)。
- 误报防线沿用既有的 `classifyQuotaFailure` 结构性证据要求
  (非零退出 / 可解析的恢复时刻 / provider 错误形状),不放宽。

## 验收要点

- 构造额度耗尽输出(含 `usage limit` 与 `try again at HH:MM`),
  验证:识别为配额失败 → 执行器进入冷却至该时刻 → **不再重派**(必测)
- 冷却期内该执行器被判为不可用;群内有其他可用执行器时能改派(R3)
- 原因**无法识别**时,连续失败达 5 次后停止重派(R4,必测 —— 这是兜底防线)
- 普通进程崩溃(非配额)→ 重试行为**不变**(回归,必测)
- 冷却与上限触发均有可读留痕(R5)
- **(v1.1 R7)** 构造「解析出的恢复时刻早于/等于当前时刻」的输出,
  断言最终冷却时长 **≥ 固定兜底冷却**,而不是 1ms / 15s;留痕含回退说明。
- **(v1.1 R7)** 正常情形回归:解析出的时刻在未来且远于最小有效冷却时,
  冷却时刻**逐字不变**,仍等于解析值。
- **(v1.1 R8)** `PATCH` 一个带额度错误正文的 `failed` 终态,
  断言该执行器进入冷却且 `executorCooldownEndMs` 落库;
  `PATCH` 一个带同样正文的 `done` 终态,断言**不**进入冷却。
- **(v1.1 R8)** 非额度错误正文的 `PATCH failed` 行为**逐字不变**(回归)。
- 测试全绿,贴出用例数
