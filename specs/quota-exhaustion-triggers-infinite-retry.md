# Spec: 额度耗尽被当成普通进程消失,10 秒一轮无限重派

> **状态**: Frozen — 待实现
> **版本**: 1.0
> **日期**: 2026-08-28

## 现象

2026-08-28 实测:Codex 额度耗尽后,平台在约 12 分钟内**重派了 72 个子任务**,
全部立刻 failed,直到检视者停掉后端才止住。

服务端日志:

```
{"type":"error","message":"You've hit your usage limit. Upgrade to Pro ...
 try again at 3:32 PM."}
{"type":"turn.failed","error":{"message":"You've hit your usage limit ..."}}
[executor] server 侧 spawn: codex exec --approve-for-me --ephemeral --json ...
```

任务侧记录的失败原因是 `executor pid <n> no longer exists` ——
即**孤儿收敛器把它当成了普通的进程消失**。

## 根因

进程确实立刻退出了,所以 `process.kill(pid, 0)` 抛 ESRCH 成立;
但退出原因是**额度耗尽**,重试在额度恢复前必然再次失败。
平台没有区分这两种「进程没了」:

```
进程崩溃 / 被杀     → 重试有意义
额度耗尽 / 限流     → 重试必然失败,应退避到恢复窗口
```

⚠️ 执行器的 stdout **明确带着原因与恢复时刻**(`try again at 3:32 PM`),
信息是有的,只是没有被读取和利用。

## 要做的

### R1 — 识别额度耗尽类失败

从执行器输出中识别配额/限流类终止,至少覆盖:

```
"usage limit"     "rate limit"    "quota"
429               "try again at <time>"
```

⚠️ 按**语义特征**匹配,不要为每个 CLI 写一套正则 ——
与 `generic-executor-output-parsing` / `generic-token-usage-collection`
的既有结论一致(定位层不得按 CLI 写死)。

### R2 — 识别为额度耗尽时进入冷却,不得立即重派

复用 `executors.ts` 既有的**冷却机制**(`cooldownEndMs` / `isInCooldown`,
`executor-availability.ts` 已在使用)。
⚠️ **不要新建一套退避实现。**

- 能从输出解析出恢复时刻(如 `try again at 3:32 PM`)→ 冷却至该时刻
- 解析不出 → 采用保守的固定冷却(建议 ≥ 5 分钟),并在日志中写明依据

### R3 — ⚠️ 冷却期内不得重派给同一执行器

冷却中的执行器视为**不可用**。若群内有其他可用执行器,可改派;
都不可用 → 任务如实标记为等待恢复,**不得空转重派**。

### R4 — ⚠️ 必须有重派次数上限,与原因无关

即使原因识别失败,同一父任务的连续失败子任务数达到阈值(建议 5)后
**必须停止重派**并如实记录,等待人工介入。

⚠️ 这是**兜底防线** —— 本次事故的教训是:只要有一条路径能无限重派,
迟早会踩到。不得只依赖 R1 的原因识别。

### R5 — 留痕

进入冷却与触发上限时,在任务 `diffSummary` 与群内各留一条可读记录,
说明原因与预计恢复时刻,便于人判断是等待还是介入。

### R6 — ⚠️ 范围限制

不改结案守卫,不改孤儿收敛器的 ESRCH 判据本身
(它没判错 —— 进程确实没了,错的是「没了之后立刻重派」)。

## 验收要点

- 构造额度耗尽输出(含 `usage limit` 与 `try again at HH:MM`),
  验证:识别为配额失败 → 执行器进入冷却至该时刻 → **不再重派**(必测)
- 冷却期内该执行器被判为不可用;群内有其他可用执行器时能改派(R3)
- 原因**无法识别**时,连续失败达 5 次后停止重派(R4,必测 —— 这是兜底防线)
- 普通进程崩溃(非配额)→ 重试行为**不变**(回归,必测)
- 冷却与上限触发均有可读留痕(R5)
- 测试全绿,贴出用例数
