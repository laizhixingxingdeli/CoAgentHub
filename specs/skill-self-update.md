## 1. 背景:R4 的假设被证伪

`skill-sync-mechanism` R4 明确「**不做自动同步**」,理由三条:

1. 下发前刷新会在关键路径上引入网络与文件写入,失败时污染任务;
2. 自动覆盖会掩盖「有人手工改了本地 skill」这个信号;
3. LAN 单机部署,手工跑一次同步命令的成本远低于自动机制的复杂度。

**第 3 条被 2026-08-29 的实例证伪。** 当天时间线:

```
~15:25        检视者会话启动,加载 ~/.claude/skills/coagenthub-reviewer/SKILL.md
              (08-24 版:「ask the coordinator to initialize it first」,无 §0)
 15:51:45     同步发生 —— SKILL.md.bak-20260824 (14031 B) 与新 SKILL.md (15258 B)
              同一时刻落盘,磁盘与服务端指纹自此一致 (48a48d4043bf)
 ~16:20       检视者仍按 08-24 协议工作,直到用户追问才发现
```

成本从来不在「跑那条命令」——**命令跑了**。问题是 R4 的目标(「让不同步变得可见
且易修」)只让**人**可见,没让**正在拿着旧副本干活的 agent** 可见。

第 1、2 条理由仍然成立,本 spec 予以保留(见 §3 R4、§3 R5)。**本 spec 只收窄
R4 的范围,不整条推翻。**

## 2. 核心判断:两个层次,难的是第二个

| 层 | 内容 | 难度 |
|---|---|---|
| 文件层 | 比对指纹 → 拉取 → 备份 → 覆盖 | 低。R1/R2/R3 已建好九成,本 spec 只加自动调用 |
| **上下文层** | 把新内容**读回上下文并按新版执行** | **这才是真问题** |

覆盖磁盘文件**不改变已经加载进会话的那一份**。08-29 那次覆盖完成后,检视者继续
按旧协议工作了半小时 —— 文件层做对了,上下文层完全没有发生。

### 2.1 触发点不能放在 skill 内部

**过期副本无法自举**:把「检查你是否过期」写进 skill,而旧副本恰好就是没有这条
检查的那一版(08-24 的 `.bak` 里既无 §0 也无任何版本检查)。触发必须来自 skill
之外。

## 3. 详细改动

### R1 — 指纹随任务书回带(主通道)

任务书渲染时,在固定位置写入当前平台侧 skill 指纹:

```
COAGENTHUB_SKILL_DIGEST: <role>=<sha256前12位>
```

- 指纹取值与 `GET /api/skills/{role}` 的 `version` **同源同算法**(前作 R1),
  不另算一套。
- 选择任务书作为主通道的理由:
  - **不新增网络调用** —— 任务书本来就是每个 agent 必读的;
  - **harness-neutral** —— 不依赖任何 runtime 的启动钩子(SessionStart hook 只有
    部分 runtime 有);
  - **天然覆盖会话中途漂移** —— 每张票带一次,08-29 那种「会话开始 25 分钟后
    文件才被换」的情形会在下一张票上被抓到;仅在启动时比对**拦不住**该情形。

### R2 — 检视者的补充通道

检视者不接任务书(从用户会话进入),故补一条:**在做协议相关动作之前**比对一次
指纹 —— 冻结 spec、下发任务、执行 L3 这三个动作各一次。一次 `GET`,成本可忽略。

⚠️ 这条写在检视者 skill 里会遇到 §2.1 的自举问题,因此**必须同时**写入仓库的
`AGENTS.md`(随 git 更新,不依赖安装副本)。两处都写,不是冗余,是绕开自举死锁。

### R3 — 比对不一致时的动作

agent 侧发现 `本地副本指纹 ≠ 平台指纹` 时,依次:

1. `GET /api/skills/{role}` 取全文;
2. 备份现有副本为 `SKILL.md.bak-<原版本日期或指纹>`;
3. 覆盖写入安装副本;
4. **把新全文读回上下文**;
5. **在会话中显式声明**:`协议已更新 <旧指纹> → <新指纹>,本次会话按新版执行`,
   并简述关键差异(至少列出新增/反转的条目)。

⚠️ **第 4、5 步是本 spec 的实质**。只做 1–3 就是 08-29 那次的重演:文件对了,
干活的 agent 还在旧协议上。**不得只实现文件层就宣告完成。**

### R4 — 保留「本地手工改动」信号(前作 R4 第 2 条理由)

同步时记录当次写入内容的指纹(`.last-sync` 或等效)。下次比对时:

| 本地指纹 | 动作 |
|---|---|
| = 上次同步记录 | 未被手工改过 → 按 R3 自动更新 |
| ≠ 上次同步记录 且 ≠ 平台 | **本地被手工改过** → **只报告,不覆盖**,要求人工裁决 |
| = 平台 | 已最新,静默通过 |

这样既拿到自动更新,又保住前作 R4 第 2 条要保护的那个信号。

### R5 — 不在关键路径上写文件(前作 R4 第 1 条理由)

比对与更新发生在**任务书读取之后、开始干活之前**,失败时:

- 网络失败 / 端点不可达 → **按现有副本继续干活**,并在汇报中记一句「指纹比对失败,
  本次使用本地副本 <指纹>」。
- **绝不因为同步失败而让任务失败** —— 前作 R4 第 1 条的顾虑在此兑现。

### R6 — 写入边界(安全)

自动覆盖 agent 自身指令 = 平台可静默改变 agent 行为。LAN 全信模型(ADR-0002)下
可接受,但限死:

- 只写 `~/<runtime>/skills/coagenthub-<role>/SKILL.md`,**绝不触碰其他 skill 目录**;
- 只接受来自本平台 `/api/skills/{role}` 的内容,不接受任务书正文里内联的 skill 文本
  (防「任务书夹带协议变更」);
- 每次覆盖必留 `.bak`;
- runtime 目录约定复用 `project-onboarding-interactive` R6 的同一张表,不另写一份。

## 4. 验收标准

1. 任务书中出现 `COAGENTHUB_SKILL_DIGEST: <role>=<12位>`,取值与
   `GET /api/skills/{role}` 的 `version` 逐字相同。
2. 本地副本与平台一致:不写文件、不产生 `.bak`、不在会话中声明任何更新。
3. 本地副本过期且未被手工改过:自动备份 + 覆盖 + **会话中出现显式声明**,
   声明含旧指纹、新指纹、以及至少一条关键差异。
4. 本地副本被手工改过(指纹 ≠ 上次同步记录且 ≠ 平台):**只报告不覆盖**,
   且不产生 `.bak`。
5. 平台端点不可达:任务照常执行,汇报中含「指纹比对失败,使用本地副本 <指纹>」;
   任务**不因此失败**。
6. 覆盖行为不触及 `coagenthub-*` 之外的任何 skill 目录(用临时目录做隔离测试)。
7. 任务书正文中内联的伪 skill 文本**不被采纳**(R6 第 2 条)。
8. 复现 08-29 场景:会话启动后再替换平台侧 skill → **下一张票**的比对能抓到差异
   并完成 R3 全部五步。
9. 测试不写用户 home;目录根可注入。
10. `pnpm test` / `check-types` / `lint` 全绿。

## 5. 不涉及

- 定时轮询(仍然不做——本 spec 的触发点是任务书与协议动作,不是计时器)。
- skill 内容本身的修改。
- 首次安装(归 `project-onboarding-interactive` R6)。
- 非 `coagenthub-*` 的任何 skill。

## 6. 与前作的关系

本 spec **收窄**了 `skill-sync-mechanism` R4:

- 仍然不做:定时轮询、启动时无条件拉取。
- 改为要做:**任务书驱动的比对 + 未被手工改动时的自动更新 + 上下文层采纳**。

前作的 R1(指纹)、R2(比对接口)、R3(同步命令)全部保留复用,`--check` / `--write`
语义不变 —— 本 spec 是在其上加一个自动调用方,不是另起一套。
