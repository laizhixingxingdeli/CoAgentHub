# Spec: 回写被拒可以无限重试 —— 一次烧掉 3600 轮、1 小时 41 分

> **状态**: Frozen
> **版本**: 1.0
> **日期**: 2026-09-11
> **来源**: 2026-09-11 的真实事故。检视者在排查「执行器是不是被抢占」时查出
> 根因,与抢占无关。

## 1. 背景与目标

### 1.1 事故经过(检视者已逐条复核)

任务 `01a09025-1c3c-72da-b1de-5070a376083a`(atomcode 执行器,群 coagenthub):

| 时刻 | 事件 |
|---|---|
| 19:05:46 | 任务创建 |
| ~#t2909 | **实现已完成**,在写测试 |
| #t2909 → #t6527 | **约 3600 轮工具调用**,全部在重试回写 |
| 20:46:59 | 平台判失败:`executor pid 5664 no longer exists` |

**跑了 1 小时 41 分,后 3600 轮没有产生任何价值。** 实现本身是好的 ——
提交 `7c4e3cb0` 在进程死之前就落了地,L2/L3 都已通过。

### 1.2 它在重试什么

`routes/group/tasks.ts:408` 的守卫:

```
本协调任务应走 L3 三方检视,但 diffSummary 缺少 review_request 交接载荷
(群内 reviewer 与 coordinator 同时在场)。
```

执行器的汇报逐轮记录了它的困惑(原文摘录):

> `#t6254` 回写被 L3 三方检视守卫拒绝:本协调任务需带 `review_request` 交接载荷。先读守卫逻辑拿到要求的载荷形状。
> `#t6369` …正在补齐后重试。读守卫细节 + 查任务 dispatchKind。
> `#t6523` …按 schema 形状补载后重试回写。

它反复去**读守卫源码**试图推断载荷形状,始终没成。

### 1.3 为什么注定无解:守卫自己说了

`tasks.ts:128` 的 `coordinationCloseError`,在 `runtime.stale` 时**追加**一句:

> 注意:当前运行时为陈旧构建(staleReason: …),本次拒绝**可能来自旧版守卫**;
> 若已在源码中修改结案规则,请**在发起方重启后重试回写**。

事故当时 `stale: true`(`reason: process` —— 构建产物比运行进程新 6 小时)。
这句提示在该任务输出里**出现了 2 次,执行器看到了**。

**但执行器没有重启 server 的能力。** 平台等于告诉它「这个拒绝可能得别人来
解决」,然后放任它重试了 3600 轮。

### 1.4 两个独立缺陷

事故暴露的是两件事,合并成本票是因为它们是同一个故事的两半:

**缺陷 A —— 回写被拒没有任何上限。**
跟项目无关、跟 stale 无关。守卫在任何三方编制的群都会触发;载荷形状写错
就会转。stale 只是让它**注定**无解,没有 stale 时它**可能**有解 ——
**但两种情况下都没有上限。**

**缺陷 B —— stale 提示会污染所有项目。**
`stale` 是**全局进程状态**。`runtime-status.ts:183` 的 `resolveScanRoots()`
从模块自身位置自动解析,**只扫平台自己的源码树**;但追加提示时**不分项目**。

后果:平台一旦被重建而没重启 —— 不管为了什么原因 —— **所有项目**的执行器在
任何守卫拒绝时都会收到「请发起方重启」。它们的项目跟平台源码毫无关系,
却被指向一个**完全错误的排查方向**。这比不给提示更糟。

### 1.5 为什么 stall 检测没救下来

平台有 30 分钟无输出的 stall 告警。**它一直在输出** —— 在忙着失败。

**「有输出」≠「有进展」。** 这是本票不打算彻底解决的问题(判据难定,
容易误杀长跑任务),但缺陷 A 的计数兜底能覆盖这个具体形态。

## 2. 改动范围

| 文件 | 改什么 |
|---|---|
| `packages/backend/server/src/routes/group/tasks.ts` | 回写被拒计数 + 超限终止;stale 提示按项目归属决定是否追加 |
| 可能的状态/存储 | 计数的落点(见 R1 的口径要求) |
| 对应测试 | 新增用例 |

**不改**:守卫本身的判定规则(`shouldWalkL3` / `summaryHasReviewRequest` /
`reviewRequestLiteFlag` 逐字不动);任何业务语义;stall 检测。

## 3. 详细改动

### R1. 回写被拒计数,超限即终止(缺陷 A)

同一任务的回写**连续被拒**达到阈值后,平台**主动把任务判终态**,不再让调用方
继续试。

口径要求:

- **按任务计数**,不是全局;
- **连续**被拒才累加 —— 一次成功的回写应清零(否则一个长期活跃的任务会被
  历史失败拖死);
- 终态的 `diffSummary` 里**必须写明**:被拒次数、**最后一次拒绝的原文**。
  没有原文,排障的人只能重走一遍执行器走过的弯路。

⚠️ **阈值要能配**,放进 `scripts/dispatch-policy.json`(与 `maxRetries` 等
同源),不要硬编码。缺省值由实现建议,票面不指定 —— 但要在汇报里说明
依据。

⚠️ **这条兜底不得依赖客户端配合**。它的全部价值在于:无论执行器是哪家、
skill 怎么写、有没有读懂提示,上限都成立。

### R2. stale 提示按项目归属决定是否追加(缺陷 B)

`coordinationCloseError` 只在**任务所属群绑定的 project_path 就是平台自身的
仓库**时,才追加那句 stale 提示。

其余项目照常返回原始拒绝消息,**不提重启**。

⚠️ 判据要写明:怎么认定「就是平台自身」。`COAGENTHUB_REPO_ROOT` 环境变量、
`runtime-status` 的 scan root、群的 `project_path` —— 选哪个、为什么,
写进汇报。**不要用字符串包含之类的脆弱判据。**

### R3. 不要顺手改守卫

排查中很容易觉得「守卫要求的载荷形状不够明确,不如把 schema 写进错误消息」。
**那是对的方向,但不在本票。** 本票只做兜底与止损;改善错误消息的可操作性
另立票(理由:那需要设计 schema 的对外表达,与本票的两条是不同量级的决策)。

## 4. 验收标准

1. 构造连续被拒场景,达到阈值后任务转终态;`diffSummary` 含被拒次数与
   **最后一次拒绝原文**。
2. **一次成功回写清零计数**:被拒 N-1 次 → 成功一次 → 再被拒,不应立即触顶。
3. 阈值可经 `dispatch-policy.json` 配置;配置缺失时用缺省值且**不报错**
   (与既有 fail-safe 口径一致)。
4. **stale 提示的项目归属**:
   - 群绑定路径 = 平台仓库 + `stale:true` → 追加提示;
   - 群绑定路径 = 其它项目 + `stale:true` → **不追加**,消息与非 stale 时逐字一致。
   ⚠️ 两个方向都要有用例,只测一半不算。
5. 守卫判定规则逐字未改:`shouldWalkL3` / `summaryHasReviewRequest` /
   `reviewRequestLiteFlag` 的 `git diff` 为空。
6. 既有测试不新增失败;受影响文件前后对照用
   `node scripts/test-baseline.mjs packages/backend/server <文件...>` 取。
7. `npx tsc --noEmit -p tsconfig.json` 通过。

## 5. 不涉及的改动

- **不改守卫的判定规则**(§3 R3)。
- **不改 stall 检测**(§1.5:判据难定,另立票)。
- 不改重试/冷却/并发的任何既有行为。
- 不试图「让错误消息自带 schema」—— 方向对,但另立票。

## 6. 工作文件的去向

沿用上一张票的约束:临时脚本、中间产物、生成器**一律放 `.scratch/`**;
交付时 `git status --porcelain` 除本票改动与用户长期未提交的两个文件外为空。
**计划文件 `plans/<name>.md` 属于交付物,要纳入提交** —— 前三张票都留成了
未跟踪,本票明确列为验收项。

## 7. 兼容性

R1 新增终态路径:原本会无限重试的任务现在会被判失败。这是**有意的行为
变更** —— 它把「无限烧额度」换成「明确失败 + 可读原因」。需在汇报里说明
是否有既有调用方依赖「回写可以一直重试」(预计无)。
