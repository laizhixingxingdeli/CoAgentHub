# Spec: 平台核实执行器的声称,而不是照单全收

> **状态**: Landed — L2 + L3 均通过(2026-08-23)

## 背景

平台的核心价值主张是**让用户看懂 agent 之间在干什么**。
但用户现在看到的,是 agent **声称**在干什么——这两件事之间隔着的东西,
正是平台存在的理由。

现状:执行器汇报的提交 hash、测试结果、token 消耗,全部由 `parseTaskReport`
从 stdout 解析成 `diffSummary` 存下,**平台不做任何核实**。

全仓唯一一处 `git rev-parse` 在 `lib/executor-runner.ts:320`,
用途是回滚前验 checkpoint 存不存在——**与执行器汇报无关**。

### 实证

执行器汇报模板里的 `提交 0123456789ab` 是**测试桩常量**,它出现在过真实任务的
汇报里,平台照单全收当作真实 commit 存进 `diffSummary.hash`。

## 判断原则

**只核实平台有独立信息源的事。** 平台有 `projectPath`、有 checkpoint ref、
有任务的时间窗——这些是它自己掌握的事实,可以拿来对账。
至于「代码写得好不好」「测试覆盖够不够」,平台没有独立信息源,**不在本票范围**
(那是 L1/L2/L3 三层检视的职责,不是平台的)。

---

## 要求

### R1. 核实 commit hash 真实存在

任务完成、`diffSummary.hash` 非空时:

- 在该任务实际执行的仓库(`resolveTaskRepo` 的结果,与 spawn 时的 cwd 一致)里
  验证该 hash 存在(`git cat-file -e <hash>^{commit}` 或等价手段)
- **不存在 → 不要静默接受**。具体处置自行判断并**在汇报里说明**,
  可选方向:在 `diffSummary` 标记一个核实结果字段、或降级为「汇报存疑」状态
- ⚠️ **不要因为核实失败就把任务判 failed**——代码可能真的写好了只是汇报写错 hash,
  把成功任务打成失败是更大的伤害。核实结果是**附加信息**,不是裁决

### R2. 核实 commit 落在任务时间窗内

hash 存在还不够——它可能是任务开始前就有的旧 commit(执行器复述了 HEAD)。

- 取该 commit 的提交时间,与任务的执行窗口比对
  (窗口起点用 `attempts[]` 第一条的 `startedAt`,那是首次 spawn 时刻)
- 落在窗口外 → 与 R1 同样处置(标记,不裁决)

### R3. 核实结果必须可见

核实做了却不让人看见,等于没做。

- 核实结果写进 `diffSummary`(字段名自行设计)
- **本票不改前端**——前端展示是下游独立票。但字段设计要考虑到前端会读它,
  形状清晰、语义自解释

### R4. 核实失败不能拖垮完成路径

- 核实是**尽力而为**:仓库不可达、非 git 仓库、git 命令失败 → 跳过核实,
  不写核实字段,**绝不抛错影响任务落终态**
- 核实耗时要有上限(git 命令本身很快,但要防 hang)
- a2a 执行器(远端设备)本地没有对应仓库,**跳过核实**,不要报错

---

## 验收标准

- [ ] `diffSummary.hash` 非空时会核实 commit 是否存在于任务实际仓库
- [ ] 核实 commit 时间是否落在任务执行窗口内
- [ ] 核实结果写进 `diffSummary`,字段语义清晰
- [ ] **核实失败/不通过绝不把任务判 failed**,只标记
- [ ] 仓库不可达 / 非 git / git 失败 / a2a 任务 → 跳过核实,不抛错,任务照常落终态
- [ ] 核实有超时保护
- [ ] 新增测试覆盖:hash 存在且在窗口内、hash 不存在、hash 是窗口外的旧 commit、
      仓库不可达跳过、a2a 跳过
- [ ] `pnpm --filter server test` 全绿(先跑一次确认基线,不得减少)

## 不涉及

- **不改**前端(展示是下游独立票)
- **不核实**测试结果与 token 数字(平台没有独立信息源;真要核实测试就得平台自己跑,
  那是另一个数量级的议题,不在本票)
- **不做**代码质量判断(那是三层检视的职责)
- **不改** `parseTaskReport` 的解析规则
- 不引入新依赖

## 执行环境提示

- 本仓是 **pnpm** 项目
- 后端以 `pnpm --filter server start`(无 watch)运行中:改完需手动 build + restart
- 沙箱执行器注意:需监听本地端口的测试会报 `listen EPERM`;
  另外**沙箱内 git 写操作受限**,但本票只做只读 git 查询,不受影响

## v1.1 补充:核实只覆盖了一条路径(2026-08-23)

`6cfc84e` 的实现**只在 CLI 完成路径核实**。协调者 L2 发现,检视者复核确认:

```
verifyCommitClaim 唯一调用点:  lib/executor-task/queue.ts:1293
                               且被 `if (!isA2a)` 包住
PATCH 路径 routes/group/tasks.ts:349:  只做 review_request 归一化,
                                       diffSummary.hash 原样落库,零核实
```

**两条路径漏网**:

1. **detached 任务的 PATCH** —— 协调者按 §3.17.4 回写终态走的正是这条。
   它自己汇报的 commit hash 从不被核实。
2. **a2a 执行器** —— `if (!isA2a)` 直接跳过。

### 追加要求

- 核实**不得只挂在 CLI 完成路径上**。任何写入 `diffSummary.hash` 的入口
  (CLI 完成 / PATCH / a2a 完成)都应经过同一套核实
- ⚠️ **a2a 执行器在本地没有对应仓库**——原 spec R4 已写明此时**跳过核实、不报错**。
  跳过与"不核实"的区别在于:跳过要留下"未核实"的痕迹,而不是让 hash 看起来
  像是已核实过的
- PATCH 路径核实失败时**同样只标记不裁决**(原 spec R1 的约束不变:
  绝不因核实失败把任务判 failed)
- 核实逻辑**复用 `claim-verification.ts`,不要写第二份**

### 追加验收标准

- [ ] detached 任务 PATCH 提交 `diffSummary.hash` 时会核实
- [ ] a2a 完成路径要么核实、要么留下明确的「未核实」标记,不是静默跳过
- [ ] 三条入口共用同一套核实实现,无重复代码
- [ ] PATCH 路径核实不通过时任务**仍照常终态**,只标记
- [ ] 新增测试覆盖:PATCH 带真实 hash、PATCH 带不存在的 hash、a2a 路径标记
