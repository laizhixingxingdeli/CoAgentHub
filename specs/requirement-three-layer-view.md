# Spec: 需求详情要展示 L3→L2→L1 完整链条,而不只是执行者那一层

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-23
> **前置已满足**: `task.parentTaskId`(`6cfc84e`)已落地并在填充

## 现状(浏览器实测)

点开需求「修复建群接口的两个静默缺口」,详情里**只有一层**:

```
修复建群接口的两个静默缺口
└─ AtomCode 执行器 · 汇报 / 测试 / 遗留 / Token 92 / 耗时 16m 20s
```

L2(协调者的功能验收)、L3(检视者的架构检视)**都不在里面**。

而左栏平铺着十几行 **「协调请求(检视者 → 协调者)」** ——
它们本身不是需求,**是某个需求的 L2 层**,却被当成独立需求各占一行。

结果是:平台的核心卖点「让用户看懂 agent 之间在干什么」只兑现了三分之一。
用户看到执行者说了什么,**看不到有没有人验过、验出了什么**。

## 根因

需求聚合(`group-tasks-by-spec.ts`)按 `specRef` 分组,一个 task = 阶梯一步。
但三层结构里,同一件事对应**两条任务**:

| 层 | 载体 | 现状 |
|---|---|---|
| L3 检视者 | `review_result` 群消息 + `spec_published` 公告 | 不在详情里 |
| L2 协调者 | 那条 detached 协调任务(`diffSummary.review_request`) | 左栏单独成行 |
| L1 执行者 | 执行任务(`diffSummary` 五段 + 自检) | 详情里只有这个 |

**`parentTaskId` 已经把 L1 与 L2 连起来了**(实测:执行任务的父正是那条协调任务),
只是前端还没用这条边。

---

## 要求

### R1. 需求 = 一条完整的三层链,不是一个 task

- 聚合时用 `parentTaskId` 把执行任务归到它的协调任务之下
- **协调任务不再单独成行**——它是某个需求的 L2 层
- 同一条协调任务下可能有多个执行任务(拆票、打回重做、收尾),**都归在同一条需求里**
- ⚠️ **历史数据 `parentTaskId` 为 null**(27 条里 23 条)。这些任务**保持现状各自成行**,
  不要为了好看去猜父子关系——猜错比不猜更糟

### R2. 详情按 L3 → L2 → L1 分层呈现

层级顺序自行判断(自上而下或自下而上皆可),但**必须让人看出这是三道关卡**,
而不是一串平铺的卡片。每层内容:

| 层 | 数据来源 |
|---|---|
| **L3** | 群消息里的 `review_result` 载荷(`verdict` / `findings` / `note`);另有 `spec_published` 可作为该需求的规范锚点 |
| **L2** | 协调任务的 `diffSummary.review_request`(含 L2 结论文本);任务状态即 L2 是否完成 |
| **L1** | 执行任务的 `diffSummary`(`summary`/`tests`/`todo`/`hash`/`tokenUsage`/`claimVerification`)与耗时 |

- **每层的"通过/未通过"必须一眼可见**。L2 打回、L3 findings 这些是最该被看到的信息
- 长内容沿用现有的折叠 + 展开变色规则(`timeline-readability` 已实现,不要另起一套)

### R3. 缺层要显式,不能装作没有

三层不是每次都齐:两层模式没有 L3;L2 可能还没做;L3 可能在等。

- 缺失的层**显式呈现为「未开始 / 进行中 / 不适用」**,不要直接不画
- **两层模式下 L3 显示为「不适用」**,判据按 spec v3.9 §3.14.5:
  **reviewer 与 coordinator 同时在场 = 三层**,否则两层。
  ⚠️ 不要用 v3.8 的旧判据(「有无 reviewer」),那条已被修订
- 不存模式字段、不加配置项,由成员构成实时推导

### R4. 与既有实现的关系

- 阶梯(`RequirementStepper`)已有 L3 虚拟节点(`timeline-readability` v1.1)。
  本票让详情区与阶梯**表达同一件事**,不要出现阶梯说三步、详情说一步
- `claimVerification`(`0630cba`)的核实结果应在 L1 层可见——
  「执行者声称的 commit 有没有被核实过」正是用户该看到的
- **不要回退**任何已落地的票:`timeline-readability`、`live-output-in-timeline`、
  `task-token-and-duration`、`task-title-readability` 的成果都要保留

## 验收标准

- [ ] 左栏**不再**把「协调请求」单独列为需求
- [ ] 执行任务通过 `parentTaskId` 归入其协调任务所属的需求
- [ ] 同一协调任务下的多个执行任务归在同一条需求
- [ ] 历史 `parentTaskId` 为 null 的任务保持各自成行,**未猜测父子关系**
- [ ] 详情区分 L3 / L2 / L1 三层,可看出是三道关卡
- [ ] 每层的通过/未通过一眼可见
- [ ] L3 读 `review_result` 载荷;L2 读协调任务的 `review_request`;L1 读执行任务 `diffSummary`
- [ ] 缺层显式呈现,不静默省略
- [ ] 两层模式下 L3 显示「不适用」,判据为**两个角色同时在场**,非旧判据
- [ ] 未存模式字段、未加配置项
- [ ] `claimVerification` 在 L1 层可见
- [ ] 阶梯与详情表达一致
- [ ] 既有票的成果未被回退
- [ ] 新增测试覆盖:三层齐全、缺 L3、缺 L2、历史无 parent 的任务、多执行任务归并
- [ ] `pnpm --filter @laizhixingxingdeli/web test` 全绿,用例数不减(当前 247)
- [ ] `pnpm --filter @laizhixingxingdeli/web build` 通过

## 不涉及

- **不改**后端(`parentTaskId`、`review_request`、`review_result` 都是现成数据)
- **不做**历史数据回填父子关系
- **不改**需求按 specRef 分组的既有逻辑——本票是在其上**再加一层父子归并**
- 不引入新依赖
