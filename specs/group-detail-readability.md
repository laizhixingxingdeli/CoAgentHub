## 背景

平台的核心价值是**让用户看懂 agent 之间在干什么**。当前群详情页做不到这一点：
左栏看不出任务是什么，中间信息过载，右栏还有一份完全冗余的重复渲染。

三处问题均为实测截图确认（群 `01a02a4b-42a2-741f-95d9-2e17386a9655`）。

---

## 问题一：左栏任务名是 spec 文件名，用户看不懂

### 现状

左栏只显示 `mcp-contract-defects` —— 那是 **specRef 的文件名**（`group-tasks-by-spec.ts`
的 `label` 取自 `specRef` 去扩展名）。用户看到它不知道这个任务在修什么。

### 数据里其实有可用的标题

`task.brief` 的**第一行就是人写的任务名**：

```
# 任务:修 MCP 契约两缺陷      ← 第一行
                              ← 空行
## 关联规范                    ← 后续是结构化正文
- specRef: `specs/mcp-contract-defects.md`
...
```

取第一行、去掉开头的 `#` 与空白，就是「修 MCP 契约两缺陷」——正是用户需要看到的。

### 要求

- 左栏每行的标题优先取 `brief` 首行（去掉 markdown 标题标记）
- `brief` 为空或首行不像标题时，回落到现有的 specRef 文件名
- 标题过长时截断，但**保证前半句可读**（不要在第 3 个字就截断）

## 问题二：中间详情信息过载，任务名被包在气泡里

### 现状（截图确认）

- 顶部 `mcp-contract-defects` 出现**两次**（列表标题 + 详情标题），
  中间还夹着 `executor`、`步骤 1` 这类内部标识
- **任务名被塞进消息气泡**：
  `🚀 [atomcode] 开始执行:# 任务:修 MCP 契约两缺陷 ## 关联规范 - specRef: spe`
  —— 任务名、markdown 标记、specRef 糊成一条并被截断
- 执行器汇报是一整段未分段的文字墙（几百字连续排布，无视觉层次）

### 要求

- **任务名不得包在气泡里**：它是这条需求的标题，应作为标题呈现，
  与「谁在什么时候说了什么」的消息卡片分开
- 移除冗余：同一个名字不重复显示两遍；`executor`、`步骤 1` 这类
  内部标识对用户无意义，**不要直接暴露**（要么去掉，要么转成人话）
- 执行器汇报本身是结构化的（`diffSummary` 有 `summary`/`tests`/`hash`/`todo`/`tokenUsage`
  五个字段），**按字段分区呈现**，不要把原始文本整段倒出来
- **长汇报默认截断，点击展开**；展开部分的文字**用与正文不同的颜色**
  （让人一眼分得清「摘要」与「展开的细节」，而不是一片同色文字墙）
### 状态不单独成条，挂在触发它的真实消息上

平台会自动生成 `contentType: "task_status"` 的消息（「🚀 开始执行…」「✅ 任务完成…」），
它们把任务书原样复述一遍，而任务名已在标题、状态已在标题旁 —— 纯重复。

**要求**：

- **不为 `task_status` 单独渲染消息卡片**
- 状态改为**标注在触发该任务的那条真实消息上**。锚点是现成的：
  `task.messageId` 指向触发消息（schema 里是 `notNull().unique()`，一一对应），
  反查即可把状态挂回去
- 具体呈现方式自行设计（角标、状态点、行内标签皆可），
  但**必须能看出「这条消息触发的任务，现在是什么状态」**

### 隐藏 skill 安装引导

成员入群时平台自动发的「请先安装 coagenthub-xxx skill」是**系统提示，不是沟通内容**，
当前混在时间线里占位置（实测一个群里就有三条）。

**要求**：不在需求时间线中显示。是否在别处保留（如折叠区）自行判断。

### 判断原则

用户想知道的是：**谁、在做什么、结果如何**。
不想知道的是：内部 key、步骤编号、markdown 源码、specHash 全文。

## 问题三：右栏「任务」tab 是完全冗余的重复渲染

### 现状（截图确认）

右栏切到「任务」tab 后，把主区那套需求两栏**原封不动又渲染了一遍**：
同样的需求列表、同样的阶梯指示器、同样的时间线，挤在约 160px 宽的栏里，
文字被压成**一列一个字**，完全不可读。

### 根因

早前的重构把需求两栏从右栏 tab 提升为主区内容，但**右栏的 tab 没有撤掉**，
于是同一份内容渲染了两处。

### 要求

- 移除右栏的「任务」tab（主区已经承载这份内容）
- 其余 tab（成员与分工 / 消息 / 项目）保留
- 确认移除后没有功能丢失 —— 若「任务」tab 里有主区没有的能力，
  **在汇报里指出**，不要静默丢掉

## 验收标准

- [ ] 左栏显示人可读的任务名（取自 `brief` 首行），无 `brief` 时回落 specRef
- [ ] 中间的任务名作为标题呈现，**不在消息气泡内**
- [ ] 同一名称不重复显示；`executor`/`步骤 N` 等内部标识不直接暴露
- [ ] 执行器汇报按 `diffSummary` 的字段分区呈现，不是整段文字墙
- [ ] 长汇报默认截断、可点击展开，展开部分文字颜色与正文不同
- [ ] `task_status` 消息不单独成条；状态标注在 `task.messageId` 对应的真实消息上
- [ ] skill 安装引导不出现在需求时间线中
- [ ] 右栏无「任务」tab；其余 tab 正常
- [ ] 移除右栏 tab 后无功能丢失（或已在汇报中说明）
- [ ] `pnpm --filter @laizhixingxingdeli/web build` 通过
- [ ] `pnpm --filter @laizhixingxingdeli/web test` 全绿（先跑一次确认基线，不得减少）

## 不涉及

- **不改**后端、不加接口（`brief` 与 `diffSummary` 都是现成数据）
- **不做**整页三栏重构（那是更大的独立议题）
- **不改**需求聚合逻辑（`groupTasksBySpec` 按 specRef 分组是对的）
- 不引入新依赖
