# Spec: 结案守卫要求等待,协调者规则禁止等待 —— detached 协调任务无法结案

> **状态**: Landed — 2026-09-07(修复 `7159a525`;L3 已 pass)
>
> 落地要点:结案守卫拒绝时登记续跑,正常等待不再被判 failed
> **相关**: `skills/coordinator/SKILL.md` §3.4「派发成功后退出本轮、不轮询等待」

## 1. 现象(2026-09-03 实证)

协调任务 `01a067f6-37eb` 的 `diffSummary`:

```json
{"l2": {"verdict": "retry_dispatched", "retries": 3,
        "guard": "stale build rejected detached close while child queued"},
 "error": "已派发最终重试子任务 01a067f7-8adf…,但因旧构建守卫拒绝回写:
           存在非终态执行子任务 01a067f7-8ae9 (queued)。不得轮询等待。"}
```

协调者派完重试后要 PATCH 结案,**守卫以「尚有子任务非终态」拒绝回写**;
而 coordinator skill 明文要求「派发成功后结束本轮 CLI 调用、不轮询等待」。

**两条规则互斥。** 协调者唯一能做的就是退出;退出后没有任何人回来结案,
根任务 `01a067e3` 最终被孤儿回收判 `failed`(`executor pid no longer exists`)。

## 2. 危害(v1.1 更正)

> ⚠️ v1.0 写的是「退出后没有任何人回来结案,净产出为零」。**那是错的** ——
> 只观察了 14 分钟就下了结论。补查完整时间线后更正如下,危害仍在,但不是那两条。

完整时间线:

```
15:29:01  01a067e3 根协调任务 created
15:49:44  01a067f6 created → 15:51:53 failed(守卫拒绝结案)
15:55:29  01a067fb created,queued
15:56:03  01a067e3 被孤儿回收判 failed
15:57~16:09  仍 queued,群内零执行器进程、执行方可用、无 running 占工作树
20:57:20  01a067fb 被拾起并跑完,给出完整 L2 结论(三次重试上限,交回 reviewer)
```

链条**没有断**,它最终得出的结论是「执行器三次重试仍未达标」。
零提交是执行器的问题,不是本缺陷造成的。

**真实危害是两条:**

1. **根协调任务被误判 `failed`。** `01a067e3` 因守卫拒绝而**正常退出**,
   却被孤儿回收判 `failed`(`executor pid no longer exists`)。
   它没有失败,它是在等。
2. **拒绝不可归因、等待不可见。** 从 15:55 到 20:57 约 **5 小时**,
   界面上只有一个 `queued`,与「马上会跑」无法区分;
   守卫拒绝的原因只存在于 `error` 的自由文本里,靠人读才看得懂。

本轮 L2 本身是**对的**,它独立识别出了检视者判的两条问题
(`staged-only/no independent commit`、`Pi parser still emitted empty report`),
并按重试上限交回 reviewer。**不要把本票理解为「L2 失灵」。**

## 3. 根因辨析(不要修错地方)

守卫本身是对的:子任务没终态就结案,会把未完成的工作记成已完成。
skill 的「不轮询」也是对的:detached 设计的全部意义就是协调进程不驻留。

**错的是二者之间缺少交接机制。** 平台已经有「续跑任务」
(`platform.resumeOf` / `resumeForChild`)在子任务终态时把协调者重新拉起 ——
这条路径本该覆盖本场景,但它没有在「协调者因守卫无法结案而退出」时被触发。

## 4. 要做的

**R1 守卫拒绝结案时,必须留下显式的续跑约定。** 协调者 PATCH 结案被守卫拒绝时,
平台须为其登记一次待续跑(等价于 `resumeOf` 机制)。
⚠️ v1.1:本条的目的是**补齐显式交接与可见性**,不是「修一条断掉的链」——
链最终会走通,但走通与否目前不可预期、不可观察。

**R2 协调者退出不得被判为失败。** 因守卫拒绝而正常退出的协调任务,不得被孤儿
回收判 `failed`;它应保持等待续跑的状态,直到子任务终态触发续跑。

**R3 守卫的拒绝要可归因。** 拒绝时须在 `diffSummary` 记录被哪个子任务挡住
(id + 当时状态),以及是否已登记续跑。本次靠人读 `error` 自由文本才看懂。

## 5. 硬验收

真实端到端,不接受只有单测:

1. 起一个协调任务,让它派发子任务后立即尝试结案(子任务仍 queued/running)→
   断言 (a) 结案被拒 (b) **已登记续跑** (c) 协调任务**不落 `failed`**。
   第 (c) 条是本票的核心 —— 正常等待不得被记成失败。
2. 子任务落终态后 → 断言协调者被重新拉起,并**完成结案**(根任务落 done 且带 `l2`)。
3. 等待期间任务 API 须能把「因守卫等待续跑」与「普通排队」区分开
   (v1.1 新增,替换原第 3 条「零人工干预」—— 那条的判据在本次事故里
   其实是满足的,不构成验收)。

## 6. 不涉及

- 不放松守卫本身(子任务非终态仍不得结案)。
- 不改「派发后退出、不轮询」的 skill 规则。
- 不改孤儿回收对**真正**失联进程的处置。
