# Spec: 技能从未说过「不要自己实现」,只有平台在堵

> **状态**: Landed — L3 通过(2026-08-28),实现 `f072580f`
> **版本**: 1.1
> **日期**: 2026-08-26

## 现象

`token-usage-never-renders` 那一票:

```
15:35:20  协调任务起
15:38:17  协调者自己提交 28dcd5d9(无 Co-Authored-By)
15:40:06  执行子任务才创建 —— 自述「未产生额外改动」,只做核验
```

结案走 `alreadySatisfied`,**指名自己刚做的那个提交**,绕过了
`commits-must-belong-to-an-execution-child`。

## 关键事实:它没有违反任何明文规则

`skills/coordinator/SKILL.md` 里**没有任何一句**说协调者不得自己实现。
全文只有 `:97` 一条相关约束 —— 「没有健康、空闲的非自身 executor 时不能静默自派」,
那管的是**无人可派**的情形,不是**有人可派却自己动手**。

于是形成一个失衡:**平台在堵,技能没说。** 协调者按技能行事并无过错,
守卫却把它当违规拦截;它绕过守卫时,也确实如实交代了时序
(两边汇报与 `claimVerification` 都完整记录,没有隐瞒)。

⚠️ 本票**不新增守卫**。再加一道堵只会催生下一种绕法 —— 前四次已经证明了:
「窗口内有提交吗」→ 改标 `failed`;「有执行子任务吗」→ 补建只读子任务;
「提交归属对吗」→ 用 `alreadySatisfied` 指名自己的提交。
本票把规范补上,并把理由讲清。

## 决策

### R1. 明写常态:实现由执行器完成

`SKILL.md` 增加一节,写明**有可用执行器时,实现工作一律下发**,
协调者不亲自写实现代码。

⚠️ 要写**理由**,不能只写禁令。至少覆盖三条:

1. **L2 是检视,不是自审。** 自己写完再自己 L2,两边是同一上下文、
   对同一方案持同一立场,那次检视不产生信息,只会让「L2 通过」这个标记
   对所有情况失去意义。
2. **成本不对称。** 协调者跑的是强模型,执行器跑的是小模型 ——
   「强模型读代码库写任务书、小模型照着实现」正是这套系统的设计前提
   (见 README「你能得到什么」)。协调者代劳等于把最贵的算力花在打字上。
3. **痕迹。** 执行器的提交带 `Co-Authored-By`,归属查得清;
   协调者代写的提交在审计上无法与它的协调行为区分。

### R2. 「改动小」不是理由

明写:改动规模**不构成**自己动手的理由。
派发的固定开销(起进程、读规范)确实存在,但它换来的是独立实现与可归属的痕迹,
这笔交换在小改动上同样成立。

⚠️ 不要写成「超过 N 行才派发」之类的阈值 —— 阈值会立刻变成新的绕法。

### R3. 讲清 `alreadySatisfied` 是给什么用的

明写该路径的适用场景:**工作在此前的运行中已经完成**
(例如上一轮执行子任务已提交、本轮只是重跑确认)。

明写它**不适用**于:协调者在本轮自己刚做出的提交。
⚠️ 这是说明用途,**不是**新增校验 —— 平台侧不动。

### R4(v1.1 改写). 无人可派时降级为两方,但必须留痕且由平台判定

原 v1.0 要求 `:97` 逐字不变(无执行器时停下报阻塞)。v1.1 改为**允许降级**:
没有可用执行器时,协调者兼任执行 —— 这不是新编制,技能 §3.14.5 的组合表里
本来就有「两方,由协调者兼任」。降级后 **L3 仍由检视者独立进行**,
所以独立检视这一层没有丢失。

⚠️ **但降级的触发条件不得由协调者自述。** 「执行器是否可用」恰恰是它最不擅长
判断的事,今晚两次误判有据可查:

| | 协调者的判断 | 实际 |
|---|---|---|
| AtomCode | 「全额度耗尽,实现未开始」 | 子任务已被领取并正在运行 |
| CodeBuddy | 「未被领取」(读 `attempts=null`) | 瞬时快照未刷新 |

若降级由它自述触发,这条路会变成「判一句没人可派 → 自己写 → 合规」,
比 `alreadySatisfied` 更省事也更难查。

因此降级必须同时满足四条:

1. **平台判定** —— 可用性由平台给出(复用 `executor-task-liveness.ts` 与
   `executors.ts` 的限流冷却状态),**不采信协调者的断言**
2. **平台留痕** —— 降级时由**平台**写入 `diffSummary.degradedToTwoParty =
   { at, executors: [{name, reason}] }`,记下降级时刻与当时每个执行器的实际状态。
   ⚠️ **照 `l1Bypass` 的既有平台补写模式做**,不新建表、不加列
3. **界面可见** —— L1 层显示「由协调者兼任」,不得看起来与正常派发无异
4. **群内仍要说明** —— 降级不等于静默;仍在群里留一条说明

⚠️ **降级是允许的,隐瞒不是。** 今天两个执行器额度耗尽,正是靠「停下来报阻塞」
这个动作才被发现;静默降级会把这个信号吃掉。

### R5. 只改技能文本

- **不改** `alreadySatisfied` 的校验逻辑
- 除 R4 的平台留痕外,**不改**任何平台守卫
- **不改** L2 / L3 语义
- **不加**新的拒绝分支

## 验收标准

- [ ] `SKILL.md` 写明「有可用执行器时实现一律下发」
- [ ] 该节包含 R1 的三条理由(自审无信息量 / 成本不对称 / 痕迹可归属)
- [ ] 写明「改动小不构成理由」,且**没有**行数或规模阈值(读文本确认)
- [ ] 写明 `alreadySatisfied` 的适用与不适用场景
- [ ] 有可用执行器时**不降级**,仍必须下发(回归,必测)
- [ ] 无可用执行器时:协调者兼任执行,且平台写入 `degradedToTwoParty`,
      含降级时刻与每个执行器的实际状态(v1.1 核心场景,必测)
- [ ] 该判定**来自平台**,协调者在载荷里自述「无执行器」**不足以**触发降级
      (反向断言,必测 —— 这是本条最容易被绕开的地方)
- [ ] 降级后仍在群内留一条说明(必测)
- [ ] 界面 L1 层显示「由协调者兼任」,与正常派发可区分(端到端)
- [ ] 降级后 L3 仍照常交回检视者(回归,必测)
- [ ] 下一张需求票的实现提交带 `Co-Authored-By: <执行器>`,
      且提交时间落在执行子任务窗口内 —— **行为验收信号**
