# Spec: 建群接口的两个缺口

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-23
> **协作模式**: 三层

## 背景

搭建三层模式验证环境时连续踩到两个建群相关的问题，都不报错、都静默生效，
因此发现得很晚。两项均已核实代码，不是设想。

---

## 缺口一：`POST /groups` 静默忽略 `projectPath`

### 现状

`routes/group/groups.ts:37` 的建群入参 schema 只有 `title`：

```ts
z.object({ title: z.string().min(1) })
```

而 `PATCH /groups/:id`（同文件 190 行）有完整的 `projectPath` 支持，
含校验逻辑：空串视作清空绑定，非空值必须是**存在的绝对目录路径**。

### 实测后果

建群时传 `{"title": "...", "projectPath": "/Users/apple/Projects/xxx"}`，
接口返回 200、群创建成功，但 **`projectPath` 是 `null`**。
连建三个群都没绑上项目路径，直到列出群列表才发现。

没有报错、没有警告——zod 默认剥掉未声明字段，调用方无从察觉。

### 为什么要修

- **建群时一步绑定是自然预期**，尤其对以 API 驱动的调用方（agent、脚本）
- 群绑了 `projectPath` 才有 Matt 文档检查（`messages.ts:307`）等行为，
  没绑就静默跳过——又一处「不报错但功能没生效」
- 分两步做意味着中间存在一个「已创建但未绑定」的窗口

### 要求

- `POST /groups` 接受可选 `projectPath`
- **复用 `PATCH` 已有的校验逻辑**（绝对路径 + 目录必须存在），不要写第二份
- 校验失败时**报错**，不要静默忽略或静默置空
- 不传时行为与现状一致（`null`）

## 缺口二：建群者被自动塞成 `coordinator`，可能导致模式推导错误

### 现状

`groups.ts:53-57` 在建群事务里自动把创建者加为成员，角色写死 `coordinator`：

```ts
await tx.insert(groupMemberTable).values({
  groupId: created.id,
  participantId,
  roles: ["coordinator"],
});
```

注释说明理由是「群不能没有协调者」——这个出发点合理。

### 为什么这是问题

上游 spec v3.8 §3.14：**协作模式由成员构成推导** ——
群内有 `reviewer` 角色成员 = 三层，无 = 两层。

而检视者建群是正常场景（检视者是用户侧唯一入口，需求从它这里进来）。
此时：

1. 检视者被自动写成 `coordinator`
2. 若不手动纠正，群里**有两个 coordinator、零 reviewer**
3. **模式推导错成两层**，L3 整层静默消失

实测中我建三层群后手动 `POST members` 把自己改成 `reviewer`（幂等 upsert 覆盖了角色），
才没出错——但那是因为我知道有这回事。**换个人建群就会踩坑，而且不报错。**

### 要求

方案自行判断，**在汇报里说明选了哪个及理由**。以下是可考虑的方向：

- **A. `POST /groups` 接受创建者角色参数**，默认仍为 `coordinator`（向后兼容）
- **B. 建群后允许角色被后续 `POST members` 覆盖**（现状其实已如此，
  但**行为未文档化**，得靠试才知道）—— 若选此项，至少要在
  接口描述与 `CONTEXT.md` 里写明
- **C. 其他** —— 只要能让「检视者建群」不静默退化为两层

⚠️ **不要**取消「创建者自动入群」这个行为本身：
群不能没有成员，这个保护是对的，问题只在角色写死。

## 验收标准

### 缺口一
- [ ] `POST /groups` 传 `projectPath` 能生效（返回体与库里都是传入值）
- [ ] 校验复用 `PATCH` 的实现，不存在两份路径校验逻辑
- [ ] 传入非法路径（相对路径 / 不存在的目录）时**报错**，不是静默忽略
- [ ] 不传时仍为 `null`，既有调用方不受影响
- [ ] 新增测试覆盖：传合法路径、传非法路径、不传

### 缺口二
- [ ] 检视者建群后，不需要手动纠正即可得到正确的模式推导
      （或：行为已明确文档化，调用方知道该怎么做）
- [ ] 「创建者自动入群」的保护仍在（群不会没有成员）
- [ ] 新增测试覆盖所选方案

### 共同
- [ ] `pnpm --filter server test` 全绿（先跑一次确认基线，改完不得减少）

## 不涉及

- **不改**前端
- **不改** `PATCH /groups/:id` 的既有行为
- **不改**模式推导规则本身（由成员构成推导，这条是对的）
- 不引入新依赖

- 后端当前以 `pnpm --filter server start`（无 watch）运行中：
  **改完后端代码需手动 build + restart 才生效**，但跑测试不受影响
- 沙箱执行器注意：全量测试里有需要监听本地端口的用例会报 `listen EPERM`，
  那是环境限制不是回归 —— **全量由协调者代跑**，你只需跑定向测试与类型检查
