# Spec: 任务状态条重复任务卡片,占满时间线

> **状态**: Ready for Implementation
> **版本**: 1.1(2026-09-02 L3 后订正:§1.1 依据 + 验收 6 豁免)
> **日期**: 2026-08-30

## 1. 现象

用户在群组时间线里看到一连串状态条(2026-08-30 截图,05:26–09:11 连续 9 条):

```
✅ 任务完成 pi          05:26
✅ 任务完成 atomcode    05:36
✅ 任务完成 atomcode    05:44
✅ 任务完成 atomcode    05:56
✅ 任务完成 atomcode    06:37
✅ 任务完成 atomcode    07:36
✅ 任务完成 pi          08:28
✅ 任务完成 pi          08:57
✅ 任务完成 pi          09:11
```

它们**不带任务 id、不带提交、不带耗时**,唯一的信息是执行器 label ——
而这些在同一时间线的任务卡片上全都有,且更完整。

用户原话:「这个不要,或者放到对应的任务上」。

### 1.1 量化(群 01a03be2-4a58,153 条 `content_type='task_status'`)

| 形态 | 条数 | 卡片之外的信息量 |
|---|---|---|
| `🚀 [x] 开始执行:<任务书前几十字>` | ~46 | **零**(卡片有任务书全文;卡片出现本身即"已开始") |
| `✅ 任务完成 <label>` | 29 | **零(见下方订正)** |
| `❌ [x] 任务失败 (原因/恢复时刻)` | 4 | 有 |
| `📋 [x] 任务已排队(前面还有 N 个)` | 3 | 有(排队位次卡片没有) |
| `⚠️ L3 逾期提醒` | 1 | 有 |

**75 / 153 ≈ 49% 是纯重复**;真正携带卡片之外信息的只有 8 条。

同群 `text/plain` 正文仅 104 条 —— **状态条已超过正文成为消息主体**。

> **⚠️ 依据订正(2026-09-02,L3 后由检视者补)**
>
> 上表「`✅ 任务完成 <label>` 信息量为零」的**结论成立,但依据写错了**。
> 那些消息**不是**单行状态条 —— `renderTaskCard`(`report.ts:265`)自
> **2026-08-16**(`adb55fc7`)起产出的就是**多行卡片**(提交/测试/汇报/遗留四段),
> 早于本 spec 写作日两周。实测(2026-09-02,351 条 task_status):
> **单行 `✅` = 0 条,多行卡片 = 64 条。**
>
> 正确依据是**渲染口径**而非消息内容:`RequirementTimeline.tsx` 对 task_status
> 只渲染首行(`message.body.split("\n")[0]`),完整正文仅挂在 `title` 悬浮提示上。
> 所以在**这个视图里**它确实是零增量 —— 四段内容在同一时间线的任务卡片上已有。
>
> 取数语句(供复算):
> ```sql
> select (position(E'\n' in body)=0) as 单行, count(*)
> from group_message where group_id='<gid>' and content_type='task_status'
>   and body like '✅ 任务完成%' group by 1;
> ```
>
> ⚠️ 教训:spec 的事实断言必须实跑核对 —— 本条错误依据直接导致初版实现
> 加了 `isSingleLine` 守卫,使验收 1/5 未满足。

## 2. 根因

`lib/executor-task/notify.ts:84` 的 `postStatus` 把状态插成**普通广播消息**,
只标 `contentType: "task_status"`,**不携带任何任务引用**:

```ts
const full = await insertGroupMessage(db, {
  groupId, senderId, parentId: null,
  audience: "broadcast", audienceRef: null, body,
  contentType: STATUS_EMOJI_RE.test(body) ? "task_status" : "text/plain",
  fileRef: null,
});
```

前端 `RequirementTimeline.tsx:309`(R6)已经把它降级为轻量状态行、不占发言气泡
—— 方向是对的,但**降级解决不了"内容本身是重复"**。因为消息上没有 taskId,
前端也无法把它挂到对应卡片上,只能平铺。

## 3. 决策

**按"是否携带任务卡片之外的信息"分流,而不是按是否 `task_status` 一刀切。**

⚠️ 明确**不采纳**的两个方案,以及理由:

- **全部隐藏**:会连带丢掉排队位次、失败原因、额度恢复时刻 ——
  这三样卡片上没有,是人判断"该等还是该介入"的依据。
- **本票就给消息加 taskId 并挂到卡片上**:那是结构上更对的解法(见 §5 遗留),
  但涉及 schema + 生产端 + 消费端三处改动;而 49% 的噪音**不需要**它就能消除。
  先做能立刻见效的一半,不把小修拖成大改。

### R1 — 纯重复状态条不在需求时间线渲染

`RequirementTimeline` 对 `contentType === "task_status"` 的消息,
**不渲染**下列两类:

- 以 `✅ 任务完成` 开头的
- 以 `🚀 [<label>] 开始执行:` 开头的

其余 `task_status`(`❌` / `📋` / `⚠️`)**渲染方式逐字不变**(仍是 R6 的轻量状态行)。

⚠️ **判据用首行前缀,不做正文关键词匹配** —— 与
`live-output-hide-thinking-and-autoscroll` R1 同源纪律:
不得用"完成""开始"二字去匹配,那会误伤汇报正文里出现该词的状态条。

### R2 — 不改生产端

`postStatus` **照常发送**这两类状态,`contentType` 与正文**逐字不变**。

理由:它们仍是 WS 实时提示与消息表审计的一部分,别的消费方(其他 runtime、
未来的通知渠道)可能依赖;本票只改**这一个视图的渲染**,不改事实的产生。

⚠️ 因此本票**不减少**数据库中的消息条数,只减少屏幕上的行数。
验收要按**渲染出的行数**量,不要按消息条数量 —— 否则会得出"没改动"的错误结论。

### R3 — 不涉及

- 不改 `MessageList`(另一个视图)的状态条渲染。
- 不改 `content_type` 的取值集合与 `STATUS_EMOJI_RE`。
- 不清洗历史消息。
- 不改任务卡片自身的内容与布局。

## 4. 验收标准

1. 时间线中不再出现 `✅ 任务完成 <label>` 与 `🚀 [<label>] 开始执行:…` 两类行。必测。
2. `❌ 任务失败` / `📋 任务已排队` / `⚠️ L3 逾期提醒` **仍然渲染**,
   样式与位置**逐字不变**(回归,必测)。
3. 正文里**包含**「任务完成」「开始执行」字样但**不以该前缀开头**的
   `task_status` 消息**仍然渲染**(防误伤,必测)。
4. 数据库中的 `task_status` 消息条数**不变**(R2:生产端未改)。必测 ——
   这条防止实现者跑去改 `postStatus` 或删数据。
5. 用本群真实数据(153 条 task_status)回放:渲染行数较修复前下降,
   且下降量等于 `✅ 任务完成` 与 `🚀 开始执行` 两类的条数之和。
6. 既有 `RequirementTimeline` 测试全绿。
   ⚠️ **豁免(2026-09-02 修订)**:`RequirementTimeline.render.test.tsx` 的
   R6 用例「多行状态卡片只取首行做提示」**断言的正是验收 1 要移除的那个行为**,
   两条不可能同时满足。该用例**应随本票更新**(已更新为「多行状态卡片不再渲染」),
   不构成违反。其余 R6/R7 用例仍不得修改。
   ⚠️ 本条原文「R6 相关用例不被修改」与验收 1 冲突,是 spec 自身矛盾 ——
   初版实现因此加了 `isSingleLine` 守卫来迁就验收 6,反而使验收 1/5 落空。

## 5. 遗留(不在本票)

**结构上更对的解法是给状态消息一个任务引用**,让前端把生命周期状态挂到对应
卡片上(用户提的第二个选项)。它能同时解决:本票没覆盖的 `MessageList` 视图、
以及"状态与卡片分离"这个根问题。

不在本票做的原因见 §3。若将来 `📋 排队位次` 这类信息也希望呈现在卡片上,
再按 schema + 生产端 + 消费端一并设计。

## 6. 兼容性

- 纯前端渲染改动,无 schema 变更、无 API 变更。
- 历史消息不受影响,只是不再渲染其中两类。
