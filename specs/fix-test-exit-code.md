# Spec: `pnpm test` 退出码为 1,让所有「测试全绿」判断失真

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-23
> **优先级**: 高 —— 它污染每一票的验收信号

## 现象

```
Test Files  1 failed | 33 passed (34)
     Tests  423 passed (423)
Exit status 1
```

**423 个用例全过,但退出码是 1。** 失败的不是用例,是
`test/dispatcher-fields.test.ts` 的 `afterAll` 钩子超时——该文件 8 个用例全部通过,
挂在清理阶段。

## 为什么优先级高

执行器和协调者判断「测试全绿」时看的是命令是否成功。现在**这个信号永远是失败**:

- 执行器会以为自己弄坏了什么,可能去改无关代码
- 协调者 L2 无法用退出码判断,只能靠人读用例数
- 任何 CI / 自动化门禁都会长期红着

**一个永远红的信号等于没有信号。**

## 已知信息

- 该 `afterAll` 是既有代码,最近一次改动 `d1b57dd`,与近期任何票无关
- 它的意图(注释写明):等待队列清空 + DB 无 queued/running 任务,
  避免文件结束时残留任务写已关闭的 PGlite / 已删除的仓库,产生未处理拒绝
- 超时上限 20 秒(`Date.now() + 20_000`),vitest 默认 hook 超时更短
- 有人推测是「临时 Git 锁竞争」,**该归因未经证实**——输出里没有锁相关信息,
  只有钩子超时。**不要把这个推测当成已知事实**

---

## 要求

### R1. 先定位,再修

- 查清 `afterAll` 到底卡在哪一步(等队列?等 DB?某个 await 不返回?)
- **在汇报里写明真实原因**。定位不出来就说定位不出来,不要套用未经证实的推测

### R2. 修复后退出码必须为 0

- `pnpm --filter server test` 退出码 0
- 用例数**不得减少**(当前 423)

### R3. 不要用「关掉清理」来绕过

该 `afterAll` 存在是有理由的(见上文注释)。**不要简单删掉它或把超时调大了事**——
残留任务写已关闭的 PGlite 会变成偶发的未处理拒绝,那比现在更难查。

- 若判定该清理逻辑本身设计有问题、需要换做法,**在汇报里说明新做法为什么同样安全**
- 若确实只需调整超时,要说明为什么原值不够、新值依据是什么

### R4. 顺手确认没有别的文件有同类问题

- 跑一次全量,确认修完后**只有** `Test Files N passed`,无 failed
- 若发现其他文件也有类似的钩子问题,**列进汇报**,不要一并修(范围失控)

---

## 验收标准

- [ ] `pnpm --filter server test` **退出码为 0**
- [ ] `Test Files` 全部 passed,无 failed
- [ ] 用例数 ≥ 423
- [ ] 真实原因已在汇报中写明(或明确说明未能定位)
- [ ] 未通过删除清理逻辑 / 单纯放大超时绕过(若调整超时,依据已说明)
- [ ] 其他文件的同类问题(若有)已列出但未一并修

## 不涉及

- **不改**生产代码(除非定位结论指向生产代码的真实缺陷,此时**先写进汇报**)
- **不改**其他测试文件的用例
- 不引入新依赖

## 执行环境提示

- 本仓是 **pnpm** 项目
- 单文件复现:`pnpm --filter server exec vitest run test/dispatcher-fields.test.ts`
  —— 约 12 秒即可复现,不必跑全量
- 沙箱执行器注意:需监听本地端口的用例会报 `listen EPERM`,那是环境限制不是回归
