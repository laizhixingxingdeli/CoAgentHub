## 1. 背景与目标

### 1.1 现状证据(检视者已复核代码)

`docs/adr/0003-single-scheduler-executors.md` 写「server 是唯一调度器」,
**但实际约束比 ADR 表述更强** —— 下列状态**全部只存在于单个 Node 进程内存里**
(`packages/backend/server/src/lib/executor-task/state.ts`):

| 状态 | 行 |
|---|---|
| `groupQueues` | 25 |
| `activeRuns` | 28 |
| `executorCooldowns` | 104 |
| `cooldownTimers` | 117 |
| `liveCoordinatorProcesses` | 435 |

外加全部定时器。

**而这个约束已经被违反过**:`queue.ts` 里存在一整套 PID 启发式补偿 ——

| 函数 | 行 |
|---|---|
| `registerTaskOwnerServer` | 534(调用点 2160) |
| `ownerServerPidOf` | 562 |
| `isOwnedByLiveForeignInstance` | 683(调用点 607) |

这套东西存在的唯一理由,就是「同库可能跑着第二个 server」这件不该发生的事。

### 1.2 危害

两个 server 连同一个库时,两套内存队列各自派发、各自冷却、各自记账,
互相看不见。PID 启发式只能**事后猜**某行是不是别人的 ——
猜错的方向是重复执行或永久卡住。

**这不是理论风险**:检视者 2026-09-08 在完成事件里读到
`platform.ownerServerPid: 18548`,说明这套补偿逻辑在日常路径上就在跑。

### 1.3 目标

**启动时拿不到锁就拒绝启动**,把「不可能有第二个实例」变成事实,
而不是一句注释。这与 S3「同一事实不在多个模块独立推导」的目标一致。

## 2. 改动范围

| 文件 | 改什么 |
|---|---|
| `packages/backend/server/src/index.ts`(或实际启动入口) | 启动时取咨询锁 |
| 可能新增一个小模块存放锁的获取/释放 | 实现者定 |
| 对应测试 | 新增用例 |

**不改**:`state.ts` 的内存态结构;队列/冷却/派发逻辑;
`ownerServerPid` 那套 PID 启发式(**见 §3 R4,本票不删它**);
ADR-0003 的结论;任何 API。

## 3. 详细改动

### R1. 启动时 `pg_try_advisory_lock`

- 键取自**固定常量**(写在代码里,不走配置);
- **拿不到锁 → 拒绝启动,并给出明确错误** ——
  错误信息必须让人一眼看懂发生了什么、该怎么办
  (例如「同一 DATABASE_URL 上已有 server 在运行;先停掉它,或改用不同的库」),
  **不要只打印一个锁失败的堆栈**。

### R2. 锁必须活到进程结束

`pg_try_advisory_lock`(session 级)绑在**持有它的那条连接**上。

⚠️ **连接池是这里的陷阱**:如果锁在池里的某条连接上取,
那条连接被回收/重置时锁就没了,约束静默失效。

**必须用一条专属的、不参与池化的连接持锁**,或用其它能保证同等效果的做法。
在汇报里**明确写出你怎么保证锁不被连接池回收掉的**,这是本票的技术核心。

### R3. 释放要覆盖正常退出

进程正常退出时释放(或依赖连接断开自动释放 —— 说明你依赖哪一种)。
**进程被 kill -9 时依赖 PG 侧连接断开回收,这是可接受的**,
不必为此做额外机制。

### R4. ⚠️ 本票不删 PID 启发式

`registerTaskOwnerServer` / `ownerServerPidOf` / `isOwnedByLiveForeignInstance`
**原样保留,一行不动**。

理由:锁只保证**今后**不会有第二个实例,但库里**已经存在**由旧实例写下的
`ownerServerPid` 数据;而且删除这套逻辑要动 `queue.ts` 的分流判定,
是独立一票的工作量与风险。

本票只加约束,不做清理。**清理另票**,等这个锁在生产里跑稳之后再谈。

### R5. 测试环境不能被锁住

多个测试文件会各自起 server 实例。**锁不得让测试互相排斥。**

处置方式自选(测试环境跳过、按库名/schema 分键、按环境变量关闭……),
但必须:

- 在**代码注释**里写清楚为什么测试环境是安全的例外;
- 在**汇报**里说明你选了哪种,以及它会不会掩盖生产环境的问题。

⚠️ **不要用「测试里没人起两个 server」当理由跳过思考** ——
先跑一遍确认,再下结论。

## 4. 验收标准

**基线先用工具取**(先自行判断哪些测试文件会受影响,清单写进汇报):

```
node scripts/test-baseline.mjs packages/backend/server <你判断受影响的测试文件...>
```

1. **核心**:同一 `DATABASE_URL` 启动**第二个** server 进程 → **立即失败**并说明原因。
   给出实际的错误输出。
2. **第一个退出后第二个可正常启动**。
3. **锁不被连接池回收**(R2):构造一个能暴露该问题的用例 ——
   例如启动后跑足够多的查询把池轮换一遍,再尝试起第二个实例,**仍应失败**。
   ⚠️ 这条是本票最容易做假的地方:如果只测「起来立刻再起一个」,
   连接池回收的问题测不出来。**必须真的让池轮换过。**
4. **锁不因长事务被意外释放**:说明你怎么验证的。
5. **PID 启发式未被改动**(R4):`git show --stat` 中 `queue.ts` 无改动,
   或若有改动**逐行说明为什么不得不改**。
6. **测试不互相排斥**(R5):受影响的测试文件前后基线对照,失败数不增加。
7. `npx tsc --noEmit -p tsconfig.json` 通过。

## 5. 不涉及的改动

- **不设计 lease、属主标识与失效接管**(那是「允许多实例」方案,决策已排除)。
- **不删 PID 启发式**(R4)。
- 不改内存队列结构、冷却策略、派发逻辑。
- 不改 ADR-0003 的结论(可另票补记实施方式)。
- 不宣称第三方副作用 exactly-once(R6 原文明确排除)。

## 6. 兼容性

- 无 schema 变更,无迁移(advisory lock 不落表)。
- **行为变更(需写明)**:此前同库起第二个 server 会「跑起来但行为诡异」,
  现在会**直接拒绝启动**。
  ⚠️ 若有人的本机流程依赖「起第二个实例」(例如忘了停旧的就起新的),
  这个改动会让它显式失败 —— **这是本票的目的**,不是回归。
  但要在汇报里提醒:**升级后第一次启动前,确认没有残留的旧 server 进程**。
