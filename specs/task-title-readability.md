# Spec: 任务标题可读 —— 左栏 11 行 8 行叫「CoAgentHub Task」

> **状态**: 待验收 — 实现已落地(`b67d3e9`),**L2 与 L3 均未完成**
> **版本**: 1.0
> **日期**: 2026-08-23
> **修正**: `specs/timeline-readability.md` 问题一的实现假设有误(详见背景)

## 背景:上一份 spec 的假设是错的,不是执行器做错

`timeline-readability`(`36cb10b`)问题一要求「左栏标题优先取 `brief` 首行」。
执行器严格照做了,`deriveBriefTitle` 实现正确。

**但真实数据里 `brief` 首行是模板标题。** 浏览器实测(群 `01a029c4-b67f-...`):
左栏 11 行,**8 行显示 `CoAgentHub Task`**,完全无法区分。

写那份 spec 时我举的样本是**我手写**的任务书(`# 任务:修 MCP 契约两缺陷`),
而真实流程里任务书由协调者的 `taskBook()` 模板生成,首行恒为 `# CoAgentHub Task`。
**拿特例当了通例。**

好消息:真正的任务名就在模板的下一段——

```
# CoAgentHub Task          ← 模板标题,无信息

## Goal
按冻结规格实现 timeline 可读性：在三层模式中将需求列表与 timeline...
                           ↑ 这才是人能看懂的任务名
```

---

## 要求

### R1. 标题派生改为多级回落

按顺序取第一个可用的:

1. **`brief` 首行** —— 仅当它**不是模板标题**时(见 R2)
2. **`## Goal` / `## 目标` / `## 任务内容` 段的首句** —— 模板生成任务书的真实任务名所在
3. **`specRef` 派生名** —— `specs/timeline-readability.md` → `timeline-readability`
   (现有 `deriveLabel` 已有这段逻辑,复用)
4. 以上都拿不到 → 保持现有兜底(任务 id)

- 取到的标题过长时截断,**保证前半句可读**(不要在第 3 个字截断)——
  这条是 `timeline-readability` 的原要求,不得回退

### R2. 模板标题的识别

已知的模板标题(两处不同来源,都要认):

- `# CoAgentHub Task`(协调者 MCP `taskBook()` 生成,英文)
- `# CoAgentHub 任务`(平台 `buildTicket()` 生成,中文)

- 识别方式自行设计,但**必须是可维护的**——不要散落多处硬编码字符串,
  集中成一个可读的判定
- ⚠️ **不要用「以 `#` 开头就算模板」这种粗判**:用户手写的任务书首行
  `# 任务:修 MCP 契约两缺陷` 是**合法且优质**的标题,不能被误杀

### R3. 消除中间区标题重复

浏览器实测:详情区顶部出现同一个名字两次——

```
协调请求(检视者 → 协调者) · 控制      ← requirement-control-bar.tsx:50
协调请求(检视者 → 协调者)             ← RequirementDetailPanel 的标题
```

`timeline-readability` 问题三写了「同一个名字不重复显示两遍」,**这条没做到**
(L3 检视时只核对了代码逻辑与测试,没看渲染结果,是检视方法的疏漏,不是执行器的锅)。

- 控制条不再重复渲染需求名。它承载的是「停止/回滚」,标题已在正上方
- 具体保留什么自行判断(如只留「· 控制」这类标识,或直接去掉文字只留按钮),
  但**必须能看出这一条是控制区而不是内容区**
