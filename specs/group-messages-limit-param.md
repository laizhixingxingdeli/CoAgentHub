# Spec: `GET /groups/:id/messages` 缺 `limit`,预览拉取整群消息

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-24
> **发现于**: `sidebar-preview-all-groups`(`d66d4ff` 一带)的 L3 非阻塞发现,
>   当时未单独立票,现在补上

## 背景

`GET /groups/:id/messages` 只接受 `after`(增量拉取)与 `q`(关键词搜索),
**没有条数上限**,返回该群可见的**全部消息**,按接收时间正序。

侧栏预览(`hooks/use-unread.ts:163` 的 `seedGroupPreviews`)只需要**最后一条**
消息的正文,却要拉取全群历史来取数组末项:

```ts
const fetched = (await res.json()) as Array<{ body?: unknown }>;
const last = fetched[fetched.length - 1];
```

群消息多的群,这一次首屏拉取的载荷会随消息数线性增长。此前诊断时收件箱
(不同接口,但同一类无上限问题)曾实测返回过 331KB。

## 决策

加 `limit` 查询参数,**服务端按时间倒序取最后 N 条再翻正序返回**——不是
「正序拉全部再让前端截断」,那样载荷问题完全没解决。

## 要求

### R1. `limit` 参数

```ts
limit: z.coerce.number().int().min(1).max(200).optional()
```

- 不传 → 现状行为不变(返回全部),**保持向后兼容**,不破坏现有调用方
- 传了 → 服务端只查询并返回最新的 `limit` 条,**返回顺序仍是时间正序**
  (与不传时的顺序约定一致,调用方不需要为传参改变处理逻辑)

### R2. 与 `after` 的组合语义

`after` 是增量拉取(拿 `after` 之后的新消息),`limit` 是条数上限。两者可以
同时传:`after=X&limit=50` = 「`X` 之后最多 50 条」。**不要求这个组合当下有
实际调用方**,但实现时不能让两者互斥或互相踩踏。

### R3. `seedGroupPreviews` 改用 `limit=1`

```ts
fetch(`/api/groups/${groupId}/messages?limit=1`)
```

**只改这一处调用**,预览只需要最后一条。

### R4. 其它调用方不改

仓库里其它调用 `GET /groups/:id/messages` 的地方(消息流主视图等)
**保持不传 `limit`**,现状行为不变。本票不扩大到「所有地方都该加分页」——
那是另一个更大的话题,当前只解决预览这一个已知的过量拉取。

## 验收标准

- [ ] 不传 `limit` 时行为与改动前完全一致(回归,必测)
- [ ] 传 `limit=N` 时返回**最新的 N 条**,顺序仍是时间正序
- [ ] `limit` 超出 1–200 范围返回 400
- [ ] `after` + `limit` 组合可用,语义符合 R2
- [ ] `seedGroupPreviews` 改为 `?limit=1`,**其它调用方未被改动**
- [ ] 群消息数远大于 1 时,侧栏预览请求的响应体积明显下降(实测对比)
- [ ] 新增测试覆盖:不传行为不变 / limit 生效 / limit 越界 400 / after+limit 组合,
      四条都要有
- [ ] 后端测试全绿,贴出用例数
- [ ] 前端仅改 `seedGroupPreviews` 一处,贴出 diff 确认范围

## 不涉及

- 其它接口(收件箱等)的类似问题——本票只处理这一个已确认的实例
- 消息流主视图的分页/虚拟滚动
- 可见性过滤逻辑本身(不改)

## 执行环境提示

- 后端 `:3001`,前端 `:5173`
- 实测:找一个消息数较多的群,对比改动前后 `?limit=1` 与不传时的响应大小
