# Spec: 实时输出去掉思考行,并默认跟随最新输出滚动

> **状态**: v1.2 增补待实现(v1.0/v1.1 已 Landed,实现 `de73f0f4`)
> **版本**: 1.2
> **日期**: 2026-08-29

## 背景

`two-tier-output-summary-and-detail`(`a6ed2759`)把思考折叠成一行要旨
(`[思考 #t7] …`),缓冲从 262143 降到几千字节。但实际使用下来,
**思考行仍然占据了摘要流的大部分行数**,而用户要看的是「agent 在做什么」——
即工具调用、命令、汇报。

实测(修复前)思考占缓冲比重:

```
01a03eca  AtomCode    95.3%
01a03f23  AtomCode    89.5%
01a03f35  AtomCode    84.5%
01a03f15  CodeBuddy   64.0%
```

折叠后字节降下来了,但**行数占比仍高**,动作行被稀释。

另:前端输出容器已有滚动(`OutputDetailBlock.tsx:124`
`max-h-96 overflow-auto`),但**不会自动滚到最新**——
任务运行中新行不断追加,用户每次都要手动往下拖。

## 要做的

### R1 — 摘要流默认不显示思考行

`kind === "thinking"` 的条目**不进摘要流**。

⚠️ **明细仍要落盘**(`detail-store` 照常写入),仅从摘要流中隐去 ——
思考是排障的重要线索(本轮多次靠它定位问题),不得丢弃。

⚠️ 判据用**已解析出的 `kind`**,不得用文本匹配「思考」二字 ——
后者会误伤汇报正文里出现该词的行。

### R2 — 提供取回思考的途径

⚠️ 隐去不等于不可得。已有的展开 API
(`GET /groups/:gid/tasks/:tid/output?detail=1`)必须仍能取到思考条目全文。
⚠️ 不得因 R1 而在明细中跳过 thinking 的落盘。

### R3 — 前端:展开后默认定位到最新

输出容器展开时,**默认滚动到底部**(最新输出处),而不是停在顶部。

### R4 — 前端:运行中跟随滚动

任务运行中有新行追加时,若用户**当前已在底部**,则自动跟随滚动到最新。

⚠️ **用户手动向上滚动查看历史时,不得强制拉回底部** ——
这是本条的成败关键。判据:仅当滚动位置在底部附近(建议阈值 ≤ 32px)才跟随。

### R5 — ⚠️ 不得回归既有能力

- 带 `#id` 的行仍可点击展开(`frontend-expand-output-detail` 全部要求)
- 已展开的条目不因新行到达而收起
- 明细取不到时仍就地显示失败原因
- 终态任务仍可展开
- 既有前端测试不得删改


## ⚠️ v1.1 扩充(2026-08-29):合并四项显示问题

本 spec 原只含「去思考行 + 自动滚动」。经与用户确认,合并另外三项 ——
它们都在渲染层,分开改要动三次同一批文件。

### R6 — 恢复 🚀 状态条,改为按 content_type 分渲染

⚠️ 前一轮 fix 票(`c71f778a`)按旧方案**删除了**平台代发的
「🚀 开始执行」状态条。**新方案是恢复它,改在前端区分渲染。**

依据:平台早已区分消息类型,只是前端没按它渲染 ——

```sql
select content_type, count(*) from group_message group by content_type;
  text/plain    24    ← 任务书、汇报、findings(人/agent 写的内容)
  task_status   38    ← 🚀 开始执行 / 📋 已排队 / ✅ 任务完成
```

状态条本身有信息价值(排队位次、失败原因、额度恢复时刻),
问题在于它被渲染成**一条普通发言**,内容只有一行 emoji,看着像空气泡。

- 恢复 `queue.ts` 中被删的「🚀 开始执行」`postStatus` 调用
- 前端按 `content_type` 分渲染:`task_status` → **轻量状态提示样式**
  (单行、不占发言气泡);`text/plain` → 保持现有发言样式

⚠️ 不改 `postStatus` 函数本身,不改 `content_type` 的写入逻辑。

### R7 — 任务书按 markdown 渲染

前端**没有任何 markdown 依赖**,`message.body` 直接当纯文本显示
(`RequirementTimeline.tsx:299-306`)。而任务书全是 markdown,
`#` / `**` / `-` 原样显示,层级与重点全丢 —— 这是用户反馈「不好理解」的原因。

⚠️ 渲染需**防注入**:消息内容来自 agent,不得直接 `dangerouslySetInnerHTML`
未净化的 HTML。

### R8 — 长命令执行期间显示已耗时

执行器跑全量测试等长命令时(单次 340 秒以上),实时输出**完全静默**,
外部分不清「在跑」还是「挂了」。本轮已因此误判两次
(检视者查 pid 一次、用户问「执行器是不是卡了」一次)。

动作行在命令未完成时显示已耗时,例如:

```
[命令 #t192] pnpm --filter server test        (运行中 5m12s)
```

⚠️ 耗时由**前端按 `#id` 条目的时间戳推算**或后端提供,择一实现并说明依据;
不得为此改动摘要流的行格式约定(仍是一行一条目)。

## ⚠️ v1.2 增补(2026-08-29):显式暂停跟随 + 终端块一致性

### R9 — 显式「暂停跟随」控件

R4 的暂停是**隐式**的:上滚即停止跟随。实测问题是它**不可见** —— 没有任何提示
说明「已脱离最新」,也没有回到底部的入口;输出快时用户根本察觉不到自己已脱离。

- **输出永不暂停**。本条只影响**滚动跟随**,不影响接收、缓冲、WS 推送与落盘。
  「暂停」二字仅指滚动。
- **状态必须可见**:处于「未跟随」时显示持久指示(如底部悬浮条),并提供
  **「回到最新」**入口;点击后恢复跟随并滚到底部。
- **可手动切换**:提供显式暂停/恢复控件。显式暂停后,**即使滚动位置在底部也不跟随**
  (sticky),直到用户显式恢复。
- **两个来源的合并规则**(避免状态打架):
  - 显式暂停 → 强制不跟随,**优先于**滚动位置判定;
  - 显式恢复 → 立即滚到底部,并**交还给** R4 的滚动位置自动判定;
  - 未显式暂停时,行为与 R4 完全一致(≤32px 才跟随)。
- 该控件对**两个终端块组件**同时生效(见 R10),不得只做一处。

### R10 — 两个终端块组件必须行为一致

实测二者已分叉:

| 组件 | 使用方 | R4(≤32px 才跟随) |
|---|---|---|
| `OutputDetailBlock` | RequirementTimeline | ✅ 已实现(`FOLLOW_THRESHOLD_PX = 32`) |
| `LiveOutput` | TaskPanel | ❌ 无条件 `scrollTop = scrollHeight`,强制拉回底部 |

而 `LiveOutput` 的文件注释仍写着「两处共用,行为一致 —— 不要在各处重写终端块」,
**该描述已失实**。

要求:滚动跟随逻辑(R4 判据 + R9 控件)抽成**单一实现**,两个组件共用;注释与实际
一致。不接受「两处各写一份、行为凑巧相同」。

### v1.2 验收

- 输出持续追加时点「暂停」:输出**继续增长**(字节数持续变大),滚动位置**不动**。
- 暂停态下滚到底部:**仍不自动跟随**(sticky 生效)。
- 点「回到最新」:滚到底部并恢复跟随;此后行为与 R4 一致。
- 未显式暂停时:上滚 >32px 停止跟随并出现可见指示;滚回底部自动恢复。
- 两个组件(TaskPanel 与 RequirementTimeline)行为**逐条一致**,由共用实现保证。

## 验收要点

- 运行中任务采样:摘要流中**无 `[思考]` 行**,动作行(工具/命令/汇报)完整可见
  (必测,贴出采样)
- 通过 `?detail=1` **仍能取到 thinking 条目全文**(R2,必测)
- 展开输出容器 → **初始滚动位置在底部**(R3,必测)
- 已在底部时追加新行 → **自动跟随**(R4,必测)
- ⚠️ 用户上滚到历史位置后追加新行 → **不被拉回底部**(R4,必测,成败关键)
- `frontend-expand-output-detail` 的既有用例**全部通过且未改动**(R5)
- R6:群消息中 `🚀 开始执行` **已恢复**,且在界面上渲染为状态提示而非发言气泡
- R7:任务书的 `#` / `**` / 列表**按 markdown 渲染**,未使用未净化的 HTML 注入
- R8:长命令运行期间动作行显示已耗时,静默期可判断在等什么、等了多久
- 测试全绿,贴出用例数
