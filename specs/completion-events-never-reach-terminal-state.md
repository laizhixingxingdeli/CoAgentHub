# Spec: 完成事件永久滞留 pending,被无限重扫

> **状态**: Landed — (2026-09-02 状态订正:DB 中该 specRef 有 4 个 done 任务为证;此前状态未随关票更新)
> **版本**: 1.0
> **日期**: 2026-08-31

## 1. 现象

`task_completion_event` 只在**成功创建续跑任务**时才置 `delivered`。
其余七种跳过路径下事件**永远停在 `pending`**,而消费器每 5 秒把**全部 pending
事件**拉出、逐条执行 task 查询与判定。

**实测(生产库,2026-08-31 核实):**

```
delivered  105
pending     72     ← 每完成一个任务就永久 +1
leased       1
```

历史任务总数 178。也就是说消费器基线即 **72 次 task 查询 / 5 秒**,
且这个数字**只增不减** —— 随任务数线性恶化,现在无感,长期是无界增长。

## 2. 根因:状态机缺口

`maybeCreateCoordinatorResumeTask` 返回 `"created" | "skipped"`,
**七处 skip 不区分性质**,调用方一律保留 pending:

| 行 | 条件 | 性质 |
|---|---|---|
| 164 | 事件属于续跑任务自身(R4 防环) | **永久** |
| 167 | 子任务无 `parentTaskId` | **永久** |
| 171 | 父任务查不到 | **永久** |
| 172 | 父任务已终态 | **永久** |
| 178 | 父任务执行方不是协调者 | **暂时**(见 §3.2) |
| 186 | R2:父协调进程仍存活 | **暂时** |
| 199 | R3:已存在非终态续跑 | **暂时** |

代码注释(L107-112)自述了这个缺口:续跑任务自身的完成事件"终态会被 R4 防环
跳过、事件永久 pending"。

## 3. 决策

### R1 — 永久不可处理的事件置 `dead`

`maybeCreateCoordinatorResumeTask` 的返回值细化为区分两种 skip;
消费循环对**永久**类事件置 `dead` 并写 `lastError` 说明原因。

**置 `dead` 的四类(且仅这四类)**:行 164 / 167 / 171 / 172。

- `dead` 态**已存在**(`routes/participant/task-completion-events.ts:356`,
  fail 端点重试耗尽时使用),**不新增状态、不加迁移**。
- `lastError` 写明具体原因(如「事件属于续跑任务自身,按 R4 防环不产生续跑」),
  保证可审计 —— 静默丢弃是被禁止的降级。

### R2 — 暂时不可处理的事件**保持 pending**(现有行为)

行 178 / 186 / 199 三类**逐字不变**。

### 3.2 ⚠️ 行 178 为什么必须算「暂时」

`isCoordinatorTask` 是**按群成员角色实时判定**的,而群成员角色**可变**
(运行期可增删成员、改角色 —— 本仓 2026-08-30 就在运行中新增过执行器成员)。

若把「父执行方当前不是协调者」判为永久并置 dead,该父任务日后恢复
coordinator 角色时,这条续跑将**永久丢失**。**保守保留 pending。**

### 3.3 ⚠️ 与孤儿收敛豁免的交互(已核实不受影响)

`hasPendingResumeEvent`(孤儿收敛豁免的另一半)查 pending 事件判定父任务是否
"正在等待续跑"。置 dead 会减少 pending 集合,**必须确认不破坏该判定**:

- 其最后一行是 `rows.some((row) => !isResumeTask(row))` ——
  **本就排除续跑任务自身的事件**,故 R1 的行 164 类不影响其结果;
- 行 167(无 parentTaskId)不会匹配任何 `parentTaskId = X` 查询;
- 行 171/172(父不存在 / 父已终态)对应的父任务**不是孤儿收敛的候选**
  (终态任务不被收敛),故不影响。

⚠️ **实现必须为这三点各留一条回归断言**(见验收 4),
不得因"看起来不影响"而略过 —— 这是本 spec 唯一可能造成新死锁的方向。

### R3 — 不涉及

- 不改 `hasPendingResumeEvent` / `hasExemptingChildTask` / 孤儿收敛判据。
- 不改续跑任务的创建条件与 R2/R3/R4 语义。
- 不改消费器周期(5 秒)与 inbox 路由。
- 不清洗存量 pending 事件 —— 由消费器在正常周期内自然收敛。
- 不加迁移、不新增状态。

## 4. 验收标准

1. 四类永久 skip 各构造一例 → 事件置 `dead` 且 `lastError` 含具体原因。必测。
2. 三类暂时 skip 各构造一例 → 事件**保持 pending**(回归)。必测。
3. 正常路径(成功创建续跑)→ 事件仍置 `delivered`(回归)。必测。
4. **豁免交互回归(不得省略)**:
   - 父任务下仅有「续跑任务自身」的事件被置 dead →
     `hasPendingResumeEvent` 结果**与置 dead 前一致**;
   - 父协调进程已退、子任务事件仍 pending → 父任务**仍被豁免**(不被判死)。
5. 存量收敛:一次消费周期后,pending 数应收敛到"仅暂时性滞留"水平
   (预期 < 在途任务数)。以实测数字给出证据。
6. 既有 coordinator-resume / orphan-task-reconciler / task-completion-events
   测试全绿。

## 5. 兼容性

- 无 schema 变更、无迁移、无新状态。
- 回滚代码后新事件恢复堆积行为;已置 dead 的事件带 `lastError` 可审计,
  不产生错误数据。
