## 2. 动作 1:按**速度**算,不值得

清点结果(静态求和,每处只算一次):

```
116 处固定 sleep / setTimeout 等待,合计 16,725 ms = 16.7s
```

前五名:`executor-trigger`(3.1s / 13 处)、`ws-hub`(2.5s / 7 处)、
`dispatcher-fields`(2.0s / 8 处)、`executor-queue`(1.6s / 6 处)、
`executor-quota-redispatch`(1.0s / 3 处)。

**全量套件本机实测约 728 秒。16.7s 占 2.3%。**

⇒ **116 处改造、每处都可能引入新的等待竞态,换 2.3%。不做。**

⚠️ 这与 T2 形成对照:T2 只改了 3 个文件,纯逻辑测试 **11.28s → 1.29s(8.7×)**。
**同样是「测试提速」,收益差了两个数量级** —— 区别在于 T2 打的是
**结构性成本**(每文件都建库),T4 的 sleep 是**分散的小额支出**。

## 3. 动作 1/2 的另一半:按**稳定性**算,值得 —— 但只改已经翻过车的

固定 sleep 的另一个问题与速度无关:**「等一段时间然后断言」在机器变慢时就会翻**。
这是竞态,不是慢。

**但结论仍是不做批量改造,只改有实证的**:

- 2026-09-11 修过两条真竞态(`executor-queue.test.ts` 的认领超时阈值与占位
  任务时长设成等量、等进程退出却断言占用归零),用的正是
  **「等待被断言的那个事实」**而不是「等固定时长」;
- 那两条是**被 CI 红出来的**,不是扫出来的。

⇒ **判据:某处 sleep 真的翻过车,才改它。** 无差别转换会把 116 处稳定的代码
改成 116 处新写的等待逻辑,而新代码的竞态概率不低于旧代码。

⚠️ **「证明一段时间内不会发生」那一类必须保留 sleep** —— 例如断言
「冷却期内不派发」「停止后不再产生新输出」。把它换成事件等待是**逻辑错误**:
没有事件可等,正是要证明的东西。**批量改造最容易毁掉的就是这一类。**

## 3.1 §3 的判据当天就兑现了一次(`28bf2c46`)

T2/T3 落地后,CI 连红两笔(`bc1cadc2` / `4758d847`),
挂在 `retry-rollback-guard.test.ts` 验收#3:`expected null to be truthy`。

**根因不是回归,是一个从来就不成立的假设被暴露了:**

```ts
const running = await waitForTaskStatus(..., "running", 10000);
expect(running.checkpointRef).toBeTruthy();   // ← null
```

生产里 `status: "running"` 写在 `queue.ts:819`,`checkpointRef` 写在 **994** ——
**checkpoint 在后**,中间隔着若干 `await`。
「看到 running ⇒ checkpointRef 已就位」**从来没有保证**,
只是靠两次写入之间的偶然延迟蒙对。

⚠️ **是优化把它逼出来的**:T2 让每文件不再建库、T3 让 teardown 降了 90%,
机器争用变少、窗口变窄,这条就开始输。
**「优化会暴露潜伏竞态」不是优化的错,是那条竞态一直在。**

**修法正是 §3 说的**:改成**直接轮询被断言的那个事实**
(`waitForRunningWithCheckpoint`,等「running 且 checkpointRef 非空」),
**不是把 sleep 调大**。同文件另一处同款假设(验收#1 的
`running + sleep 300ms`)一并改掉,sleep 去除。
零生产改动;检视者独立连跑 **4 次全绿**。

**这恰好证明 §2 的结论是对的**:值得改的是**翻过车的那一处**,
不是那 116 处里"看起来也像"的其余部分。批量改造既换不来速度(2.3%),
也不会帮你找到这一条 —— 找到它的是 **CI 变红**。

## 3.2 另一类:**预算 vs 负载**(与 §3.1 不同,不要混为一谈)

同一轮里 CI 还偶发挂过一次
`executor-transient-quota.test.ts > 验收 4`,**单条耗时 20110ms —— 撞 20 秒上限**。
本机连跑两轮各约 14s 全过;紧接的同代码提交(`1daa3891`)CI 也绿。

> ### ⚠️ 本段原来的定性是**错的**(2026-09-13 纠正)
>
> 原文写的是「这不是竞态,是预算太紧 —— 该测试要等三轮真实退避,
> 本机宽裕,CI runner 慢或有负载时就临界」。**核实后推翻:**
> 该用例的退避配的是 `__setTransientQuotaForTests(200, ...)` = **200 毫秒**,
> 三次 attempt 合计该在 2 秒内跑完;CI 日志显示它**只 spawn 了一次**就
> 静默 20 秒。这是**真缺陷(丢唤醒)**,不是预算。详见
> [transient-requeue-lost-wakeup.md](transient-requeue-lost-wakeup.md)。
>
> **教训**:判「预算 vs 竞态」之前**必须先核对被等待那个量的真实配置值**。
> 只看「耗时撞上限」就归到预算,会把真缺陷记成无害问题 ——
> 本条因此被放过了两次。
>
> 下面保留原文的对照表(**表本身仍然成立**,错的是把本用例归进右列)。

⚠️ **与 §3.1 的区别要分清,否则会改错东西:**

| | §3.1 竞态 | §3.2 预算 |
|---|---|---|
| 症状 | 断言拿到 null / 早期值 | **超时** |
| 根因 | 等的是**近似信号**,不是被断言的事实 | 等的是**对的事实**,只是**给的时间不够** |
| 修法 | 改成等那个事实(**不要加时间**) | **加预算**或降低该用例的真实等待量 |
| 改错的后果 | 加 sleep = 窗口变大,竞态仍在 | 改成"等事实" = 它本来就在等事实,白改 |

**同类已知的还有一处**:T3 的 `drainBackgroundWork` 固定 20 秒上限
(见 [drain-background-work-instead-of-idle-guess.md](drain-background-work-instead-of-idle-guess.md)
的「三轮未能复现」一节)。

**处置**:两处都**先观察,不改**。判据是「在 CI 上反复出现」——
偶发一次就调预算,等于把测试变成对机器速度的断言。
若反复出现,优先**降低真实等待量**(例如把退避阈值调得更小),
而不是简单加大上限。

> **后续(2026-09-13)**:`executor-transient-quota` 那一处已按上面的
> 「反复出现」判据触发复核(累计 4 次),但复核结论是它**根本不属于本节**
> —— 见本节开头的纠正框。`drainBackgroundWork` 的 20 秒上限**仍在观察**,
> 至今 0 次。

### 3.2.1 第三个实例:这条够判据了,已修(`d00e3bf8`)

`web/src/router.test.tsx` 三处 `findByTestId("requirement-workspace")`。

**证据链(同代码、同机器,只差负载):**

| 跑法 | 结果 |
|---|---|
| 检视者跑完一堆活之后直接跑 | **2 failed**(3728ms / 1435ms —— 都越过 1000ms) |
| 机器闲时用基线工具跑 | **0 failed \| 8 passed**(全程 5s) |
| CI(`cb7a1e77`) | **红** |

它同时满足「本机长期红」与「CI 上出现」,**够「反复出现」这条判据**,
于是按 §3.2 的修法处理:**加预算,不改成等事实**(等的事实本来就对 ——
`requirement-workspace` 在 `lazy + Suspense` 后面,要等一次动态 import)。

**改法**:三处显式 `{ timeout: 5000 }` + 紧邻注释写明「这是 lazy 动态 import,
不是竞态」;**不全局抬 `findBy` 默认值**(那会把真正的竞态一起掩盖)。

#### ⚠️ 一个二阶陷阱:抬了 findBy 还不够

执行侧在**连跑第 4 次**时撞红才发现:`findBy` 抬到 5000ms 之后,
**vitest 的单用例 `testTimeout` 默认也是 5000ms** —— 用例会被**先**杀掉,
表现成另一种失败。必须同时把这三条用例的 `testTimeout` 抬高(取了 15s)。

**记下来**:调 `findBy` 预算时,**永远同时检查外层 `testTimeout`**;
两者相等或内层更大时,你抬的那个预算根本没机会生效。
**这个陷阱是「连跑 5 次」抓出来的,跑一次是看不见的。**

检视者复验:常规连跑 **5 次全 exit 0**;**8 个 CPU burn 并行下再跑 2 次,
也全绿**;只动测试文件,零生产改动。

## 4. 处置

**T4 视为完成**:三项已满足、一项不适用、一项经量化后判定不做。
不做的理由是**数字**(2.3%)与**风险方向**(新等待逻辑的竞态不低于旧的),
不是「来不及」。

后续若某处 sleep 在 CI 上翻车,按 §3 的判据单独改那一处,不要重开批量改造。
