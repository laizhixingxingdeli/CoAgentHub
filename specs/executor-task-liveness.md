# Spec: 执行器任务的存活探测 —— 监工被自己看管的对象杀掉

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-24

## 背景:一个架构循环

本轮同一张票连续两次因**执行器进程静默消失**而中断,两次都是检视者人工发现的:

| 次 | 现象 |
|---|---|
| 1 | 任务挂 `running` **八小时**,无进程、无提交、无 PATCH |
| 2 | 实现做完、成果留在暂存区,进程消失前未提交 |

平台**有**静默检测:`stallAlertMinutes: 15` 提醒、`stallTimeoutMinutes: 30`
标 `failed`。两次都没有触发。

### 为什么没触发

两条原因叠加,第二条是根本的:

**① 计时器是内存态。** `run.stallTimer` / `run.stallAlertTimer` 挂在内存里的 run
对象上(`queue.ts:627-628`)。**后端进程一死,全部计时器随之消失。**

**② 任务书要求执行器重启后端 —— 而后端正是看管它的那一个。**

涉及后端的票,任务书里都写着「改完必须重启后端」。于是每一张这样的票都有一段
**无人看管的窗口**:执行器停掉后端 → 计时器全没了 → 若执行器在这段时间里死掉,
**没有任何东西会发现**。

**监工被自己看管的对象亲手杀掉,然后监工的闹钟也一起没了。** 这是结构性的,
不是偶发。

### 现有兜底覆盖不到

- `recoverInterruptedTasks`(启动恢复)只在**后端重启时**跑。若没人重启,
  任务就一直挂着 —— 本轮那次挂了八小时,正是因为我没重启。
- `detached-task-liveness`(30 分钟阈值)**只覆盖协调任务**
  (`isDetachedTask()` 为假直接返回,见 `detached-task-liveness.ts:48`),
  **执行器子任务不在其中**。

## 决策:改用读时求值,不依赖计时器

`detached-task-liveness` 已经证明了这条路可行:**判定在读任务详情时顺带算出**,
不需要常驻计时器,因此**天然不受后端重启与停机影响**。

把同一套办法扩展到执行器任务。

### R1. 执行器任务的存活判定

对 `status === 'running'` 且**非**协调任务(`isDetachedTask()` 为假)的任务,
读详情时派生:

```json
"liveness": { "warning": true, "lastSignalAt": "2026-08-24T11:31:56.000Z" }
```

存活信号取以下最大值(与 `detached-task-liveness` 同款口径,**复用其取值逻辑**):

- `task.createdAt` / `task.updatedAt`
- `taskOutputUpdatedAt(task.id)`(进程本地输出时间)

⚠️ **不含子任务** —— 执行器任务没有子任务,该维度不适用。

`warning` = `now - lastSignalAt > 阈值`。

### R2. 阈值复用现有配置,不新增

**直接用 `stallTimeoutMinutes`(缺省 30)**,不要新增配置项。

理由:同一件事(「这个执行器多久没动静了」)已经有一个阈值,再加一个只会
让两个数字漂移。现有那个只是**触发方式**不可靠(内存计时器),**数值本身是对的**。

### R3. 与内存计时器并存,不删除

**保留**现有的 `stallTimer` / `stallAlertTimer` 机制。

理由:后端持续运行时,计时器能**主动**把任务标 `failed` 并释放队列槽位 ——
那是读时求值做不到的(没人读就不会算)。两者互补:

| 机制 | 优势 | 盲区 |
|---|---|---|
| 内存计时器 | 主动、能改状态、释放槽位 | 后端一停就全没 |
| 读时求值(本票) | 重启/停机免疫 | 被动,要有人读才算 |

**本票只补盲区,不替换现有机制。**

### R4. 只报不拦,不改状态

与 `detached-task-liveness` R3、`l3-verdict-observability` R5、
`stale-runtime-detection` R4 同一立场:

- **不修改** `task.status`
- **不触发**自动重试、自动终止、自动通知
- 只让「这条执行链可能已经断了」**变得可查询**

### R5. 载荷洁癖

- 仅对**执行器任务**输出 `liveness` 字段;协调任务**不输出**
  (它已有 `livenessWarning` / `lastSignalAt`,见 `detached-task-liveness`)
- 不满足条件(非 running、非执行器任务)**不输出该字段**,不是输出空对象
- 与 `l1` / `l3` / `runtime` 的处理保持一致

### R6. 不做这些

- **不改**任务书模板里「改完必须重启后端」的要求 —— 那个循环是真的,但解开它
  (例如改由协调者重启)是更大的改动,**本票只做可观测**
- **不新增**配置项(R2)
- **不删除**内存计时器(R3)
- **不改**前端

## 验收标准

- [ ] `running` 的执行器任务超过 `stallTimeoutMinutes` 无信号 → 详情含
      `liveness.warning: true`
- [ ] 有信号(`updatedAt` 或 `outputTail` 更新)在阈值内 → `warning: false`
- [ ] `lastSignalAt` 取三个来源的最大值,取值逻辑**复用** `detached-task-liveness`
- [ ] **协调任务不输出** `liveness` 字段(它走既有的 `livenessWarning`,回归必测)
- [ ] 非 `running` 的任务**不输出**该字段
- [ ] 判定**不修改** `task.status`(回归,必测)
- [ ] 未新增配置项,阈值取自 `stallTimeoutMinutes`
- [ ] 内存计时器机制**未被删除或改动**(回归,必测)
- [ ] **后端重启后**,对同一条 `running` 任务的判定结果不变
      (证明不依赖内存态 —— 这是本票的核心价值,必测)
- [ ] 后端测试全绿,贴出用例数
- [ ] **未改动**前端

## 不涉及

- 解开「执行器重启后端」的循环(R6)
- 自动重试 / 自动终止 / 通知(R4)
- 前端展示 `liveness`(另开票)

## 执行环境提示

- 本仓 pnpm 项目,后端 `:3001`
- 现成参照:`lib/detached-task-liveness.ts`(读时求值 + 信号取最大值),
  **按同款结构写,能复用的直接复用**
- 改完重启后端;**重启前确认无 running/queued 任务**
- 验收「重启后判定不变」这条时注意:重启会触发 `recoverInterruptedTasks`
  把 running 任务标 failed,**测试里应直接构造数据验证纯函数**,不要依赖真实重启
