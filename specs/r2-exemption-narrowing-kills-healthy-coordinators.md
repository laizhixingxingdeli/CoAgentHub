# Spec: 豁免收缩误杀正常协调者 —— 子任务只是排队,父任务就被判死

> **状态**: Frozen
> **版本**: 1.0
> **日期**: 2026-09-11
> **来源**: 2026-09-11 的真实级联事故。检视者定位到
> `orphan-task-reconciler.ts:90` 的 R2 收缩是把「单点耗尽」放大成「全盘死锁」
> 的那个放大器。

## 1. 背景与目标

### 1.1 事故:一个做对了一切的协调者被判死

任务 `01a090bc`(协调者 pi,弹窗票):

- 输出显示它**完整做完了派发** —— 写了计划、建了子任务
  `01a0910f`、回填了 taskId;
- 然后按 coordinator skill 的 **exit-after-dispatch** 规则**正常退出**
  (该 skill 明令禁止轮询等待);
- 平台随后以 `executor pid 20708 no longer exists` 把它判 **failed**。

**它没有任何做错的地方。**

### 1.2 判据在哪

`packages/backend/server/src/lib/orphan-task-reconciler.ts` 的豁免条件:

```ts
if (
  (await isCoordinatorTask(db, task.groupId, task.executorParticipantId ?? "")) &&
  ((await hasExemptingChildTask(db, task.id)) ||
    (await hasPendingResumeEvent(db, task.id)) ||
    (await hasPendingCloseGuardResume(db, task)))
) {
  continue;  // 豁免,不判死
}
```

其中 `hasExemptingChildTask` 的 **R2 收缩**(:90 注释原文):

> R2 收缩:queued 且从未启动(executor_pid 为空)、执行器不可派发
> (**冷却中 / 并发已满** / 查无配置)的子任务并不在干活,不构成豁免 ——
> 否则已死的协调者链会被「排队等冷却(最长 300 分钟)」的子任务无限期钉住,
> 整棵子树无进展也无告警。

本例中子任务 `01a0910f` 正是 **queued + `executor-concurrency`**:
另一张票的执行器 `01a0909f` 烧了约一万轮后挂起,长时间占住 atomcode 的
并发槽(`maxConcurrency: 1`)。

→ `hasExemptingChildTask` 返回 false → 协调者被判死。

### 1.3 R2 的本意是对的,但判据太粗

R2 要防的是:**已死的协调者**被一个**永远排不上**的子任务无限期钉住。
那个担心成立。

但它用「执行器当前不可派发」代替了「这棵子树没有进展」,而这两者**不等价**:

| 情形 | 执行器不可派发 | 子树有进展吗 |
|---|---|---|
| 子任务排在**另一个任务后面**(并发已满) | 是 | **有** —— 前面那个跑完就轮到它 |
| 子任务等 300 分钟额度冷却 | 是 | 可疑 |
| 子任务的执行器**查无配置** | 是 | **没有** —— 永远排不上 |

**第一行被误杀了。** 「并发已满」是**临时且必然解除**的状态 —— 占槽的任务终会
终态,届时排队的子任务就会启动。把它和「查无配置」归为一类,等于把「正在排队」
当成「永远不会动」。

### 1.4 放大效应

事故的完整链条:

```
执行器烧光轮次挂起 → 长期占住并发槽
  → 另一张票的子任务排队(executor-concurrency)
    → R2 判「不构成豁免」
      → 该票的协调者被判死(1.1)
        → 与此同时另一个协调者成僵尸,占住工作树闸
          → 两个 queued 任务全被挡,全盘停摆
            → 只能等 stall(30 分钟)/ detached(24 小时)超时
```

**单点耗尽本该只影响一张票,R2 把它放大成了全盘死锁。**

### 1.5 目标

让「子任务只是排在别人后面」不再导致父协调者被判死,**同时保住 R2 防
「永远排不上」的本意**。

| 文件 | 改什么 |
|---|---|
| `packages/backend/server/src/lib/orphan-task-reconciler.ts` | `hasExemptingChildTask` 的判据细化 |

`hasPendingCloseGuardResume`);`isCoordinatorTask` 的判定;detached 超时兜底;

## 3. 详细改动

### R1. 区分「临时排队」与「永远排不上」

把当前的二元判据(可派发 / 不可派发)细化,至少要把下面两类分开:

- **临时**:并发已满(占槽者会终态)、额度冷却(有明确 ETA);
- **终局**:执行器查无配置、执行器被禁用之类 —— 这棵子树**确实**不会动。

**临时** → 构成豁免(父协调者不判死);**终局** → 不构成豁免(保持 R2 本意)。

⚠️ **额度冷却归哪一类由实现判断并说明理由。** 它有 ETA(最长 300 分钟)、
终会解除,但也确实可能很久。票面不预设 —— **但必须在汇报里写明选择与理由**,
因为这正是 R2 当初收缩的动机所在。

### R2. 判据要能自证「为什么这次豁免/不豁免」

豁免与否的结论**要能被外部看见**。当前判死时写 `reconciledReason`;
豁免时什么都不写,排障只能读代码猜。

要求:豁免路径也留痕(日志或 diffSummary 皆可,由实现选择并说明),
至少能回答:**是哪一条豁免命中了、为什么**。

理由:本次事故检视者是靠读源码才定位到 R2 的,如果豁免判定可观测,
第一时间就能看出「子任务 queued 但未被计入豁免」。

### R3. 不要顺手改 detached 超时

24 小时的 detached 超时是**最后一道兜底**,R2 收缩的注释里明确把它当作
「不成立情形」的保底。本票只细化豁免判据,**不动兜底**。

## 4. 验收标准

1. **子任务 queued 且因「并发已满」不可派发** → 父协调者**豁免,不判死**。
   ⚠️ 这条是本票的核心,必须直接对着事故形态构造。
2. **子任务 queued 且执行器查无配置** → 父协调者**仍判死**(R2 本意未丢)。
   ⚠️ 只测第 1 条不算 —— 那等于把 R2 整条删掉。
3. 额度冷却的归类有用例覆盖,且汇报里写明为何这样归类。
4. 豁免路径可观测(R2):说明留痕在哪、含什么。
5. 其余两条豁免路径(`hasPendingResumeEvent` /
   `hasPendingCloseGuardResume`)逐字未改(`git diff` 自证)。
6. detached 超时未改。
7. 既有测试不新增失败;受影响文件前后对照用
   `node scripts/test-baseline.mjs packages/backend/server <文件...>` 取。
8. `npx tsc --noEmit -p tsconfig.json` 通过。

## 5. 不涉及的改动

- 不改并发上限、工作树闸、调度泵的任何行为。
- 不改 detached 超时。
- **不试图解决「执行器轮次耗尽」** —— 那是本次事故的**根因**,本票只修
  **放大器**。根因另有专票。

## 6. 工作文件的去向

临时脚本与中间产物**一律放 `.scratch/`**;交付时 `git status --porcelain`
除本票改动与用户长期未提交的两个文件外为空。
**计划文件 `plans/<name>.md` 属于交付物,要纳入提交。**

## 7. 兼容性

行为变更:原本会被判死的一类协调任务现在会保持 running,等子任务进展。
需说明:这是否可能让某种此前能被收敛的情形变成长挂 —— detached 超时
(24h)是否足以兜住。
