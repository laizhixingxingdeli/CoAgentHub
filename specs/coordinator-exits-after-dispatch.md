# Spec: 协调者派完子任务后应当退出,而不是阻塞等待

> **状态**: Ready for Implementation
> **版本**: 1.0
> **日期**: 2026-08-26

## 背景

`wake-the-coordinator-on-child-completion`(`785e4f1a`)落地后,平台会在执行子任务
进入终态时创建**续跑任务**把协调者重新拉起。但协调者技能里**没有任何一句**
说明派发之后该走还是该留,于是它自己选择了**阻塞轮询等待**。

实测(本群任务 `01a03be7`):

```
01a03be7  Codex     pid 2395 + 2396   存活   ← 协调者阻塞着
01a03bed  AtomCode  pid 3061          存活   ← 子任务在跑
```

阻塞的实际收益只有「省几次重读」,代价却是占住 CLI 槽位、持续消耗额度与时长、
并承担超时风险。**而这正是历史上五次绕过 L1 的根因**:阻塞成本太高,
自己动手 6–12 分钟必成,派子任务 15–43 分钟且四次里坏两次。

## 关键前提:上下文是可复得的

续跑任务书(`coordinator-resume.ts` 的 `buildResumeBrief`)已经带齐:

- 父任务 id、`specRef`、`specHash`
- 本次终态子任务的 id、状态、完整 `diffSummary`
- 全部子任务的 id 与当前状态
- 操作指引(做 L2 → 结案父任务 → 结案续跑任务)

丢掉的只是协调者上一轮 CLI 里的思考过程。**L2 是「对着冻结规范检视产出」**,
本就应当只依赖可复得的事实(仓库里的 spec、`diffSummary`、任务详情 API),
而不依赖上一轮想过什么。

并发也已经处理:平台在**父进程仍存活时不创建续跑**(`coordinator-resume.ts:80-86`,
`isExecutorProcessAlive` 判定),所以退出不会导致双跑。

## 决策

### R1. 派发成功后结束本轮,不轮询等待

协调者在**确认执行子任务创建成功**后,应当结束本轮 CLI 调用,
**不得**为了等待子任务终态而轮询、`sleep` 或以任何形式阻塞。
子任务终态时平台会通过续跑任务把它拉回来做 L2。

### R2. 退出的前提是派发确已成功

⚠️ 只有在子任务**确认创建成功**(接口返回成功且拿到子任务 id)后才可以结束。
派发失败、被 403/400 拒绝、或找不到健康执行器时**不适用本条** ——
那些情况按现有规则处置(在群内说明阻塞原因 / 以 `failed` 结案并写明),
**绝不能**在没有任何子任务的情况下静默退出:那样既没有子任务能触发续跑,
父任务也会挂成僵尸。

### R3. 续跑后先看子任务状态,不要重复派发

被续跑任务拉起后,**先读全部子任务的当前状态**(续跑任务书里已列出),
再决定动作。已完成的工作**不得重复派发**。

### R4. 一次只派一个,天然串行

本条与既有的「串行下发」约束一致:派一个 → 退出 → 续跑时再派下一个。
⚠️ **不要**为了少几次往返而在一轮里连派多个子任务 ——
它们会成为共享同一棵 git 树的并行进程。

### R5. 只改技能说明,不动平台逻辑

- **不改** `coordinator-resume.ts` 的任何判定(R1–R4 防护、防环标记、存活检查)
- **不改** L2 / L3 的语义与时机
- **不加**平台侧的强制退出机制 —— 无法可靠判定「它是在阻塞还是在正常工作」,
  误杀正在做 L2 的协调者比阻塞更糟

      派发 → 协调进程退出 → 子任务终态 → 平台创建续跑任务 →
      协调者被拉起 → 完成 L2 → 结案父任务

- [ ] 平台侧代码零改动(`git diff` 确认,回归)
