# Spec: 消息已提交、task 未创建的窗口没有恢复手段

> **状态**: Frozen
> **版本**: 1.0
> **日期**: 2026-09-08
> **来源**: `docs/implementation-optimization-review-2026-09-07.md` §4 **R4**
> **前置决策(用户 2026-09-07 已拍板)**:**持久化调度意图**,
> 不采用「事务内创建 task」。R4 原文把这两条列为二选一 —— 决策已做出。

## 1. 背景与目标

### 1.1 现状证据(检视者已复核代码)

`packages/backend/server/src/routes/group/messages.ts` 第 624–657 行,
消息写入后有两条派发路径:

| 路径 | 写法 | 行 |
|---|---|---|
| `audience: role` | `await maybeDispatchExecutorTask(...)` | 634 |
| **participant 定向** | **`void maybeDispatchExecutorTask(...)`** | **654** |

participant 定向是 **fire-and-forget**:消息已经提交,派发在响应之后异步发生。

而 `packages/backend/server/src/lib/executor-task/queued-task-reclaim.ts`
**只扫 DB 里 `status = 'queued'` 的行** —— 它恢复的是
「**已经存在但没被拾起**」的 task。

### 1.2 危害:一个没有任何兜底的窗口

消息提交成功 → **进程退出/异常** → task 从未创建。

此时:

- 消息在库里,用户看得见,以为派下去了;
- **没有 task 行**,所以 `queued-task-reclaim` 扫不到它 —— 它只认已存在的行;
- `message_id UNIQUE` 只能**防止重复** task 行,**不能补齐未创建的记录**;
- 结果是**永久**的「有消息、无 task」。

⚠️ 注意这不是理论窗口:今天(2026-09-08)平台上就发生过多次进程级异常
(执行器 spawn 失败、任务重试、检视者手工干预)。

### 1.3 目标

**符合派发条件的请求最终一定得到一个 task;
拒绝派发有明确记录;不重复执行。**

R4 原文的硬要求:
「**不得仅靠扫描所有历史消息猜测是否应执行**」。

## 2. 改动范围

| 文件 | 改什么 |
|---|---|
| `packages/backend/server/src/routes/group/messages.ts` | 在消息事务中持久化调度意图 |
| DB schema + 迁移 | 存放调度意图 |
| `packages/backend/server/src/lib/executor-task/queued-task-reclaim.ts` 或新恢复入口 | 恢复未创建 task 的意图 |
| 对应测试 | 新增用例 |

**不改**:`maybeDispatchExecutorTask` 的派发判定口径;
`message_id UNIQUE` 约束;控制指令通道;
`queued-task-reclaim` 现有的 R1/R2/R3 三项职责(**只增不改**);
本轮刚落地的检视者派发守卫(`dispatch-must-not-spawn-the-reviewer`)。

## 3. 详细改动

### R1. 调度意图与消息同事务持久化

消息写入的**同一个事务**里记下「这条消息要派发,目标是谁」。

事务提交 = 意图已持久化。之后进程怎么死,恢复时都能从意图重建 task。

⚠️ **意图不是 task**。它记的是「该派」,不是「已派」。
两者的状态机要分清楚,不要把意图表当成 task 表的影子。

### R2. 意图必须记下解析结果与拒绝原因

R4 原文:「目标解析、拒绝派发和重试结果**必须可追踪**」。

至少要能回答:

- 目标解析成了谁(participant id),或为什么没解析出来;
- 若**拒绝派发**(控制指令跳过、检视者目标不可派发、角色无匹配……),
  **拒绝原因是什么** —— 拒绝也是一种终态,不能让意图永远悬着;
- 重试/恢复发生过几次,结果如何。

### R3. 恢复入口:意图有、task 无 → 补建

恢复器要能处理「意图存在但没有对应 task」。

**必须与正常派发走同一条判定口径** —— 不要写第二套「该不该派」的逻辑
(这正是 S3「同一事实不在多个模块独立推导」要避免的)。

特别地:**恢复时也要过检视者守卫**。若目标在群内是 reviewer,
恢复同样不建 task,并把拒绝原因写回意图。

### R4. 不重复执行

意图 → task 的转换必须幂等。已经有 task 的意图不得再建一个。
`message_id UNIQUE` 是既有防线,**保留它**,但不要只依赖它 ——
它防的是重复行,不防重复 spawn。

### R5. 派发失败如何向调用方暴露

R4 原文列为需决策项。**本票的口径**:

- **同步能判定的拒绝**(控制指令、检视者目标、角色无匹配)——
  沿用**现有的响应头 warning 机制**,行为不变;
- **异步发生的失败**(意图已持久化但补建时失败)——
  **不改响应**(那时响应早发出去了),写回意图的失败记录,
  并按既有的 stall 处置路径可见化。

**不要为此新增 API 或改变响应结构。**

## 4. 验收标准

**基线先用工具取**(自行判断受影响文件,清单写进汇报):

```
node scripts/test-baseline.mjs packages/backend/server <受影响的测试文件...>
```

1. **核心:在交接位置注入中断**。
   在「消息提交成功」与「task 创建」之间注入进程退出/异常,
   恢复后该请求**最终得到一个 task**。
   ⚠️ **这条用例改动前必须是红的** —— 给出改前的实际现象
   (消息在、task 不在、恢复器扫不到)。
2. **拒绝派发有明确记录**:控制指令跳过、检视者目标不可派发、
   角色无匹配三种拒绝,各有一条用例断言拒绝原因被记下,**且意图不悬着**。
3. **不重复执行**:同一意图被恢复器处理两次 → 只有一个 task。
4. **恢复过检视者守卫**(R3):意图目标是 reviewer 时,恢复**不建 task**。
   ⚠️ 这条容易漏 —— 恢复路径绕过消息层的守卫是本票最可能引入的新缺陷。
5. **既有派发路径行为不变**:`audience: role` 的 await 语义、
   响应头 warning、控制指令跳过,全部保持原状态(回归)。
6. **迁移可用**:给出迁移文件;说明**已存在的历史消息**如何处理
   (合理的答案是「不追溯」,但要**明说**)。
7. 定向测试前后对照,失败数不增加。
8. `npx tsc --noEmit -p tsconfig.json` 通过。

## 5. 不涉及的改动

- **不采用「事务内创建 task」**(决策已排除)。
- 不改派发判定口径、不改 `message_id UNIQUE`、不改控制指令通道。
- 不改 `queued-task-reclaim` 既有的 R1/R2/R3 三项职责(只增不改)。
- **不实现「扫描历史消息猜测是否应执行」**(R4 原文明令禁止)。
- 不新增 API,不改响应结构(R5)。

## 6. 兼容性

- **有 schema 变更与迁移** —— 这是本票唯一一处 schema 改动,
  在汇报里单独说明表结构与索引。
- 已存在的历史消息不追溯(§4.6 要求明说)。
- 行为变更:此前 participant 定向派发失败会静默丢失,现在留下可追踪记录。
