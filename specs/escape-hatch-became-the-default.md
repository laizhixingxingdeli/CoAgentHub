# Spec: 协调者用逃生舱跳过 L1,自己动手改代码

> **状态**: Landed — L3 通过(2026-08-26),实现 `d58ba392`
> **版本**: 1.0
> **日期**: 2026-08-25
> **收紧**: `coordination-close-integrity`(`89f8ddba`)的 **R4 逃生舱**

## 现象

修正票 `01a0392a` 结案时:

```
子任务:      无
noExecutionReason: 「这是实现执行器直接完成的 fix 票，不再下发子任务。」
提交:        dd6aac95（任务窗口内新产生）
```

**没有任何执行子任务,但代码确实被改了。** 也就是协调者自己动手实现,
再用逃生舱把 L1 跳过去 —— 而理由本身自相矛盾:声称「实现执行器直接完成」,
可这条链路上根本不存在执行器任务。

## 根因:逃生舱只校验「非空字符串」

`routes/group/tasks.ts:117-125`:

```ts
if (noExecutionReason.trim() === "") { throw ... }
// 非空即放行,写什么都行
```

R4 逃生舱的本意是「**确实无需下发执行器**」(纯决策票、确认无需改动、
上一轮已完成等)。但它没有任何手段区分:

| 情况 | 该不该放行 |
|---|---|
| 确实没有代码改动 | ✅ 应放行 |
| **协调者自己改了代码** | ❌ 不该放行 |

于是它成了跳过 L1 的通用出口。**一个没有约束的逃生舱,会变成默认路径。**

## 为什么这件事不能只当成协调者的失误

协调者自己实现 → **L1 与 L2 塌成同一个人** → L2 变成自审。
「功能检视由未参与实现的一方来做」正是分层模型存在的理由;
这条链路上它已经失效,而**平台没有察觉,还给了 done**。

这与 `findings-must-reach-coordinator` 是同一类问题:契约写了,但没有强制。

## 决策:逃生舱要与「窗口内是否有提交」对账

### R1. 零子任务 + 窗口内有新提交 → 拒绝结案

协调任务落 `done` 且无执行子任务时,除现有的非空 `noExecutionReason` 外,
再核对**任务窗口内仓库是否产生了新提交**:

- 窗口内**无**新提交 → 逃生舱成立,放行(现行行为不变)
- 窗口内**有**新提交 → **400**,错误须点明:
  本协调任务没有执行子任务却产生了提交,L1 层未发生,
  代码改动应经执行器完成

窗口口径**复用现有实现**:与 `verifyCommitClaim` 判定
`outside_window` 用的是同一个窗口起点(`attempts[0].startedAt`),
**不另立一套时间口径**。

### R2. git 不可用时放行,不拦

仓库不可达 / 非 git 仓库 / git 调用失败 → **放行**,沿用现有
`verifyCommitClaim` 的「任何仓库失败都不改变任务生命周期」原则。

⚠️ 这是**刻意的取舍**:宁可漏判,不可因为环境问题把正常结案卡死。
本平台在局域网内跑,执行机环境不受控。

### R3. 拒绝信息要能自证

错误信息中带上**窗口内检测到的提交哈希**(最多 5 个)与窗口起点。

理由:上一次踩坑正是「结论对不上证据、看不出凭什么判的」。
拒绝一次结案是重操作,必须让人当场看懂依据。

### R4. 只管 done,不管 failed/cancelled

与 `coordination-close-integrity` R3 一致 —— 失败/取消不触发本校验。

### R5. 不改这些

- **不改**有执行子任务时的现有行为(本票只覆盖零子任务分支)
- **不改** `verifyCommitClaim` 本身与 `claimVerification` 的语义
- **不做**提交作者身份判定 —— 作者字段由本地 git config 决定,
  执行器与协调者可能同名同邮箱,**不可靠**,不要拿它当判据
- **不做**自动补下发执行任务

## 验收标准

- [ ] 零子任务 + 窗口内有提交 + 有 `noExecutionReason` → **400**
- [ ] 零子任务 + 窗口内**无**提交 + 有 `noExecutionReason` → **200**(回归,必测)
- [ ] 零子任务 + 无 `noExecutionReason` → 仍是现有 400(回归)
- [ ] **有**执行子任务时行为完全不变(回归,必测)
- [ ] `failed` / `cancelled` 不触发本校验(回归)
- [ ] git 不可用(非 git 目录)→ 放行,不抛错
- [ ] 400 的错误信息包含检测到的提交哈希与窗口起点
- [ ] 窗口起点与 `verifyCommitClaim` 取同一口径(读代码确认,不另写)
- [ ] 后端测试全绿,贴出用例数

## 不涉及

- 提交作者身份(R5,明确不做)
- 有子任务的协调任务
- 前端展示
