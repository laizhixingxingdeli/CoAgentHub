## 1. 背景与目标

### 1.1 靶子(CI 实测,非本机)

`docs/test-perf-baseline-ci-and-local.md` §R6.3:

| 项 | CI 占比 | 内容 |
|---|---|---|
| `executor-queue.test.ts` | **21.3%**(134s) | 单文件;CI 上绿,耗时来自假执行器 `sh` 的固有开销 |
| **collectionOverhead** | **29.3%**(185s) | vitest 冷启 + 每文件 collect/transform/import + **每文件的 PGlite 实例创建** |
| teardown | 8.7% | 每文件 ~0.4s,非优先 |
| exec | 62.0% | 真实测试成本 |

本票针对 **collectionOverhead** 里可由「分类 + 解耦」回收的那部分。

### 1.2 为什么每个文件都在建库(现状证据,检视者已复核)

- `packages/backend/server/vitest.config.ts` 的 `setupFiles: ["./test/setup.ts"]`
  —— **对全部 129 个测试文件生效**;
- `test/setup.ts:13` 在**模块顶层**写着 `import { testClient } from "./db"`;
- `test/db.ts:13` 是**模块顶层** `export const testClient = new PGlite();`;
- `test/setup.ts` 的顶层 `beforeAll` 把 `database/drizzle/migrations` 下
  **全部 32 个 `.sql`** 逐个 `testClient.exec()`。

→ **每个测试文件都要:建 PGlite → 跑 32 个迁移 → afterAll 关库**,哪怕它
只测一个纯函数。这是结构性成本,落在 collectionOverhead 桶里。

### 1.3 ⚠️ 报告 T1 的验收有一条做不到

报告 §12.4 的验收原文:「**标记为纯逻辑的测试不创建 PGlite**、不执行 Git、
不访问真实数据库」。

但由 §1.2:PGlite 的创建发生在 `setup.ts` / `db.ts` 的**模块顶层**,由
`setupFiles` 无条件施加给每个文件。**测试文件自己改成什么样都改变不了这件事** ——
除非动 `setup.ts` 的加载方式,而那是报告 §12.5 **T2**(拆分 setup 与 fixture
生命周期)的范围。

**本票因此明确不承接那一条。** 硬把它塞进来,要么逼出一个半吊子的 setup 改造
(与 T2 撞车、且没有 T2 要求的 fixture 分组设计),要么逼出"改了分类清单但
PGlite 照建"的假交付。

本票交付的是 **T2 的输入**:一份可执行的分类清单 + 已解开的 barrel 耦合。

### 1.4 目标

1. 产出**覆盖全部测试文件**的真实依赖分类清单;
2. 解开纯逻辑测试对 barrel 的导入耦合(这部分**能**独立降低 collect/transform
   成本,不需要动 setup)。

## 2. 改动范围

允许触碰:

- 测试文件的 **import 语句**(barrel → 实际模块)
- 新增分类清单文档(路径在计划阶段定,建议 `docs/`)
- 仅当某个纯函数确有独立领域行为时,才移动它;**并保持既有公共导出兼容**

**不允许**:

- ⚠️ **不动 `test/setup.ts`、`test/db.ts`、`vitest.config.ts`** —— 那是 T2。
- ⚠️ **不改任何断言**。包括输出断言与错误分支断言。本票是搬运与分类,
  不是重写测试。
- **不为测试新增转发层**(报告 §12.4 第 3 条原文)。如果一个纯函数必须从
  barrel 拿,那就记进分类清单说明原因,不要造一个只为测试存在的再导出。
- 不改生产代码的行为。
- 不修任何既有红(本机的 Windows-only 那批、CI 的任何红)。

## 3. 详细改动

### R1. 分类按导入图与副作用定,不按文件名

报告 §12.4 第 1 条原文:「按导入图与副作用分类,**不能仅按文件名**」。

分类维度(报告给的六类):纯内存 / 临时文件 / 数据库 / Git / HTTP-WS /
执行器生命周期。一个文件可以同时属于多类。

⚠️ **判据要可复核**:清单里每一项都要写明**凭什么这么分**(哪条 import、
哪个副作用),不能只给结论。检视者要能照着抽查。

### R2. barrel 导入是重点排查对象

报告 §12.4 第 2 条点名了 `output-parser.test.ts`:它从 `executor-task` barrel
导入函数,而那个 barrel 会把整个 executor-task 模块图拖进来 ——
**看起来是纯解析测试,实际拉起一大片**。

⚠️ 报告同时警告:该文件「覆盖明细文件和 queue 中的流文本函数,**不能直接
认定为纯解析测试**」。所以不是无脑改 import,要先确认它到底用了什么。

把这类逐个查出来:**纯逻辑测试改为从实际模块导入**。这一项能独立降低
collect/transform 成本,是本票唯一的量化收益来源。

### R3. 混合文件:记下来,不急着拆

报告 §12.4 第 4 条允许「按验收责任拆开,保留原断言」。

但本票**倾向不拆**:拆文件会改变文件数与文件名,而基线报告的文件排名是按
当前文件名建立的 —— 拆了之后 T2 及后续的前后对照就断了。

**本票只在分类清单里标出「混合」并说明混了什么**;真要拆,留给 T2 连同
fixture 分组一起做,那时拆分与分组是同一个设计决策。

### R4. 拿不准的,保留重环境

报告 §12.4 第 5 条原文:「未确认依赖的测试**保留重环境**,避免错误优化」。

清单里允许出现「未确认」这一类,并写明为什么拿不准。**把它标成纯逻辑然后
出错,比标成未确认要糟得多** —— 后者只是少回收一点收益,前者会让 T2 基于
错误清单去掉某个文件真正需要的 fixture。

## 4. 验收标准

1. 分类清单**覆盖全部测试文件**(server 包全量;若含其它包,说明范围)。
   文件数与 CI run `34571914641` 采集到的 **129** 对齐,若有出入说明原因。
2. 每一项都写明**分类判据**(哪条 import / 哪个副作用),可抽查。
3. barrel 导入逐个列出;已改为直接导入的,列出改了哪些文件。
4. **断言一行未改**:`git diff` 里测试文件的改动只应出现在 import 段
   (以及必要的类型导入)。若有例外,逐条说明。
5. **`test/setup.ts`、`test/db.ts`、`vitest.config.ts` 一行未改**
  (`git diff --stat` 自证)。
6. 受影响测试文件的用例数与通过数**前后一致**
   (用 `node scripts/test-baseline.mjs packages/backend/server <文件...>` 取对照,
   清单写进汇报)。
7. 未新增任何只为测试存在的转发层;若某处不得不保留 barrel 导入,说明原因。
8. 明确给出**交给 T2 的结论**:哪些文件可以不要 DB fixture、哪些必须要、
   哪些未确认。

## 5. 不涉及的改动

- **不动 setup / fixture 生命周期**(T2)。
- **不拆混合文件**(§R3,留给 T2)。
- 不碰 `executor-queue.test.ts` 的执行位问题 —— 那是 CI 上最大的单文件
  (21.3%),但成因是假执行器 `sh` 的固有开销,属独立票。
- 不做任何测试逻辑优化。

## 6. 兼容性

无生产代码变更。测试的公共导出面若因移动函数而变化,需在汇报里列出并说明
既有调用方是否受影响。
