# Spec: 陈旧构建提示被无差别附加到所有结案拒绝上

> **状态**: Deferred — 等自动重建落地后重新评估(守卫由 10 降为 7,曝光面已显著缩小)
> **版本**: 1.0
> **日期**: 2026-08-26

## 现象

`coordinationCloseError` 只要检测到运行时陈旧,就给**任何**结案拒绝
追加同一句注解:

```ts
// packages/backend/server/src/routes/group/tasks.ts:90
function coordinationCloseError(message: string): BizError {
  const runtime = getRuntimeStatus();
  if (!runtime.stale) return new BizError(BizCodeEnum.InvalidRequest, message);
  return new BizError(
    BizCodeEnum.InvalidRequest,
    `${message} 注意:当前运行时为陈旧构建(staleReason: ${runtime.staleReason}),
     本次拒绝可能来自旧版守卫;若已在源码中修改结案规则,请在发起方重启后重试回写。`,
  );
}
```

该函数在同文件中被抛出 **11 处**,其中大部分与构建版本毫无关系 ——
提交归属校验、L1 层未发生、子任务未到终态、`claimAdjudication` 缺失等,
都是**当前构建下的真实业务拒绝**,换个新构建照样拒绝。

## 危害:这句注解会把执行器带偏,已经发生过

任务 `01a03da6` 的结案被**提交归属守卫**拒绝(提交 `9029dab0` 不在任何执行
子任务窗口内 —— 这是真实且正确的拒绝)。但它读到那句注解后,汇报写成:

> 「L2 功能检视已通过,但父任务 done 结案被**陈旧运行时的提交归属守卫**拒绝
> ……服务端明确返回 staleReason=build」

续跑任务 `01a03dd8` 也做了同样归因。**两条任务都把一个真实的归属问题
误判为「旧版守卫的误伤」**,于是都放弃修正、以 `failed` 收场。

检视者(我)最初也照单接收了这个说法,直到读代码才发现归属守卫和构建陈旧
毫无关系。⚠️ **一句无差别的注解,同时误导了执行器和检视者。**

## 决策

### R1. 注解只在拒绝确与构建版本相关时附加

`coordinationCloseError` 不得再对所有拒绝无差别追加。调用点需要显式表明
本次拒绝**是否可能因构建版本而不同**,只有可能不同的才附加注解。

⚠️ 默认必须是**不附加**。新增调用点若不表态,行为应是不加注解 ——
宁可少提示,不可误导。

### R2. 逐个调用点判定,不要一刀切

11 处调用点须逐一判断并在实现中给出结论。判据是:
**同样的输入,换成最新构建重跑,这条拒绝会消失吗?**

- 会消失 → 与构建相关,可附加注解
- 不会消失(提交确实不在窗口内、子任务确实非终态、字段确实缺失)
  → **不得**附加

⚠️ 不接受「全部改成不附加」的偷懒实现,也不接受「保留现状只改文案」。

### R3. 陈旧运行时本身仍要可见

本票**不删除**陈旧构建的告警能力 —— `/api/health` 的 `stale` /
`staleReason`、以及 `runtime-status.ts` 的启动日志,都保持原样。
本票只管**结案拒绝信息里那句注解的附加条件**。

### R4. 不改守卫本身的判定逻辑

⚠️ 归属守卫、L1 守卫、`claimAdjudication` 守卫的**判定规则一律不动**。
本票只改错误信息的构造。想放宽归属守卫是另一张票的事。

## 验收要点

- `coordinationCloseError` 的注解不再无差别附加,默认不加
- 11 处调用点逐一判定并有明确结论(实现或注释中可查)
- 单测:构建陈旧 + 归属校验失败 → 错误信息**不含** staleReason 字样
- 单测:构建陈旧 + 确与构建相关的拒绝 → 错误信息**仍含**注解
- `/api/health` 的 stale/staleReason 行为不变(回归覆盖)
- 各守卫判定逻辑未被修改(读 diff 确认)
- 测试全绿,贴出用例数
