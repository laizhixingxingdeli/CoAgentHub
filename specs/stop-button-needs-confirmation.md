# Spec: 停止按钮需要二次确认,防误触

> **状态**: Frozen — 2026-09-02
> **日期**: 2026-09-02
> **依赖**: [stop-button-cannot-interrupt-running-task.md](stop-button-cannot-interrupt-running-task.md)
> —— 先让按钮真的能停,再给它加确认;顺序反了会做出「确认一个不生效的动作」。

## 1. 问题

停止按钮**点下即执行**,全链路没有任何确认:

`ControlButton` → `onStop(task)` → `sendCommand(task, "停止 <id>")` → POST 消息。
`control-button.tsx` 只处理禁用态与提示,`requirement-workspace.tsx:559/:608`
直接发送。前端全仓没有 `AlertDialog`,`components/ui/` 下只有 `dialog.tsx`。

今天误触的代价已经是实的:对 `queued` 任务点一下,任务立即 `cancelled`。等
[前一票](stop-button-cannot-interrupt-running-task.md)落地后,误触将能杀掉一个
已经跑了一小时的进程 —— 代价从「取消一个还没开始的任务」变成「丢掉一小时工作」。

停止按钮与展开、折叠这些无害操作**在同一张卡片上并排**,尺寸相同、无视觉分级。

## 2. 验收

**R1 — 停止必须经过二次确认。** 点击「停止」不再直接发送指令,先弹确认;
只有确认才发送,取消则什么都不发(不发消息、不刷新、不置 `commandSending`)。

**R2 — 与仓内既有破坏性操作保持同一形态。** 本仓已有 6 处破坏性确认,全部是
`window.confirm(t(...))`(删除消息 `use-messages-page.ts:519`、归档群
`use-groups-page.ts:324`、移除成员 `members.tsx:463`、删除文件 `files/index.tsx:92`
等)。停止沿用同一形态与 i18n key 约定,**不为此引入自定义弹窗组件**
—— 一致性优先,且 `components/ui/` 下今天没有 `alert-dialog`。

**R3 — 确认文案必须说清停的是哪一个、会发生什么。** 至少包含:任务标识(短 id 或
执行器名 + 需求名,足以与同屏其它任务区分)、当前状态、以及后果一句话
(排队中 → 取消;运行中 → 终止正在运行的进程,已产出的改动不会自动回滚)。
**不接受只写「确定要停止吗?」** —— 判断的依据必须在弹窗里,不能要求人回到卡片上
核对(ADR-0009:判断要指名事实)。文案进 `lib/i18n/zh.ts`,带参数插值,
不硬编码在组件里。

**R4 — 禁用态与只读不变。** 无权限 / 归档只读时按钮仍禁用,且不弹框
(禁用按钮本就不触发点击)。`ControlButton` 现有 title 提示行为不变。

**R5 — 只加在停止上。** 展开、折叠、刷新等无害操作不受影响。

**R6 — 两处接线都要覆盖。** `requirement-workspace.tsx` 今天有**两处** `onStop`
接线(`:559` 需求详情、`:608` 无需求时回退的 TaskPanel),两处都必须走确认。
测试须分别覆盖,不接受只测一处(本会话曾因只跑一个测试文件而误判)。

## 3. 不涉及

- **不改回滚按钮。** 回滚同样无确认且更危险(`git reset --hard`),但那是独立一票。
  本票落地后应立即补一张,复用同一个确认组件。
- 不做自定义弹窗、不引入新依赖(见 R2)。若将来要把全仓 `window.confirm` 统一换成
  设计过的弹窗,那是一次独立的整体改动,不在本票内单点开特例。
- 不改停止指令本身的语义、权限、回执。

## 4. 实现提示(非约束)

确认判断建议收在一处(例如 `sendCommand` 之前的一个小 helper,或 `ControlButton`
的可选 `confirmText`),使**回滚**下一票能直接复用,而不是在两处 `onStop` 接线上
各写一遍 —— R6 的两处今天已经各自独立接线。
