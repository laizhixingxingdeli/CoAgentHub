# Spec: L2 复验范围 —— 定向复验 + 证据核对,不重跑全量

> **状态**: Landed — (2026-09-02 状态订正:DB 中该 specRef 有 13 个 done 任务为证;此前状态未随关票更新)
> **版本**: 1.2
> **日期**: 2026-08-29

## 1. 背景:同一套全量测试每票跑两遍

现状是 L1 与 L2 各跑一次全量测试:

- **L1**:执行器自检,跑 `pnpm --filter @laizhixingxingdeli/server test`。
- **L2**:协调者不信执行器的「测试全绿」声明,**重跑同一套全量**去核实。

L2 的动机是对的 —— `specs/verify-agent-claims.md` 的立场就是**声明不等于事实**;
首航报告 P4 记录过 L2 声称验证、实际没跑,结果放行了一个物理上不可能成立的结论。

但代价被实测量化了(2026-08-29):

```
全量 server 测试:59 文件 / 845 用例 / 372 秒
一张票 = L1 全量(~6min) + L2 全量(~6min) ≈ 12 分钟起
```

当天队列有十余张票,仅重复的全量重跑就占掉一个多小时,且 L2 还要为一份完整测试
输出付 token。**重跑的边际信息量极低**:同一棵工作树、同一个提交、同一套用例,
两次运行结果不同只可能来自 flake 或环境漂移,而这两者恰恰不是 L2 要防的东西
(L2 要防的是「执行器谎报」)。

## 2. 决策

**L2 改为「定向复验 + 证据核对」,不重跑全量。**

| 层 | 测试范围 |
|---|---|
| **L1(执行器)** | 跑**全量** + `check-types`,并在汇报中写明全量结果(文件数 / 用例数 / 是否全绿) |
| **L2(协调者)** | **只重跑本票定向的测试文件** + `check-types`;核对 L1 汇报里的全量结果证据是否存在且自洽 |

### 2.1 为什么不是「L2 全信 L1」

定向复验**仍然是实测**,不是采信声明:本票改了什么,就跑什么。L2 亲手验证的仍是
「这次改动本身是否达成验收标准」——那正是 L2 的职责(功能性验收)。让渡出去的只有
「改动是否在**别处**引入回归」这一项。

### 2.2 让渡的那项由什么兜底

**下一张票的 L1 全量。** 队列串行推进,每张票的 L1 都跑全量,因此任何回归最多
**晚一票**暴露,且暴露时工作树里只多了一个提交,定位成本极低。

⚠️ 这是一个**明码标价的取舍**,不是「反正没事」:代价是回归的发现被推迟一票;
收益是每票省一次全量重跑与一份完整测试输出的 token。**批次收尾时必须补一次全量**
(见 R3),把推迟的风险收口。

## 3. 详细改动

### R1 — 协调者 skill 的 L2 段

`skills/coordinator/SKILL.md` 的 L2 验收部分明确:

- L2 **不重跑全量测试**;跑本票定向测试文件 + `check-types`。
- L2 **必须核对** L1 汇报中的全量结果证据;证据缺失或与汇报矛盾时,
  **要求执行器补跑并重新汇报**,不得自行跑全量替它补齐(那会把 L2 变成 L1)。
- 「定向」的判定依据是**本票任务书声明的改动范围**,不是执行器自己说改了哪些文件。

### R2 — 检视者写票的验收模板

检视者下发的任务书,「验收」一节按上表分列 L1 / L2 两行范围,不再笼统写
「`pnpm test` 全绿」。本 spec 冻结后的新票一律采用。

### R3 — 批次收尾补一次全量

一个批次(或一组连续修复票)的**最后一张**票,L2 **恢复全量重跑**,把期间让渡的
回归风险一次性收口。批次边界由检视者在票面显式标注(`本票为批次收尾,L2 需全量`)。

### R4 — 不改的东西

- `verify-agent-claims` / `l2-must-read-claim-verification` 的**提交核实**逻辑不动:
  claimVerification 与 claimAdjudication 照旧,与测试范围无关。
- L1 的自检范围不动(仍是全量)。
- L3 的架构检视范围不动(它本就不做功能验收)。

### R5 — 长命令必须保持流式输出(v1.1 新增)

跑测试这类长命令时,**不得用 `| tail` / `| head` 之类把输出憋到命令结束才吐的管道**。

实证(2026-08-29,任务 01a04dc6):执行器跑

    npx vitest run 2>&1 | tail -80

`tail` 直到命令结束才输出,于是整整 **13 分钟零输出**。而平台的判死口径正是
「静默」——`stallAlertMinutes: 15` 告警、`stallTimeoutMinutes: 30` 判死。
测试本身只要 6 分钟,是这条管道把它变成了逼近告警线的完全静默;并发跑全量时
(L1 与另一票的 L2 抢同一台机器)极可能真的撞线被判死。

要求:**持续,且有界** —— 两个约束同时成立,缺一条都不合格。

`| tail -80` 当初并非乱写:它同时在**限制执行器自己的上下文**。若只按「要持续输出」
理解,把默认 reporter 直接倒出来,845 个用例就是 845 行,执行器与读 outputTail 的
协调者都要为它付 token —— 那是用 token 换静默风险,拆东墙补西墙。

| 命令形态 | 执行期间输出 | 判定 |
|---|---|---|
| `\| tail -80` | 0 行(结束才吐) | ❌ 静默,逼近判死线 |
| 默认 reporter 直接流 | ~845 行(逐用例) | ❌ 无界,token 浪费 |
| **按文件粒度 / dot reporter** | ~59 行 / 每用例一字符 | ✅ 持续且有界 |

- **心跳粒度按文件,不按用例**;或用 dot 类 reporter(一个用例一个字符)。
  执行期间的输出行数应与**文件数**同量级(数十行),不是**用例数**(数百上千行)。
- 或 `tee` 到文件 + **行缓冲**过滤(`grep --line-buffered`、`awk` 需 `fflush`),
  只让「文件级通过/失败/最终统计」流出,全文留在文件里,结束后按需取尾。
  ⚠️ 管道任一级不行缓冲,过滤结果就会卡在缓冲区里,等于没流。
- 明确禁止的是**两个极端**:零输出,以及全量倒灌。
- 该规则对 L1 与 L2 同等适用,也适用于任何预期超过数分钟的命令(构建、迁移、e2e)。
- 检视者写票时把本条写进任务书;执行器与协调者据此选择命令形态。

## 4. 验收标准

1. `skills/coordinator/SKILL.md` 的 L2 段含 R1 三条,且明确「不重跑全量」。
2. 该 skill 经 `GET /api/skills/coordinator` 返回的内容与仓库一致(指纹相同)。
3. 一张新票走完全流程:L1 汇报含全量结果(文件数/用例数);L2 汇报显示**只跑了
   定向测试 + check-types**,并引用了 L1 的全量证据。
4. 构造 L1 汇报**缺失**全量证据的情形:L2 要求补跑并重新汇报,
   **不自行跑全量替代**。
5. 标注「批次收尾」的票:L2 恢复全量重跑(R3)。
6. 既有 coordinator skill 相关测试全绿。
7. (v1.1)任务书模板含 R5;一次真实长命令执行期间,任务 outputTail **持续增长**,
   不出现数分钟零输出的窗口。
8. (v1.2)同一次全量测试,执行期间产生的输出行数与**文件数**同量级(数十行),
   **不是**用例数量级(数百上千行);即持续与有界同时成立。

## 5. 不涉及

- 不改测试本身的执行速度(全量 372 秒里很大一块是执行器队列的真实等待用例,
  提速属另一张票)。
- 不引入测试结果缓存 / 增量测试选择(turbo 缓存等),那是更大的工程。
- 不改 L1 的范围,也不改 L3。
