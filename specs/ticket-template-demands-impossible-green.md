# Spec: 平台任务书要求「测试全绿后提交」,而本机永远不可能全绿

> **状态**: Landed — L3 通过(2026-09-08),实现 `3a4bb2e6`(Pi 直连实施,
> 检视者完成 L2/L3)。
> L2:`buildTicket` 范围内「全绿」字样已清零;新文案三要素齐全并点名
> `scripts/test-baseline.mjs`;R4 要求保留的「不动 schema/迁移/scripts」句原样保留。
> **基线对照:改前 = 改后 = `18 failed | 47 passed (65)`,失败数一条未增。**
> 其中改前那一跑由**检视者补做** —— 执行器如实报告「未单独取
> `executor-report-quota` 改前基线,无法用数字证明改前也是 9 红」,
> 没有把推测写成结论;检视者据此补测确认。
> 执行器另记一条待清扫项:`parseTaskReport` 的测试夹具仍含旧句
> 「完成后必须运行测试…」,不影响解析语义,另票处理。
> **版本**: 1.0
> **日期**: 2026-09-08
> **来源**: 2026-09-08 检视者在「平台是否可以恢复使用」的核查中发现。
> **前置**: `docs-drift-sync-2026-09-07.md`(Landed)已把 AGENTS.md 改成新口径,
> 但**平台自己生成的任务书没跟着改** —— 文档与平台行为再次漂移。

## 1. 背景与目标

### 1.1 现状证据

`packages/backend/server/src/lib/executor-task/queue.ts` 的 `buildTicket()`
(第 3936 行)固化了这一行:

```
默认约束(除非消息里明确说明):不动 schema/迁移/scripts/ 下其他脚本、
不删数据;测试全绿后提交,commit message 按功能写。
```

同段第 3933 行还有:

```
- 完成后必须运行测试并验证改动(新增/相关用例),汇报需包含测试结果。
```

**「测试全绿后提交」在本机不可能达成**:后端红基线 **129 failed / 924 passed**
(2026-09-07 实测)。执行器要么陷在无法满足的条件里反复重试,要么无视它 ——
两种都坏。

D1(`e3ed2cb8`)已把 AGENTS.md 改成「票面给显式测试文件清单、口径是失败数不增加」,
但那只改了**给人读的文档**;**平台派发时生成的任务书仍在下达旧指令**。

### 1.2 危害

这是 R2 那轮的同款陷阱换了个入口:当时 CodeBuddy 按 AGENTS.md 跑全量回归,
在一张票上白耗 40 分钟。现在文档修好了,**平台自己成了旧口径的最后一个发声者**。

恢复走平台链路后,**每一张平台票都会带着这条不可能满足的指令下去**。

### 1.3 目标

任务书里的测试指引与 AGENTS.md 当前口径一致,且**可执行**。

## 2. 改动范围

| 文件 | 改什么 |
|---|---|
| `packages/backend/server/src/lib/executor-task/queue.ts` | `buildTicket()` 的「执行与测试要求」段与「默认约束」行 |
| 断言任务书正文的测试文件 | 随模板同步(见 R3) |

**不改**:`buildTicket` 的其它段落(关联规范、本群分工、汇报格式要求、ReplyMode 等);
任何调度/队列/派发逻辑;AGENTS.md(D1 已改)。

## 3. 详细改动

### R1. 「测试全绿后提交」改为可达成的口径

替换为与 AGENTS.md 一致的表述,至少表达三件事:

1. **跑票面指定的测试文件清单**,而不是全量;
2. **口径是「失败数不增加」**,不是「全绿」—— 并说明理由(本机存在既有红基线);
3. **改动前先取一次基线**,改动后再取一次,汇报里给出前后对照。

### R2. 指出取基线的现成工具

任务书里点名 `scripts/test-baseline.mjs`(已 Landed,`50a5f6dc`),给出用法一行:

```
node scripts/test-baseline.mjs <包目录> <测试文件...>
```

这是让新口径**可执行**的关键 —— 只说「失败数不增加」而不给取数手段,
执行器仍要手工跑、手工数。

### R3. 同步断言任务书正文的测试

改模板会打断既有断言。**自己找出所有断言该段落的测试文件并同步**
(至少 `executor-trigger.test.ts` 里有多条断言任务书内容的用例)。

⚠️ **同步的是断言里的期望文本,不是测试意图**。若某条用例的意图就是
「任务书必须要求全绿」,那条用例本身也过时了 —— 按新契约改写,并在汇报里
逐条说明改了哪些、为什么。

### R4. 不扩大范围

「不动 schema/迁移/scripts/ 下其他脚本」这句保持不变。它已有
「除非消息里明确说明」的兜底,票面可以覆盖,不是缺陷。

## 4. 验收标准

1. **模板不再要求全绿**:`grep -n "全绿" packages/backend/server/src/lib/executor-task/queue.ts`
   在 `buildTicket` 范围内**无输出**(若别处有无关的「全绿」字样,在汇报里说明行号归属)。
2. **模板包含新口径三要素**:票面清单 / 失败数不增加 / 前后基线对照。
   贴出改动后的该段完整文本。
3. **模板点名基线工具**:含 `scripts/test-baseline.mjs` 及一行用法。
4. **断言同步**:改动触及的测试文件全部同步;逐条说明改了哪些断言、为什么。
5. **定向测试**:用基线工具取改动前后对照(命令与文件清单由你按实际触及面确定,
   至少含 `test/executor-trigger.test.ts`),口径**失败数不增加**。
   ⚠️ 该文件属于尚未迁移的 20 个之一,**基线本身是红的**,别当成你造成的。
6. `cd packages/backend/server && npx tsc --noEmit -p tsconfig.json` 通过。

## 5. 不涉及的改动

- 不改 AGENTS.md(D1 已改)。
- 不改调度/队列/派发逻辑。
- 不迁移其余测试文件到跨平台假执行器(那是另一张票)。
- 不改「不动 schema/迁移/scripts」那句(R4)。

## 6. 兼容性

- 只影响**新派发任务**的任务书正文;在途任务不受影响。
- server 代码改动 → 需重新构建并重启(由检视者执行)。
