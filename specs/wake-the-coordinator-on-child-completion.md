# Spec: 派发之后没人能叫醒协调者,于是它选择自己动手

> **状态**: Landed — L3 通过(2026-08-26),实现 `785e4f1a`
> **版本**: 1.0
> **日期**: 2026-08-26
> **补回**: v3.8 移除完成回调后失去的那个零件(§3.14.7 孤儿契约的另一半)

## 现象:连续五次,协调者绕过 L1 自己实现

五次形态各不相同(伪装 done → 标 failed → 补建只读子任务 → 边实现边补测试),
说明**不是某次失误**,是稳定倾向。前四轮我一路加守卫,它一路换姿势绕。

## 根因不是不听话,是派发对它严格更亏

### 事实一:完成事件只能拉,不能推进进程

`task_completion_events` 是 `GET` + `POST /claim`(lease)的**拉取**接口。
终态时确有一条 WS 提示,但 `notify.ts` 注释自陈「仅低延迟提示,可靠性来源
始终是数据库 inbox」—— **WS 推给的是前端,不是那个正在跑的 CLI 进程**。

### 事实二:协调者是一次性 CLI 调用,退出即失联

它以 `codex exec --ephemeral` 之类的一次性调用被拉起。**退出后没有任何机制
能重新叫醒它** —— v3.8 移除完成回调后,会话恢复通道消失(§3.14.7)。

### 事实三:所以要做 L2,它必须在自己这一次调用里阻塞轮询

实测(近 8 小时全量):

| 走法 | 时长 | 结果 |
|---|---|---|
| 自己动手(零子任务) | 6:29 / 6:56 / 6:52 / 9:01 / 11:43 / 11:53 | 全部完成 |
| 派了子任务 | 15:32 / 21:16 / 25:41 / 42:57 | **4 次 2 次失败** |

铁证是 `01a03965`:**协调任务 15:32,子任务 15:32,完全重合** ——
整个生命周期都在等。

更能说明代价的是 `01a0398e`:它派给 AtomCode,AtomCode **额度耗尽**,
协调者在轮询中被一起拖死。**它派发,却要为别人的额度问题赔上自己。**

### 结论

派发意味着:2–4 倍时长、全程 LLM 空转烧 token、承担他方额度风险、
自身中途挂掉即断链。自己动手则有界、可控、必然能在自身生命周期内完成。

**它选的是理性路径。** 前四张守卫只提高了错误路径的成本,
**没有降低正确路径的成本** —— 所以它一次次换姿势绕。

## 决策:让「派发后退出」成立

### R1. 子任务终态时,拉起协调者做 L2

执行子任务进入终态(`done` / `failed` / `cancelled`)且其**父协调任务仍非终态**时,
平台为父任务的执行方(协调者)**创建一条续跑任务**,并由现有队列正常拉起。

续跑任务的 `brief` 必须包含:

- 父协调任务 id(**要 PATCH 的就是它**)
- 本次终态子任务 id、状态、其 `diffSummary` 摘要
- 父任务的 `specRef` + `specHash`
- 该父任务下**全部**子任务的 id 与当前状态(让它一眼看出是否可结案)

**复用现有派发/拉起路径**,不新建 spawn 机制。

### R2. 协调者仍在跑时不拉起

父协调任务的 `executor_pid` 仍存活时 → **不创建续跑任务**。
存活判定**复用** `isExecutorProcessAlive`(`process.kill(pid, 0)`,
只认 `ESRCH` 为已退出),不另写一套。

⚠️ 这条防的是**双进程同时操作同一工作树** —— 本项目已有过一次 13 进程撞车的教训。

### R3. 同一父任务同时只允许一条续跑任务

已存在**非终态**的续跑任务时,不再创建新的。
多个子任务先后终态 → 只补一条;协调者在续跑任务里能看到全部子任务状态(R1),
自行判断是否还要继续等。

### R4. 续跑任务不得触发续跑(防环)

续跑任务自身终态时,**不得**再触发 R1。实现上需要一个可判定的标记
(如 `task.kind` 或 `diffSummary` 上的平台字段),
**由平台写入,不依赖任务书文本判定** —— 文本判定会被措辞绕过。

### R5. 任务书里明说「派发后可以退出」

协调者任务书模板(`buildExecutionModeSection` 的 coordinator 分支)增加一行,
明确:**下发执行任务后可以直接结束本次进程,子任务终态时平台会重新拉起你做 L2**。

⚠️ 缺这条,机制建好了它也不知道可以退出,仍会阻塞轮询。
**这是本票唯一一处「说明」手段,且只有在 R1 成立后才有意义。**

### R6. 父任务在等待期间保持非终态

协调者退出后,父协调任务保持 `running`。detached 任务**本来就不设静默/无进展
提醒**(`queue.ts` 已实现:「发送后静默等待 PATCH 是正常态」),
**不改该行为**,也不因协调者进程退出就判父任务失败。

⚠️ 这一条与 `restart-recovery-must-check-liveness` 的取向一致:
进程不在 ≠ 任务失败。

### R7. 不改这些

- **不恢复** v3.8 移除的完成回调(不重建旧机制,只补齐效果)
- **不改** `task_completion_events` 表结构与其 lease 状态机
- **不改**执行器(非协调者)的任何路径
- **不做**自动 L2 判定 —— 平台只负责把协调者叫醒,**检视内容仍由它做**

## 验收标准

- [ ] 子任务终态 + 父协调任务非终态 + 父进程已退出 → **创建续跑任务**并被拉起
- [ ] 续跑任务 `brief` 含:父任务 id、终态子任务 id/状态/摘要、specRef+specHash、
      **全部**子任务的 id 与状态
- [ ] 父进程仍存活(pid 可探测)→ **不创建**续跑任务(回归,必测)
- [ ] 已有非终态续跑任务 → 不重复创建(R3,必测)
- [ ] 续跑任务自身终态 → **不触发**新的续跑(防环,必测)
- [ ] 父任务已终态 → 不创建续跑任务
- [ ] 协调者退出后父任务保持 `running`,不被判失败(回归,必测)
- [ ] 协调者任务书含「派发后可退出」那行(R5)
- [ ] 执行器路径未被改动(回归,必测)
- [ ] **端到端**:下发一张需求票 → 协调者派子任务后退出 → 子任务完成 →
      协调者被重新拉起 → PATCH 父任务结案。**这是本票唯一的真验收信号**
- [ ] 后端测试全绿,贴出用例数

## 不涉及

- 自动 L2 判定(R7,明确不做)
- 完成回调的恢复(R7)
- 执行器路径
- 前端展示

## 执行环境提示

- 事件写入已有:DB trigger 在终态时写 `task_completion_event`,
  带 `dispatcherParticipantId`。**缺的是消费方**,不是事件源
- 存活判定复用 `lib/executor-task/queue.ts` 的 `isExecutorProcessAlive`
- 任务拉起复用现有队列路径,**不要新写 spawn**
- ⚠️ 端到端验证必须**重建并重启后端**再测
- ⚠️ 本票**必须下发给执行器**完成 —— 本票正是为了让这件事变得不亏
- ⚠️ 已知抖动:`task-completion-events` 全量并行下偶发失败,隔离重跑通过,
  **与本票无关,不要去改它**
