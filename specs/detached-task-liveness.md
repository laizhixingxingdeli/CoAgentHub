# Spec: 悬空 detached 任务的存活探测

> **状态**: Landed — L3 通过(2026-08-24),实现 `9f789f9a`
> **版本**: 1.0
> **日期**: 2026-08-24

## 背景

协调者收到检视者的 detached 任务后,若进程异常退出而**从未 PATCH 终态**,
平台目前只有一道防线:24 小时兜底(`detachedTimeoutMinutes` 缺省 1440 分钟)。

`coordination-activity-visibility` 已经落地的机制**只在任务落终态时触发**——
它照亮的是「协调任务完成/失败了,汇报一下过程」,但**这次要处理的恰恰是
永远到不了终态的那种**:协调者进程死了,任务卡在 `running`,没有任何后续事件。
刚落地的机制照不亮这种情况,不是它的锅,是它解决的是另一个问题。

**实际后果**:检视者(或用户)发出一张 detached 任务后,唯一能知道「这条链断了」
的方式是**傻等到 24 小时**,期间界面上这条任务就是安静地显示 `running`,
和「协调者正在认真工作」没有任何视觉区别。

## 决策

给 `running` 状态的 detached 任务加一道**远短于 24 小时**的存活探测阈值,
超过阈值仍无任何进展信号 → 标记为**需要关注**,不是直接判失败。

### 为什么不直接判失败

协调者一次 L2/L3 编排可能确实需要较长时间(等执行器、等限额冷却、多轮重下发)。
探测阈值要给这种合法的长耗时留空间,**目标是把「不知道」变成「知道但还在等」
或「知道已经断了」,不是缩短允许的工作时长**。

## 要求

### R1. 存活信号是什么

以下任一发生都算「还活着」,刷新存活时钟:

- `outputTail` 有更新(进程仍在产生输出)
- 任务状态发生变化(不含终态,终态走既有 24h 逻辑之外的正常结案路径)
- 该协调任务名下**新建了子任务**(`parentTaskId` 指向它)——协调者仍在派发工作

### R2. 阈值

**30 分钟**无任何 R1 信号 → 标记为「需要关注」。

理由:协调者单次 L2 检视 + 决策通常是分钟级;30 分钟已经远超正常单步耗时,
同时留了足够余量给一次限额冷却重试(skill §2.2 提到的冷却是「全忙时」的
兜底路径,不常态发生)。**不要**把这个数字当作精确科学结论,若执行者有更好的
数据支撑其它取值,可在汇报中提出并说明理由,但要给出理由,不能拍脑袋改。

### R3. 「需要关注」不是终态,是一个可查询的派生状态

- **不修改** `task.status`——探测结果不改变任务本身的状态机
- 通过一个轻量机制暴露:可以是任务详情里的一个派生字段(如
  `livenessWarning: boolean` + `lastSignalAt`),或一条独立的审计记录,
  **执行者可自行选择实现形态**,但必须满足:
  - **前端可查询并展示**(为后续可能的 UI 提示留接口,本票不做 UI)
  - 不需要轮询额外的重量级计算——判定逻辑应该能在读任务详情时**顺带算出**
    (比较 `updatedAt`/最近子任务时间 与当前时间),不需要常驻定时任务

### R4. 探测只针对 detached 任务

普通(非 detached)任务已经有别的监控路径(`task_stall_alert` 等),
**本票不重复覆盖**。只处理「检视者下发给协调者、等待其 PATCH 回写」的那一类。

### R5. 不做自动补救

探测到「需要关注」**不触发**任何自动重试、自动通知、自动终止。本票只负责
**让这件事变得可查询**,不负责响应它。若后续想接一条通知或 UI 展示,
另开票。

## 验收标准

- [ ] detached 任务超过 30 分钟无 R1 定义的任何存活信号,可查询到「需要关注」
- [ ] `outputTail` 更新、状态变化、新建子任务 三种信号任一发生都刷新判定
- [ ] 判定不修改 `task.status`
- [ ] 判定逻辑可在读详情时顺带计算,**未新增常驻轮询任务**
- [ ] 30 分钟内有活动的任务不被误标
- [ ] 已落终态的任务不参与本判定(与 24h 兜底不冲突,两者可共存)
- [ ] 后端测试覆盖:无信号超时被标记 / 有信号不被标记 / 终态任务不参与,三条都要有
- [ ] 后端测试全绿,贴出用例数
- [ ] **未改动**前端(本票只做后端可查询,UI 展示另开票)

## 不涉及

- 前端如何展示「需要关注」(另开票)
- 自动重试/自动通知
- 非 detached 任务的存活探测(已有别的机制)
- 24 小时兜底逻辑本身(保留,两者并存,前者是早期预警,后者是最终兜底)

## 执行环境提示

- 后端 `:3001`,数据库改动记得执行迁移(若判定信号需要新列)
- 实测时可人为造一个 detached 任务,故意不 PATCH,等待/调整阈值验证
