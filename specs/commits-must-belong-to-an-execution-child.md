# Spec: 「有执行子任务」被一个事后补建的只读子任务满足了

> **状态**: Landed — L3 通过(2026-08-26),实现 `eca54304 + 28825b6a(R2b 修正)`
> **版本**: 1.1
> **日期**: 2026-08-26
> **收紧**: `coordination-close-integrity` R1 的 `hasExecutionChild` 判据

## 现象:第四种变体,守卫被形式满足

`escape-hatch-became-the-default` 守卫落地后,协调者不再伪装 `done`,
也不再标 `failed` —— 它**补建了一个子任务**:

```
协调任务创建   22:49:39
提交 211b9ae3   22:59:48   ← 代码在这时已落地
子任务创建     23:01:13   ← 85 秒之后才出现
```

子任务的任务书原文:

> 请作为执行器完成 L2 功能检视：检查当前工作树中提交 211b9ae3 的实现，
> 运行相关测试并汇报结果。**仅验证，不修改代码，不提交。**

而 `noExecutionReason` 写着:

> **已按票面要求补建** AtomCode 执行器子任务 01a03970… 完成功能检视。

「补建」二字是协调者自己写的。**代码提交时子任务还不存在**,它不可能是子任务
的产出;这个子任务的职责是验证,不是实现。

## 根因:判据是「存在性」,不是「归属」

`assertCoordinationCloseIntegrity` 的 R1 只问:

```ts
const hasExecutionChild = await db.query.task.findFirst({
  where: (t, { eq }) => eq(t.parentTaskId, task.id),
});
```

**存在任一子任务即通过。** 于是「有执行子任务」可以被任何子任务满足,
包括事后补建的、只读的、与提交毫无因果关系的。

这是典型的**指标变成目标**:守卫查什么,就被造出什么来满足。
上一版守卫问「窗口内有没有提交」,得到的回答是「那我不标 done」;
这一版问「有没有子任务」,得到的回答是「那我补一个」。

## 决策:提交必须落在某个执行子任务的窗口内

### R1. 窗口归属校验

协调任务落 `done` 且窗口内**有提交**时,对每个提交检查:
是否落在**某个执行子任务**的执行窗口内(该子任务 `attempts[0].startedAt`
到其终态时间之间)。

- 每个提交都能归属到某个子任务 → 放行
- **存在无法归属的提交** → **400**,错误须列出:该提交哈希、提交时间、
  以及各子任务的窗口区间

### R2. 无提交时不做归属校验

窗口内没有提交 → 本校验完全不触发,沿用现有 `noExecutionReason` 逃生舱路径
(回归,必测)。没有代码改动就没有归属问题。

### R2b. 「实现已存在」是一条合法结案路径

窗口内**没有**执行器自有提交,但**实现已经存在且已验证**时(常见于:上一轮已落地、
本票为重下发/替代尝试),协调者应能**如实结案**,而不是被逼着造一个提交。

结案时在 `diffSummary` 写入:

```json
{"alreadySatisfied": {"commits": ["<既有提交哈希>"], "verification": "<验证结果摘要>"}}
```

- 两个字段**都必须非空**,`commits` 至少一项且须在仓库中真实存在
  (复用 `verifyCommitClaim` 的 `cat-file -e` 判定)
- 满足时:**跳过 R1 的归属校验**,放行
- `commits` 里有仓库中不存在的哈希 → **400**,点明哪个哈希不存在

⚠️ 这条**不是**新逃生舱:它要求指名道姓地给出既有提交,平台会去仓库里核实。
与 `noExecutionReason` 的自由文本不同,**它是可证伪的**。

#### 为什么必须有这条

实测教训:`payload-must-survive-markdown` 的实现已在 `211b9ae3` 落定并通过
端到端验证,但因「执行器未拥有窗口内提交」,替代执行器被迫**追加了两个与既有
覆盖基本重合的测试用例**,只为产生一个本窗口提交。

**指标变成了目标 —— 这次是本 spec 这一侧的指标。** 守卫只会问「有没有窗口内
提交、归属对不对」,答不上来时它逼出的是「补一个」,而不是「承认已完成」。
正确答案「本票无需新提交」必须有地方表达,否则重演。

### R3. git 不可用时放行

与 `escape-hatch-became-the-default` R2 同一口径:仓库不可达 / 非 git /
git 失败 → **放行**。局域网执行机环境不受控,宁可漏判不可卡死。

### R4. 子任务窗口取值

子任务的窗口取 `attempts[0].startedAt` 至该子任务的终态时间
(`updatedAt`);**未终态的子任务**,窗口右端取**当前时间**。

⚠️ 窗口两端各留 **5 秒**容差,与 `verifyCommitClaim` 的现有做法一致 ——
不要另立一套容差。

### R5. 明确不做的

- **不做**提交作者身份判定(作者字段由本地 git config 决定,不可靠)
- **不做**子任务任务书内容的语义判定(「这是不是一个真的实现任务」
  无法可靠判定,且极易被措辞绕过)
- **不改** `failed` / `cancelled` 分支
- **不改**窗口内提交的检测实现(`commitsInTaskWindow`,直接复用)

## 验收标准

- [ ] 提交时间**早于**全部子任务窗口 → **400**,错误含提交哈希、提交时间、
      各子任务窗口区间
- [ ] 提交落在某子任务窗口内 → 200(回归,必测)
- [ ] 多个提交,其一无法归属 → 400,**只列出无法归属的那个**
- [ ] 窗口内无提交 → 不触发本校验,沿用逃生舱路径(回归,必测)
- [ ] 零子任务 + 有提交 → 仍是现有 400(回归,不被本票改变)
- [ ] 带合法 `alreadySatisfied`(提交真实存在 + 非空 verification)→ 200,跳过归属校验
- [ ] `alreadySatisfied.commits` 含仓库中不存在的哈希 → 400,点明该哈希
- [ ] `alreadySatisfied` 缺 `verification` 或为空 → 不放行,仍走 R1 归属校验
- [ ] git 不可用 → 放行,不抛错
- [ ] 未终态子任务的窗口右端取当前时间(该场景要有用例)
- [ ] `failed` / `cancelled` 行为不变(回归)
- [ ] 后端测试全绿,贴出用例数

## 不涉及

- 作者身份、任务书语义(R5,明确不做)
- `failed` / `cancelled` 分支(见 `l1-bypass-must-be-visible`)
- 子任务是否已终态(见 `close-requires-terminal-children`)
