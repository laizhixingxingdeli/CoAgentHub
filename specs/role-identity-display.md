> **版本**: 1.0

> **前置**: `specs/participant-name-not-a-key.md`(`b68b03c`)—— 改名要先解开路由绑定

## 现状:有色板,但形同虚设

`index.css:104-108` 定义了四个角色色 token(亮/暗两套):

| 角色 | 色 |
|---|---|
| coordinator | 蓝 |
| reviewer | 紫 |
| executor | **中性灰** |
| human | 浅灰 |

**全仓只有一个文件消费它**:`RequirementTimeline.tsx`,而且只用在**头像底色**上
(`ROLE_AVATAR_CLASS`)。左栏、阶梯、群列表、侧栏、设置页——全无角色标识。

### 三个问题

1. **名字压过颜色。** 即使头像是"协调者蓝",旁边写着「Codex **执行器**」——
   文字永远比颜色强,那点颜色信息直接被淹掉。
2. **颜色本身不够。** executor 是中性灰(等于没标识);蓝/紫/灰三个色相靠得近,
   对辨色障碍不友好;只有底色、没有文字,悬停也不出角色名。
3. **该有的地方没有。** 「这个群是三层还是两层」是 spec v3.9 §3.14.5 的模式判据,
   用户完全看不见。

## 要求

### R1. 改掉编码了角色的 participant 名字

前置票 `b68b03c` 解开路由绑定后,把名字改成不含角色的形式:

| 现名 | 改成 |
|---|---|
| AtomCode 执行器 | AtomCode |
| Codex 执行器 | Codex |
| Reasoning 执行器 | Reasoning |
| CodeBuddy 执行器 | CodeBuddy |
| Reviewer 检视器 | (自行判断,保持可辨识) |

- **角色由群成员关系决定,不写进名字**——同一 participant 在不同群可持有不同角色
- ⚠️ **改名前必须确认 `b68b03c` 已落地并生效**。前置未满足就改,会打断任务路由
- 历史消息显示的发送者名会跟着变(存的是 senderId),**这是预期行为**,用户已确认不介意

### R2. 角色标识必须文字化,不能只靠颜色

- 用**角色徽章**(文字 + 颜色),不是纯色块
- 现有 `roleLabel()`(`pages/app/groups/messages/types.ts:24`)已做 i18n 映射,**复用它**
- 保留现有 `--role-*` token,**不要新造颜色**;但 executor 的中性灰若在徽章形态下
  辨识度不足,可调整该 token 值(**在汇报里说明改了什么、为什么**)

### R3. 用到该用的地方

至少覆盖:

- **阶梯标签**——现在是「执行者 · 任务名」,那个"执行者"是**回落文案**
  (`RequirementDetailPanel.tsx` 里 `?? "执行者"`),不是真角色
- **设置页成员列表**——现有 `roleLabel` 只是纯文字,无视觉区分
- **群列表 / 侧栏**——让「这个群有没有 reviewer + coordinator」可见,
  即 v3.9 §3.14.5 的三层/两层判据

⚠️ **与已排队的票有交叠**:`group-list-row-signal`(`9273fce`)也要改群列表行,
`timeline-readability` 系列碰时间线。**若那些票已落地,在其成果上增补,不要回退它们**;
若未落地,只做本票范围,**不要顺手把那些票的内容一起做了**。

### R4. 模式显示要按 v3.9 判据

若实现「三层/两层」显示:

- 判据是**同时存在 reviewer 与 coordinator 成员** → 三层;否则两层(v3.9 §3.14.5)
- **不要用「有无 reviewer」**——那是 v3.8 的旧判据,已被修订
- **不存模式字段、不加配置项**,由成员构成实时推导
