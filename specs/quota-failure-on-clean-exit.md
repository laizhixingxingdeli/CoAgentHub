# Spec: 执行器"礼貌地报告限额然后正常退出"被判成成功

> **状态**: v1.0 Landed(L3 通过 2026-08-24,实现 `09fb53ce`);
> **v1.2 新增 R9,Ready for Implementation**
> **版本**: 1.2
> **日期**: 2026-08-31
> **发现于**: 两方编制冒烟验证 —— AtomCode 触发 5 小时限额,输出
>   `[rate-limited] 5h window exhausted — resets around 13:33`,**未产出任何文件**,
>   任务却落 `done`

## 背景

平台已有完整的额度处理机制:`isQuotaFailure()` 按 `dispatch-policy.json` 的
`rateLimit.detectPatterns` 匹配关键词(其中就包含 `window exhausted`),命中后
冷却该执行器、不自动重试、回传预计恢复时间。

**但它只在两条分支里被调用**(`queue.ts`):

| 行 | 分支 |
|---|---|
| 1261 | 执行**超时** |
| 1365 | 进程**失败**(非零退出) |

AtomCode 这次是**正常退出(exit 0)**:它检测到自己额度耗尽,礼貌地打印一行说明
然后干净退出。走的是成功路径,`isQuotaFailure` **根本没被调用**。

结果:

```
status: done
diffSummary.summary: "[rate-limited] 5h window exhausted — resets around 13:33"
```

**任务被标成完成,而它什么都没做。** 产出文件不存在,没有提交,没有冷却,
没有重试,也没有任何警示。

### 为什么这是真缺陷而不是执行器的问题

执行器的行为是合理的 —— 遇到额度限制时干净退出、说明原因,比崩溃或挂死好。
**平台不该把"进程退出码"等同于"任务成功"。**

而且这个洞比它看起来更宽:任何执行器**礼貌地放弃**(额度、缺少凭据、环境不满足)
都会被记成成功。本轮已经建立的三层强制全部建立在「子任务终态可信」之上 ——
`coordination-close-integrity` 的 R1 只数子任务**存不存在**,不看它是不是真干了活。
一个 `done` 但空转的子任务足以骗过 L1 层的强制。

## 要求

### R1. 成功路径也要过额度检测

进程**正常退出**时,同样以输出尾部(与现有两条分支同界:`lastLinesOf(out, 20)`)
调用 `isQuotaFailure()`。命中 → **按额度失败处理**,与 1365 分支**行为完全一致**:

- 任务落 `failed`,不落 `done`
- 冷却该执行器(`executorCooldowns`)
- **不自动重试**(额度是外部约束,重试只会再撞一次)
- 回传注明预计恢复时间(复用 `parseRateLimitRecoveryMs` + `formatEta`)

**复用现有代码路径,不要另写一套额度处理。** 若 1365 分支的处理逻辑可抽出共用,
抽出;不能则确保两处行为逐条一致。

### R2. 检测范围限定在输出尾部

与现有两条分支同一理由:限定尾部避免全量输出里无关的 `429`/`quota` 字样造成误判
(误判会停派该执行器整段冷却期)。**沿用 `lastLinesOf(out, 20)`,不要放宽。**

### R3. 不改检测关键词

`dispatch-policy.json` 的 `detectPatterns` **保持不变** —— `window exhausted`
已经在列表里,本次没被命中纯粹是因为成功路径不调用检测,不是关键词不够。

### R4. 不扩大到"空转检测"

**本票只处理额度关键词命中这一种情况。**

「执行器正常退出但没有实质产出」是更大的话题(缺凭据、环境不满足、误判任务已完成
等等),涉及如何定义"实质产出",不在本票范围。**不要顺手加一个"没有 commit 就算
失败"的规则** —— 有些任务本来就不产生提交(纯调研、纯验证)。

## 验收标准

- [ ] 执行器 exit 0 且输出尾部含 `window exhausted` → 任务落 **`failed`**,不是 `done`
- [ ] 同上,该执行器进入冷却(`isInCooldown` 为 true)
- [ ] 同上,**不发生自动重试**(`retryCount` 不增长)
- [ ] 同上,回传含预计恢复时间
- [ ] 执行器 exit 0 且输出**不含**额度关键词 → 行为**与改动前完全一致**(回归,必测)
- [ ] 额度关键词出现在输出**前部但不在尾部 20 行** → **不**命中(R2,避免误判)
- [ ] 超时分支(1261)与失败分支(1365)行为**未改变**(回归,必测)
- [ ] 成功路径的额度处理与失败分支(1365)行为逐条一致
- [ ] `dispatch-policy.json` 未被改动
- [ ] 后端测试全绿,贴出用例数;上述每条验收都要有对应用例

## 不涉及

- 「正常退出但无实质产出」的通用检测(R4)
- 额度关键词列表(R3)
- 自动切换到其它执行器 —— 那是协调者按 skill §2.2 的职责,不是平台的

- 本仓 pnpm 项目,后端 `:3001`

  确认监听进程启动时间晚于本次提交

  或等待恢复

## R6 — 干净退出路径的额度判定必须以「本次运行是否有产出」为闸(v1.1 新增)

v1.0 把额度判定接进了干净退出分支,方向正确;但它**只看行、不看结局**,于是
反向误伤:一次**正常做完并提交**的运行,因为中途出现过瞬时限流退避行,被判成
额度耗尽、任务标 `failed`、执行器被冷却 5 小时。

### 实证(2026-08-30,任务 `01a05103-db4c`)

AtomCode 执行 T4,输出尾部是完整收尾:

```
[tool→ bash #t1407] … git add -A && git commit -m 'feat(token-usage): R4 补别名 …'
[tool← ok #t1408] 125 chars
[done] 1768.0s tokens=1.83M turns=31 tool_calls=49
```

提交 `1862e03f` 真实存在,别名三条补齐,附 101 行新测试。但运行**中途**出现过
三次:

```
[rate-limited] auto-continuing in 3s…
```

平台判定结果:

```
error: exit 0(执行器额度限制,预计 2026/8/30 18:22:51 恢复)
quotaMatchedLine: "[rate-limited] auto-continuing in 3s…"
executorCooldownEndMs: 1788085371132     ← +300min 兜底,该行本就无恢复时刻可解析
```

**代价:一张已完成的票被标失败,主力执行器被无故停派 5 小时。**

### 根因

`state.ts` 的 `PROVIDER_ERROR_LINE_SHAPES` 第二条:

```js
/^\s*\[(?:rate[- ]?limit(?:ed)?|quota|limit|429)\]/i
```

方括号限流标签被当作「结构证据」。标签本身没错 —— 错在它**不区分「耗尽」与
「瞬时退避」**。`auto-continuing in 3s` 是自愈通知,行内就写明 3 秒后继续。

与 v1.0 原案对照,真正的判别信号不是措辞,而是**这次运行有没有产出**:

| | 匹配行 | 本次运行产出 | 应判 |
|---|---|---|---|
| v1.0 原案 | `5h window exhausted — resets around 13:33` | **未产出任何文件** | 额度 ✅ |
| v1.1 本案 | `auto-continuing in 3s…` | 提交 + 测试 + `[done]` | **不是额度** ✅ |

这与本 spec 的立论是同一条原则的两面:v1.0 说「不该把退出码等同于任务成功」,
R6 说「**也不该把一行限流字样等同于任务失败**」。

### 要求

- **主闸(必须实现):** 退出码为 0 时,仅当本次运行**没有产出**才可判为额度。
  「有产出」的判据取平台已有的能力:**任务窗口内存在本次运行产生的提交**。
  有提交 → 一律不判额度,无论输出里出现过什么限流字样。
- **次闸(建议实现):** 命中行若自述在**短间隔内自动恢复**
  (形如 `auto-continuing in <N>s` / `retrying in <N>s`,N 小于最小有效冷却),
  该行**不单独构成结构证据** —— 它描述的是自愈,不是耗尽。
- ⚠️ **非零退出路径逐字不变**:进程失败/超时分支的判定不受本条影响。
  本条只收紧**干净退出**这一条路径。
- ⚠️ **不得放宽 v1.0 抓到的原案**:构造「`window exhausted` + 零产出 + exit 0」
  仍必须判为额度并冷却 —— 这是本条的反向必测。

### 验收标准(v1.1)

1. `exit 0` + 输出含 `[rate-limited] auto-continuing in 3s…` + **有提交**
   → 任务落 `done`(或交由 L2 裁定),**不判额度、不下冷却**。必测。
2. `exit 0` + 输出含 `window exhausted — resets around HH:MM` + **无提交**
   → 仍判额度、冷却至解析出的时刻(v1.0 原案回归)。必测。
3. `exit 0` + 限流字样 + **无提交** + 无可解析恢复时刻 → 判额度,走固定兜底冷却
   (与 v1.1 R7 的回退口径一致,见 `quota-exhaustion-triggers-infinite-retry`)。
4. **非零退出**路径的既有判定与文案**逐字不变**(回归,必测)。
5. `quotaMatchedLine` 留痕保持;新增「因存在提交而不判额度」时,
   在 `diffSummary` 留一条可读说明,便于事后区分「没匹配到」与「匹配到但被闸掉」。

## R9 — 「有产出」的判据必须可归因到本次运行(v1.2 新增)

R6 的主闸把「有产出」定义为「任务窗口内存在**本次运行产生的**提交」,方向对;
但实现落成的是**共享工作树上 HEAD 前进了几个提交**:

```ts
// claim-verification.ts: hasCommitInTaskWindow
const count = await gitExec(["rev-list", "--count", `${checkpointRef}..HEAD`], repoRoot);
return n > 0;
```

函数自己的注释写着这个探针「与时钟完全无关」、能「严格排除上一轮运行的提交」。
**这个不变量只在独占工作树上成立。** 本部署里,检视者与执行器写的是同一棵树 ——
执行器跑着的时候,检视者随时可能提交一份冻结的 spec。那条提交落在
`checkpointRef..HEAD` 里,与执行器的产出完全无法区分。

### 实证(2026-08-31,任务 `01a05392-d476`)

CodeBuddy 跑了 35 分钟,把 8 个文件 staged 后撞上**真实 429**
(`您的使用量已超出频率限制,将在 2026-08-31 18:03:10 重置`),**未提交**。
同一窗口内,检视者提交了两份 spec(`e482b390`、`2e3f57de`)。平台判定:

```json
"quotaMatchedButCommitFound": {
  "note": "输出尾部命中额度关键词,但任务窗口内存在提交(本次运行有产出),…不判额度、不进入冷却",
  "matchedLine": "429 您的使用量已超出频率限制,将在 2026-08-31 18:03:10 UTC+8 重置…"
}
```

任务落 `done`,CodeBuddy 显示 `available`。它实际要到 18:03 才恢复。

⚠️ 这条与 R6 的起因**方向相反、形状相同**:R6 修的是「把自愈行当成耗尽」,
R9 修的是「把别人的提交当成自己的产出」—— 两次都是**拿一个近似量代替它所
指代的事实**。R6 自己就是上一次修误判时加的闸。

### 根因:两道闸的可归因性被搞反了

| | 判据 | 读的是什么 | 可归因 |
|---|---|---|---|
| 主闸(**必须**实现) | 窗口内有提交 | 共享工作树的**全局状态** | ❌ |
| 次闸(**建议**实现) | 命中行自述短间隔自愈 | 命中行**自身的文本** | ✅ |

spec 把**不可归因**的那道定为必须、**可归因**的那道定为建议;实现照做,
于是次闸至今没写(`state.ts` 中无 `auto-continuing` / `retrying in` 判据),
整条 R6 由唯一一道不可归因的闸独自承担。

### 要求

- **R9-a(必须):次闸升为必须实现。** 命中行自述在短间隔内自动恢复
  (`auto-continuing in <N>s` / `retrying in <N>s`,N < `MIN_EFFECTIVE_COOLDOWN_MS`)
  → 该行**不单独构成结构证据**。此判据只读命中行本身,与工作树无关,
  是 R6 起因(`01a05103-db4c`)真正需要的那道闸。
  ⚠️ 与 `transient-ratelimit-escalated-to-long-cooldown` 的分级**不得另起一套**:
  该 spec 已在 `classifyQuotaFailure` 内单点产出 `kind`,本条复用它,
  不新增第二处判定(**两套判据是本轮反复咬人的根因**)。

- **R9-b(必须):主闸的「有产出」改为可归因判据。**
  `checkpointRef..HEAD` 计数 > 0 **不再单独构成「本次运行有产出」**。
  可归因的证据取平台已有能力:**汇报中声明、且经 `verifyCommitClaim` 核实的提交**。
  无可归因证据 → 按「无产出」处理。

- **R9-c:接受由此产生的保守偏差,并写明理由。**
  「提交了但没写汇报段」的运行会失去豁免,可能被误判额度、进入冷却。
  **接受**:冷却是自愈的(到期自动解除,检视者也可手动清);而误判「有产出」
  会把下一张票派给一个真的已耗尽的执行器,并把失败记录整个抹掉 ——
  后者不可自愈。⚠️ 实现**不得**为了消除这条偏差而回退到 HEAD 计数。

- ⚠️ **不得放宽 R6 的反向必测**:`window exhausted` + 零产出 + exit 0
  仍必须判额度并冷却。

### 验收标准(v1.2)

1. 构造「exit 0 + 命中额度行 + 窗口内存在**非本次运行**的提交(直接在测试仓里
   由第三方身份提交)+ 汇报中**无**提交声明」→ **判额度、进入冷却**。
   ⚠️ 这是本条存在的直接理由,必测。
2. 构造「exit 0 + 命中额度行 + 汇报声明提交且 `verifyCommitClaim` 核实通过」
   → **不判额度、不冷却**,`quotaMatchedButCommitFound` 留痕保持(R6 正向回归)。必测。
3. `[rate-limited] auto-continuing in 3s…` + **零提交、无汇报声明** →
   该行不构成结构证据 → `isQuota: false`(R9-a;这是 R6 起因案例在
   **不依赖工作树**的前提下应有的结局)。必测。
4. `window exhausted — resets around HH:MM` + 零产出 + exit 0 → 仍判额度并冷却
   (R6 反向必测,逐字回归)。必测。
5. **非零退出**路径逐字不变(回归,必测)。
6. 留痕能区分三种结局:「未命中」/「命中但被次闸掉」/「命中但有可归因产出」。
