> **状态**: Frozen
> **版本**: 1.0
> **日期**: 2026-09-08
> **来源**: `docs/implementation-optimization-review-2026-09-07.md` §10
> **用户决策(2026-09-08)**:采纳,**现在实施**。
> 报告 §10.2 原文写「本文不改变当前生效规则…需要另行冻结职责变更方案」——
> **本 spec 就是那份方案**,落地后规则即生效。
> **范围**:仅 **§10.5 的「第一版」**(职责、计划与诊断模板、续跑加载计划)。
> 第二版(工作项持久化 / API / 前端)与第三版(自动依赖调度)**不在本票**。

## 1. 背景与目标

### 1.1 这不是从零加能力

`skills/coordinator/SKILL.md` 已有的基础:

- §2.1 每张任务书只有一个内聚关注点;
- §2.3 一次派一个 → 退出本轮 → 续跑后推进下一项;
- 平台仍是「一条有效派发消息创建一个 task」,**不会自行理解长消息并拆分**。

### 1.2 真正的缺口(检视者已复核代码与 skill,不是转述报告)

续跑任务书(`coordinator-resume.ts` 的 `buildResumeBrief`)带回的是:

| 带回的 |
|---|
| 父任务 id、`specRef`、`specHash` |
| 本次终态子任务的 id、状态、完整 `diffSummary` |
| 全部子任务的 id 与当前状态 |
| 操作指引(做 L2 → 结案父任务 → 结案续跑任务) |

`skills/coordinator/SKILL.md:138` 给出的理由是:

> L2 是「对着冻结规范检视产出」,本就只依赖**可复得的事实**
> (仓库里的 spec、`diffSummary`、任务详情 API),
> **不依赖上一轮 CLI 里想过什么**。

**这个设计对 L2 完全正确。** 问题在于 §10 要新增的三件事**恰好都依赖
「上一轮想过什么」**:

1. **拆分计划** —— 有哪些工作项、哪些已验收、依赖关系;
2. **未派发的剩余计划** —— 它连 task 行都还没有,任何基于 task 的查询都看不到;
3. **Bug 根因诊断** —— 验证过哪些假设、**排除了哪些**。

这三样**都不在上表里**,也无法从 spec + `diffSummary` + 任务详情 API 推得。

⚠️ **本轮实证**:2026-09-08 协调者交 L3 时,`diffSummary` 里**没有
`review_request` 载荷**,检视者只能从群消息里重建它的状态
(见 [dispatch-must-not-spawn-the-reviewer.md](dispatch-must-not-spawn-the-reviewer.md) §3 R4 的顺带记录)。

### 1.3 目标

**让「技术分析」有统一产物,且该产物能随协调者续跑完整恢复 ——
在不新增数据库实体、不改平台代码的前提下。**

## 3. 详细改动

### R1. 职责切分线:切的是职责 A 的中间两步

检视者 skill 的**职责 A** 是四步。本票的切分线:

| 步 | 内容 | 本票之后归谁 |
|---|---|---|
| §3 Grill — 对齐需求 | 与用户对齐目标、范围、期望行为 | **检视者保留** |
| §4 Review Code Architecture | 读 `CONTEXT.md` / `architecture.md` / `adr/`,阅读实现 | **协调者接** |
| §5 Write the Spec | 起草方案与拆分 | **协调者接** |
| §6 Freeze and Publish | 确认、冻结、公布 `spec_published` | **检视者保留** |

**为什么这条缝是对的**:reviewer skill §3 的 grill 规则本来就写着
「**facts are findable in the codebase/docs and are YOUR job to find,
never the user's**」—— 这个「找事实」正是 §10.2 要挪走的「阅读实现」。
挪的是找事实,**不是**挪与用户对齐决策。

**新流程**:
检视者明确需求 → **协调者技术细化与拆分(产出计划 + spec 草案)**
→ 检视者确认并冻结完整 spec → 协调者逐项下发和验收。

### R2. ⚠️ 唯一来源纪律:指向,不复制

`skills/coordinator/SKILL.md:71` 已经立过这条规矩:

> ⚠️ **严禁把 Grill / To-Spec 段落内容复制回本 skill。** 本段只写这一句指向——
> reviewer skill 是这套纪律的唯一事实来源。两份同样的纪律会各自演化并逐渐不一致,
> **正是三角色拆分最初要消除的问题**。

**本票必须复用同一机制,不得新造第二套写 spec 纪律。**

但**继承范围与两方编制不同,必须写清楚**:

| 编制 | 协调者继承的范围 |
|---|---|
| **两方**(无 reviewer 成员) | 职责 A **整体**(含 §3 grill 与 §6 冻结)—— 既有约定,**本票不改** |
| **三方**(本票新增) | **仅 §4–§5**(读架构 + 起草)。**不做 §3 grill,不做 §6 冻结。** |

协调者 skill 里写的是**一句带范围的指向**
(例如「按 `GET /api/skills/reviewer` 的 §4–§5 起草;§3 与 §6 不属于你」),
**不是**把模板和纪律抄一遍。

### R3. 计划产物:`plans/<spec 同名>.md`

**位置决策(检视者裁定,理由写在这里以免后来者反复)**:

报告 §10.3 给了两个选项:「作为 spec 的一部分」或「有明确版本引用的配套文档」。
**本票选配套文档**,理由:

- **spec 是冻结的**(`specHash` 是验收锚点),而**计划是会变的**
  —— 派发后要回填 `taskId`、验收后要标完成。
  把变动的东西塞进冻结文件,要么破坏冻结,要么每完成一项就得修订一次 spec;
- 放 `plans/` 而不是 `specs/`:`specs/` 已有 176 份、可检索性出过问题
  (报告 §13.7 **D3**),不再往里加新品类。

**路径规则**:`specs/<name>.md` → `plans/<name>.md`。
**从 `specRef` 直接推得** —— 这是 R5 能免改平台代码的前提。

**每个工作项至少记录**(报告 §10.3 原文):
稳定编号、目标、范围、前置依赖、预期产物、验收方法、`specRef`/`specHash`,
以及派发后对应的 `taskId`。

**工作项 ≠ task**:
工作项表示「要完成的事情」,task 表示「一次执行」。
重派产生的多个 task 可属于同一工作项,沿 `supersedesTaskId` 保留证据。
⚠️ **未派发工作项不得伪装成 queued task。**

拆分按**可独立验收的内聚结果**进行,**不机械按文件或步骤切碎**。
紧密相关的实现与回归测试通常属于同一工作项;
接口依赖未解决时**不提前派发下游实现**。

### R4. Bug 诊断产物:`plans/<name>.md` 的诊断段

下发修复**前**保存(报告 §10.4 原文):

- 现象、期望行为和可复现步骤;
- 已观察事实及**证据位置**;
- 根因假设、验证动作、验证结果;**明确排除的假设**;
- 建议修复范围与**不能改变的行为**;
- 能暴露旧问题的回归场景和最终产物验收方式。

⚠️ **根因未确定时,先派有具体问题和停止条件的调查任务**,
**不把未经证实的猜测写成执行器必须遵守的事实**。

执行器发现反证应反馈并修订方案;
修复越过冻结 spec 的行为或架构契约时,按现有流程交检视者修订。

### R5. 续跑加载计划 —— **不改平台代码**

续跑任务书已经带回 `specRef`。计划路径由 `specRef` 推得(R3),
**所以协调者自己就能找到计划文件,不需要平台把它塞进任务书。**

⚠️ **这是本票免于「构建 + 受控重启」代价的关键**,不要为了「更方便」
去改 `buildResumeBrief` —— 那会让一次文案级改动付出平台发布的代价
(正是 [ticket-text-is-workflow-policy-not-scheduler-code.md](ticket-text-is-workflow-policy-not-scheduler-code.md)
要治的病)。

**协调者被续跑拉起后的顺序(写进 skill)**:

1. 读 `plans/<name>.md`(从 `specRef` 推路径;**文件不存在 = 本需求还没有计划**,
   不是错误);
2. 读续跑任务书带回的**全部子任务当前状态**;
3. **以 task 事实为准校正计划** —— 见下。

⚠️ **计划是提示,task 事实是权威。** 报告 §10.3 原文:
「续跑时读取计划、当前 task 事实和验收证据,再决定下一步。
**先核对是否已有对应 task**,避免因上下文丢失重复派发。」

具体地:协调者若在**派发成功之后、回填 `taskId` 之前**退出,
计划会显示该项「未派发」而实际已派。
**因此必须先按子任务列表核对,再决定派不派**,不得只看计划就重派。

**父子关系不得假设**:报告 §10.3 明写
「父子关系的建立还需验证原协调 task 与续跑 task 的关联,
**不假设恢复会话就自动保持计划归属**」。skill 里要写明这一步要验证。

  为什么第一版不引入 DB 实体)。

### R7. 明确不变的部分(防止过度解读)

- **L3 永远是检视者的**,协调者不做 L3、不做自审;
- **两方编制的整体继承约定不变**(§3 R2 表);
- 平台**不解析计划文件**,它对平台不可见 —— 计划是角色间的约定,不是平台机制;
- `spec_published` / `review_request` / `review_result` 载荷契约不变;

## 4. 验收标准

报告 §10.5 第一版要求「至少包含**一个多工作项需求**和**一个根因起初未知的 Bug**」。

1. **多工作项需求走通**:
   一个需求 → 协调者产出 `plans/<name>.md`(≥3 个工作项,含依赖)+ spec 草案
   → 检视者冻结 → 协调者逐项下发。
   **贴出计划文件实际内容。**
2. **续跑恢复依据与剩余计划**:
   在**至少一项已完成、仍有未派发项**时让协调者退出并被续跑拉起,
   断言它**恢复出了剩余计划**并继续推进。
   ⚠️ **给出协调者退出前后的实际输出对照**,不接受「设计上可以」。
3. **已验收项不重复下发**:
   构造「派发成功但计划未回填 `taskId`」的状态 → 续跑 →
   断言协调者**先核对子任务列表**、**没有重派**(R5)。
   ⚠️ 这是本票最容易漏的一条 —— 它正是「计划是提示、task 是权威」的检验。
4. **根因起初未知的 Bug 走通**:
   诊断段落含**被排除的假设**(不只是最终根因);
   根因未定时先派了**带停止条件的调查任务**(R4)。
   贴出诊断段实际内容。
5. **执行器能按单项契约独立实现**:执行器只读该工作项 + spec 即可完成,
   不需要读整份计划。
6. **零平台代码改动**(R5):`git show --stat` 不得出现
   `packages/**/src/**`。**硬约束。**
7. **未复制写 spec 纪律**(R2):协调者 skill 里是**一句带范围的指向**,
   `grep` 不到从 reviewer skill 抄来的模板正文。
8. **五处文档同步**(R6):逐项指出改在哪一句;ADR 是追加而非抹改。
9. **两方编制未受影响**:`skills/coordinator/SKILL.md` §1.2 的整体继承约定
   逐字未改(或若改了,逐行说明为什么)。

## 5. 不涉及的改动

- **第二版**(工作项持久化、task 映射、进度与依赖展示)与
  **第三版**(自动依赖调度、隔离并行、合并与失败恢复)——
  报告 §10.5 分别评为中、高难度,**本票不做**;
- **不改任何平台代码**(R5);
- 不改 L3 归属、不改两方继承约定、不改载荷契约;
- 不引入新的数据库实体(报告 §10.3 明确第一版不做);
- 不改「一条有效派发消息创建一个 task」的平台语义。

## 6. 兼容性

- **流程变更(需在汇报中写明)**:此前是「检视者先产出冻结 spec,再交协调者」;
